**숫자·범주로 정리된 업무 데이터를 분류·예측한다면, 전통적인 ML은 먼저 비교할 가치가 있는 후보입니다. 다만 ‘표 데이터는 항상 트리’, ‘소규모 데이터는 항상 ML’이라는 규칙으로 선택을 끝낼 수는 없습니다.**

이 글에서 전통적인 ML은 선형·로지스틱 회귀, Random Forest, 그래디언트 부스팅 트리(GBDT: XGBoost·LightGBM·CatBoost 등)를 뜻합니다. DL과 LLM도 머신러닝에 포함됩니다. 또한 여러 트리를 결합한 GBDT까지 모두 ‘단순하고 설명하기 쉬운 모델’이라고 부르는 것은 부정확합니다.

수업 주제에 대한 후속 리서치 노트입니다. 아래에서 논문이 확인한 결과와, 그 결과를 업무에 적용하기 위한 기획 제안을 구분합니다.

## 1. 먼저 볼 연구 결과 — 어느 조건에서 비교했는가?

| 연구 | 확인한 결과 | 선택에 적용할 점과 한계 |
|---|---|---|

## 2. 전통적인 ML을 먼저 비교할 이유 — 유용한 정보가 이미 열로 정리되어 있는가?

이미지나 긴 문장에서는 원본에서 어떤 정보를 추출할지가 큰 과제입니다. 반면 업무 표에는 ‘최근 구매 횟수’, ‘평균 처리 시간’, ‘상품 유형’처럼 사람이 의미를 정의한 열이 들어 있습니다. 이 경우에는 유용한 표현을 처음부터 학습하는 것보다, 열 사이의 조건과 결과의 관계를 학습하는 일이 중심일 수 있습니다.

예를 들어 ‘최근 문의가 늘었고 이용 빈도는 줄어든 계정’을 찾는 문제는 이미지 이해와 요구 조건이 다릅니다. 열의 단위도 제각각이고 특정 경계에서 결과가 달라질 수 있습니다. 이런 데이터 특성은 트리 계열을 먼저 비교할 이유가 됩니다. 관련 벤치마크도 불규칙성·불필요한 특성에 대한 모델별 차이를 관찰했습니다. [Grinsztajn 외](https://proceedings.neurips.cc/paper_files/paper/2022/file/0378c7692da36807bdec87ab043cdadc-Paper-Datasets_and_Benchmarks.pdf)

**기획에 적용할 질문:** 이미 있는 업무 열로 예측할 수 있는가, 아니면 이미지·문장·시계열 원본에서 중요한 표현을 새로 얻어야 하는가?

전처리와 특성을 만드는 비용도 포함해야 합니다. 사람이 매우 많은 규칙과 특성을 수작업으로 만들어야 한다면, 전통적인 ML의 모델 실행 비용만 낮게 나와도 전체 개발 비용이 낮다고 할 수 없습니다.

## 3. 데이터가 적을 때 — 처음부터 학습할 것인가, 사전학습을 활용할 것인가?

데이터가 적으면 ‘새로 학습할 모델의 자유도를 감당할 수 있는가’를 검토해야 합니다. 하지만 사전학습된 모델을 가져오는 상황에서는 이미 학습한 지식과 표현을 활용할 수 있습니다. TabPFN과 TabLLM의 결과는 이 구분이 필요함을 보여 줍니다.

따라서 ‘몇 행 이하면 무조건 ML’이라는 공통 숫자보다 다음을 확인하는 편이 실용적입니다.

- 확보한 정답이 실제 사용 상황을 대표하는가?
- 열 이름·문장에 사전학습 지식을 활용할 의미가 있는가?
- 회사 내부 코드처럼 의미가 감춰진 입력인가, 일반 언어로 설명할 수 있는 입력인가?
- 해당 사전학습 모델이 우리 입력 형태와 실행 환경을 지원하는가?

예를 들어 `최근 30일 반품 횟수`는 의미를 전달하지만, 설명 없는 `internal_code_731`만으로는 어떤 업무 의미인지 알기 어렵습니다. 이 차이를 보고 LLM이 가진 언어 지식이 실제 예측에 도움이 될지 가설을 세울 수 있습니다. 이는 개별 업무에서 검증할 제안이며, 모든 내부 코드에 LLM이 실패한다는 뜻은 아닙니다.

**기획 인사이트:** 정답 데이터의 개수와 함께, 외부에서 미리 배운 지식을 가져올 통로가 있는지를 본다.

## 4. LLM은 무엇을 맡길 것인가 — 문장 이해와 업무 예측을 나눠 보기

‘긴 문의를 읽고 약속한 날짜를 추출하는 일’과 ‘그 계정이 다음 달에 재문의할 가능성을 예측하는 일’은 구분할 수 있습니다. 앞의 역할에는 언어 이해가 필요하고, 뒤의 역할에는 과거 결과와 입력 사이의 관계가 필요합니다.

다음은 비교해 볼 수 있는 설계안입니다. 성능 향상이 확인된 실제 프로젝트 사례는 아닙니다.

| 설계안 | 맡기는 역할 | 추가로 확인할 점 |
|---|---|---|
| 업무 표 → GBDT | 기존 숫자·범주로 결과 예측 | 현재 열만으로 필요한 정보를 담는가? |
| 문의 → 언어모델 → 추출 항목 + 업무 표 → ML | 언어모델은 추출, ML은 예측 | 추출 오류가 최종 예측에 주는 영향과 추가 비용 |
| 문장·이미지 → 사전학습 임베딩 → 분류 모델 | 원본의 표현을 활용해 분류 | 임베딩 생성 비용, 업데이트 시 결과 변화 |
| 입력 → LLM으로 직접 분류 | 사전학습된 언어 지식을 바로 활용 | 적은 정답 데이터 조건의 이점이 운영 비용을 상쇄하는가? |

예측 이유를 사용자에게 설명할 때도 모델이 실제로 사용한 정보와 검증한 근거를 연결해야 합니다. 점수만 LLM에 전달해 그럴듯한 이유를 만들게 하는 방식은 설명의 정확성을 별도로 확인해야 합니다.

## 5. 모델을 바꿀 이유는 점수 차이를 업무 효과로 환산해 판단하기

다음은 **설명을 위한 가정**입니다. 담당자가 하루에 문의 100건만 우선 검토할 수 있다면, 전체 정확도 외에 ‘상위 100건 중 실제로 긴급한 문의가 몇 건인가’를 비교할 수 있습니다. 이를 Precision@100으로 표현할 수 있고, 전체 긴급 문의 중 얼마나 찾았는지는 Recall@100으로 함께 봅니다.

같은 검토량에서 DL·LLM이 추가로 찾은 긴급 문의가 있는지, 그 개선이 다른 기간에도 유지되는지 확인합니다. 그다음 다음 비용을 계산합니다.

- 정답 수집·검수와 특성 설계 비용
- 튜닝·재학습·버전 검증 비용
- 실제 요청량에서의 추론 비용과 느린 요청의 응답 시간
- 형식 오류·재시도·사람 검토·장애 대응 비용

비교하려는 고급 모델의 **추가 가치**는 다음처럼 업무 단위로 정리할 수 있습니다.

> 같은 기간에 추가로 해결한 업무의 가치 + 줄어든 오류·재작업 비용 − 추가 개발·추론·운영 비용

이 식은 기획 검토 틀입니다. 구체적인 값과 합격 기준은 업무 담당자와 정해야 합니다. 평균 점수가 조금 높은 모델도 실제 검토 대상에서 개선이 없으면, 그 변경의 효과를 다시 확인할 이유가 있습니다.

## 6. 설명 가능성과 확률 — 전통적인 ML도 자동으로 해결해 주지 않는다

**단순한 모델의 장점과 인과 설명을 구분합니다.** 선형 모델의 계수나 변수 중요도를 확인할 수 있어도 ‘이 변수를 바꾸면 결과가 개선된다’는 결론은 별개입니다. 예측 모델은 관측 데이터의 연관 관계를 학습하며, 숨은 변수 때문에 해석이 달라질 수 있습니다. [scikit-learn 인과 해석 예제](https://scikit-learn.org/stable/auto_examples/inspection/plot_causal_interpretation.html)

예를 들어 이탈 가능성이 높은 사용자를 잘 찾는 것과, 쿠폰을 줬을 때 이탈을 막을 수 있는 사용자를 찾는 것은 다른 질문입니다. 후자의 의사결정에는 개입 효과를 확인할 실험이나 인과 분석 설계가 필요합니다.

**확률값을 출력한다고 확률이 맞는 것도 아닙니다.** ‘위험도 80%’로 표시할 계획이라면, 비슷한 점수를 받은 사례의 실제 발생 비율도 확인해야 합니다. 보정 곡선과 확률 예측 지표를 함께 봅니다. Brier score나 log loss 하나만으로 확률 보정의 좋고 나쁨을 단정하지 않습니다. [scikit-learn 확률 보정 문서](https://scikit-learn.org/stable/modules/calibration.html)

따라서 기획 단계에서 필요한 것이 ‘우선순위 점수’인지, ‘발생 확률’인지, ‘행동을 바꿀 이유’인지 명확히 해야 합니다.

## 7. 실제로 선택할 때 사용할 비교 순서

다음은 위 연구를 참고해 정리한 실험 제안입니다. 모든 모델을 반드시 실행하라는 절차는 아닙니다.

1. **예측 시점과 후속 행동부터 고정한다.** 언제 알 수 있는 정보로 무엇을 예측해 누가 어떤 결정을 내릴지 적는다.
2. **규칙·선형 모델·GBDT로 기준선을 만든다.** 숫자 예측이면 회귀, 분류면 로지스틱 회귀처럼 문제에 맞는 작은 비교안을 함께 둔다.
3. **검증 분할을 실제 사용에 맞춘다.** 미래를 예측하면 과거로 학습해 뒤의 기간으로 평가한다. 새 계정에 적용한다면 계정이 학습·평가에 섞이지 않도록 비교한다. 전처리와 특성 선택도 학습 데이터 안에서 수행한다. [데이터 누수 방지 원칙](https://scikit-learn.org/stable/common_pitfalls.html#data-leakage)
4. **DL·기반 모델·LLM을 추가할 이유를 한 가지씩 적는다.** 원본 표현을 학습해야 하는가, 사전학습을 활용할 수 있는가, 기존 모델이 놓친 사례가 명확한가? 표 데이터라면 튜닝한 작은 신경망이나 표 전용 기반 모델도 후보가 된다.
5. **같은 정보와 정답으로 비교한다.** 모델별 개발 시간을 포함한 총 예산을 기록하고, 추가 정보까지 사용한 실험은 별도 비교안으로 구분한다. 프롬프트·모델 선택에는 검증 데이터를 쓰고, 최종 평가 데이터로 반복 선택하지 않는다.
6. **업무 지표·비용·운영 조건으로 채택한다.** 여러 기간이나 분할에서 결과가 유지되는지, 특정 사용자 집단에서만 좋아진 것은 아닌지 확인한다. 차이가 불안정하면 우열을 보류한다.

|---|---|
| DL·LLM이 새로 활용할 정보는 무엇인가? | 같은 열을 더 복잡한 모델에 넣는 것 이상의 이유가 있는가? |
| GBDT 기준선의 전처리·튜닝은 어느 정도 했는가? | 약하게 설정한 비교 모델을 이긴 결과는 아닌가? |
| 데이터가 적다는 말은 정답이 적다는 뜻인가, 활용 가능한 사전학습도 없다는 뜻인가? | 데이터 수만으로 후보를 제외하고 있지 않은가? |
| 현업이 처리할 수 있는 양에서 결과가 얼마나 개선됐는가? | 모델 점수가 사용자 행동과 연결되는가? |
| 추가 품질을 얻는 데 드는 전체 비용은 얼마인가? | 실행 비용 외에 개발·검수·운영을 포함했는가? |
| 예측 이유와 실제 개입 효과를 구분했는가? | 설명을 행동 권고로 과장하지 않는가? |
