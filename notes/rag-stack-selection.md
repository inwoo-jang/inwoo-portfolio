“할인 조건을 작게 표시한 SNS 광고의 심결을 찾아줘. 위원회가 적용한 조문과 이후 개정 내용도 알려줘.”

이 질문에는 세 가지 일이 들어 있다. 유사 심결을 찾고, 해당 광고에 관한 판단 문단을 골라내고, 적용 조문의 버전과 개정 이력을 확인해야 한다. 첫 번째는 검색과 랭킹, 두 번째는 근거 선택, 세 번째는 데이터 모델링과 조회에 가깝다. 어떤 단계에서 실패하느냐에 따라 바꿔야 할 기술도 달라진다.

## 전체 흐름

| 흐름 | 입력에서 결과까지 |
|---|---|
| 데이터 준비 | 원문 수집 → 문서·문단 분리 → 식별자·메타데이터 정리 → 검색 인덱스 구축 |
| 질문 처리 | 질문 해석 → 후보 검색·결합 → 재랭킹 → 근거 문단·적용 조문 조회 → 답변 생성·검증 |
| 운영 | 단계별 오류 기록 → 평가 질문으로 회귀 확인 → 원문·법령 버전 갱신 |

## 원문에서 무엇을 저장할까?

심결문은 사건 전체와 판단 문단을 함께 보관한다. 검색 단위는 문단이나 쟁점으로 잡고, 결과에서 원문 위치와 사건 전체를 다시 열 수 있게 연결한다. 문단이 너무 짧으면 판단에 필요한 앞뒤 내용이 빠질 수 있으므로, 문단을 찾은 후 인접 문단이나 상위 섹션을 함께 가져오는 방법도 있다. 스캔 문서라면 OCR 결과에 원본 페이지 위치를 남긴다.

| 모델 | 기록하는 것 | 필요한 경우 |
|---|---|---|
| 태그·분류체계 | 매체, 상품 유형, 쟁점 | SNS 사례만 보기처럼 분류 기준이 명확할 때 |
| 관계형 스키마 | 사건, 광고, 쟁점별 판단, 적용 조문 버전과 그 연결 | 관계가 정해져 있고 SQL로 반복 조회할 때 |
| 온톨로지 | 개념과 관계가 뜻하는 바 | 심결·법령·가이드라인에서 ‘인용’, ‘적용’, ‘개정’을 공통 의미로 쓰고 싶을 때 |
| 지식그래프 | 실제 개체와 관계 | 심결에서 관련 조문, 개정 법령, 다른 심결로 이어지는 경로를 탐색할 때 |

예를 들어 ‘위원회가 적용함’은 위원회의 쟁점별 판단에서 적용 근거가 확인된 경우에 기록한다. 관계에는 근거 문단을 남기고, 조문은 번호와 함께 해당 버전을 연결한다. 적용 버전이 불명확하면 미확인으로 남긴다.

이 구조는 SQL로도 구현할 수 있다. 여러 출처에서 관계의 의미를 공유할 때 온톨로지의 가치가 커진다. EU의 ELI-I는 어떤 개정 조항이 기존 법령의 어느 부분을 변경했는지 표현하는 사례다. [W3C OWL 2 Primer](https://www.w3.org/TR/owl2-primer/) · [EU ELI-I](https://interoperable-europe.ec.europa.eu/collection/eli-european-legislation-identifier/solution/eli-i)

## 후보를 어떻게 찾을까?

| 방법 | 강점과 선택 기준 |
|---|---|
| 정확 조회·필터 | 사건번호, 특정 조문 버전, 사용자가 필수로 지정한 매체처럼 명시된 조건에 쓴다. 메타데이터가 비어 있는 사건은 필터에서 빠질 수 있으므로 누락률도 본다. |
| 키워드 검색(BM25 등) | 조문명, 업계 용어, 원문과 일치하는 표현에 강하다. 사건번호 자체는 정규화된 식별자로 조회할 수 있다. |
| 벡터 검색 | ‘할인 조건이 잘 안 보임’과 ‘할인 적용 대상의 표시가 불명확함’처럼 표현이 다른 후보를 찾는다. |
| 하이브리드 검색 | 키워드와 벡터 결과를 합친다. RRF는 각 목록의 순위를 사용한다. 점수 가중 합산을 쓴다면 검색기마다 다른 점수 척도를 맞추는 방법도 정해야 한다. |
| 질문 재작성·분해 | 복합 질문을 ‘유사 심결 찾기’와 ‘적용 조문 개정 이력 조회’로 나눈다. 사건번호나 기준일처럼 원래 질문의 조건은 보존한다. |
| SQL·그래프 탐색 | 확인된 관계를 따라 근거를 조회한다. 조회 경로가 일정하면 SQL 조인으로 시작할 수 있고, 질문마다 탐색 경로가 달라지면 그래프 조회를 비교할 수 있다. |

[Elastic 하이브리드 검색](https://www.elastic.co/docs/solutions/search/hybrid-search) · [Azure AI Search — 하이브리드 검색 순위](https://learn.microsoft.com/en-us/azure/search/hybrid-search-ranking)

## 후보는 찾았는데 순서가 틀리면?

| 재랭킹 방법 | 순위에 쓰는 정보 | 필요한 조건 |
|---|---|---|
| 수동 가중치 | 검색 점수, 매체·쟁점 일치 등 | 학습 없이 비교할 기준선이 필요할 때 |
| Tree 기반 LTR(LambdaMART 등) | 텍스트 점수와 구조화 특징의 조합 | 질문별 후보 관련성 라벨과 학습·평가 데이터가 있을 때 |
| Cross-Encoder | 질문과 후보 문단을 함께 읽어 계산한 관련성 점수 | 같은 쟁점인지 문맥으로 판단해야 할 때. 후보별 계산 비용을 감안해 상위 후보에 적용한다. |
| LLM 재랭킹 | 질문, 후보, 자연어 평가 기준 | 소수 후보에 복합 기준을 적용해 볼 때. 비용·지연과 순위 일관성을 함께 측정한다. |

Cross-Encoder 점수를 Tree 기반 랭커의 입력으로 사용할 수도 있다. 예를 들어 텍스트 관련성 점수에 ‘동일 매체’, ‘검증된 적용 조문 일치’를 함께 학습시킬 수 있다. 필수 조건은 조회나 필터로 처리하고, 선호 조건은 순위에 반영한다.

검색에서 빠진 후보는 재랭킹 단계에서 복구할 수 없으므로, 같은 후보 목록으로 랭커를 비교하고 후보 검색 성능도 따로 측정한다. [Elastic Learning to Rank](https://www.elastic.co/docs/solutions/search/ranking/learning-to-rank-ltr) · [Sentence Transformers — Retrieve & Re-Rank](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)

## 답변에 어떤 근거를 넣을까?

| 구성 | 답변에 공급하는 근거 | 적용 기준 |
|---|---|---|
| 문서 RAG | 검색된 심결문과 법령 문단 | 유사 사례와 원문 요약이 핵심일 때 |
| 문서 RAG + SQL 조회 | 판단 문단과 검증된 적용 조문·버전 | 조문이나 사건 관계를 구조화해 두었고 조회 경로가 일정할 때 |
| 그래프 조회를 활용한 RAG | 여러 관계를 따라 찾은 근거와 원문 | 심결·조문·개정 이력을 연결하는 질문이 반복될 때 |

GraphRAG는 그래프를 근거 검색에 활용하는 접근이다. Microsoft 구현의 로컬 검색은 AI가 추출한 그래프와 원문 조각을 함께 사용한다. 법률 데이터에서는 추출된 관계를 원문과 대조하고, 인용과 실제 적용을 구분해 기록해야 한다.

답변 생성 후에는 사건 ID, 판단 문단, 적용 조문 버전이 조회 결과와 일치하는지 확인한다. ID가 일치해도 근거가 답변의 주장을 뒷받침하는지는 별도로 평가한다. 검색 결과 목록과 원문만 제공하는 기능은 LLM 호출 없이도 구성할 수 있다. [RAG 논문](https://arxiv.org/abs/2005.11401) · [Microsoft GraphRAG — Query Overview](https://microsoft.github.io/graphrag/query/overview/)

## 표시광고 AI 사전검토 서비스(가칭)에서 비교할 구성과 지표

아래는 비교 계획이며, 실제 성능을 검증한 결과는 아니다.

초기 비교는 **정확 조회·키워드 검색 + SQL 근거 조회**를 기준선으로 두고, 표현이 다른 유사 사건을 놓치면 벡터 검색을 결합한다. 후보는 충분한데 순서가 문제라면 수동 가중치와 Cross-Encoder를 같은 후보에 적용한다. 관련성 라벨이 쌓이고 구조화된 신호를 여러 개 반영할 필요가 생기면 Tree 기반 LTR을 비교한다. 여러 출처를 연결하는 질문이 늘어나면 공통 관계 정의와 그래프 조회의 효과를 평가한다.

| 실패 사례 | 먼저 확인할 지표 | 비교할 변경 |
|---|---|---|
| 관련 심결이 후보에 없음 | Recall@K | 검색 방식, 질문 재작성, 필터 누락 |
| 관련 심결이 아래에 있음 | nDCG@K | 수동 가중치, Cross-Encoder, Tree 기반 LTR |
| 사건은 맞지만 판단 문단이 다름 | 올바른 판단 문단 제시율 | 문단 인덱싱, 쟁점 단위 연결 |
| 인용을 적용으로 해석하거나 버전을 혼동함 | 관계 유형·조문 버전 정확도 | 검증된 SQL·그래프 조회, 출처 기록 |
| 답변의 설명을 원문으로 확인하기 어려움 | 원문 근거 확인율, 근거가 주장을 뒷받침하는 비율 | 근거 문단 선택, 인용 검증 |

검색, 재랭킹, 근거 조회를 비교할 때는 평가 질문과 원문 집합을 고정한다. 정확도와 함께 응답 지연, 질의당 비용, 관계 검증과 법령 갱신에 드는 작업량을 기록하면 개선 폭에 맞춰 스택을 선택할 수 있다.

## 표시광고 AI 사전검토 서비스(가칭) 구조에 대입하기

현재 구현은 광고 원문과 OCR·시각 관찰에서 주장과 사실을 추출하고, 주제에 연결된 법령을 조회한다. 심결 후보는 BM25와 벡터 검색으로 찾고 RRF와 규칙으로 정렬한다. 상위 원문을 대조한 뒤 초안·반론·종합 검토를 거쳐 출처를 제시한다. 시각 맥락은 검토에 이미 쓰이며, 추천 구조에서는 이를 별도 심결 검색 입력으로도 사용한다.

추천 구조의 핵심은 **현재 광고를 주장별로 구조화한 뒤 세 경로에서 각각 다른 근거를 찾고, 쟁점 단위로 합치는 것**이다. 아래는 설계안이다.

![광고 문구·이미지·제출 자료를 주장·조건·시각 관찰로 구조화한 뒤 법령·지침, 주장·조건 유사 심결, 시각 맥락 유사 심결의 세 경로로 검색한다. 쟁점별 후보를 통합하고 법령을 연결한 뒤 심결 후보 재랭킹과 상위 원문 대조·검토 의견으로 이어진다.](media/notes/rag-evidence-flow.svg)

| 경로 | 입력 예시 | 가져오는 근거 |
|---|---|---|
| A. 법령·지침 | 할인 조건 고지 쟁점과 기준 시점 | 판단 기준, 적용 범위, 예외, 조문 버전 |
| B. 주장·조건 | ‘최대 50% 할인’, 신규 고객 한정 | 비슷한 주장이나 적용 조건을 다룬 심결의 판단 문단 |
| C. 시각 맥락 | 할인율은 중앙에 크게 표시, 제한 조건은 하단에 작게 표시 | 강조·배치·가독성이 판단에 영향을 준 과거 사례 |

B와 C는 각각 키워드·벡터 결과를 RRF로 결합할 수 있다. C에서 과거 광고 이미지를 확보하지 못한 경우에는 **심결문에 기록된 시각적 특징**을 검색한다. 판독하지 못한 문구와 해석 가설은 관찰 사실과 구분해 저장한다. 세 경로를 합칠 때는 같은 사건이라도 쟁점이 다르면 별도 후보로 유지한다. A의 법령은 심결과 함께 순위를 매기는 후보 대신, 쟁점별 비교 기준과 근거로 연결한다. 적용 조문으로 표시할 관계는 심결 원문에서 확인한다.

## 같은 그림에 나오는 기술의 역할

| 개념 | 이 구조에서 맡는 일 |
|---|---|
| **LangGraph** | 검색 분기, 결과 합치기, 검토 단계와 사용자 답변 대기 등 **실행 순서와 상태**를 관리한다. |
| **최소 온톨로지** | ‘조건이 주장을 제한함’, ‘판단이 조문 버전을 적용함’처럼 **업무 관계의 의미**를 정한다. 초기에는 구조화 출력 스키마와 관계 정의를 SQL에 구현할 수 있다. |
| **지식그래프** | 특정 광고 주장과 조건, 심결의 쟁점별 판단과 조문 버전처럼 **실제 개체 사이의 관계**를 담는다. |
| **GraphRAG** | 지식그래프의 관계를 따라 **답변에 쓸 근거**를 가져온다. 예를 들어 판단에서 당시 조문 버전과 개정 기록까지 찾아 원문과 함께 LLM에 준다. 정식 OWL 온톨로지는 선택 사항이다. |
| **Tree 기반 랭커** | 통합된 심결 후보의 **관련성 순위**를 학습한다. LambdaMART는 랭킹 방식이고 LightGBM은 이를 구현할 수 있는 라이브러리다. 검색 점수는 후보 관련성의 신호로 사용한다. |

[LangGraph — Thinking in LangGraph](https://docs.langchain.com/oss/javascript/langgraph/thinking-in-langgraph) · [LightGBM — Parameters](https://lightgbm.readthedocs.io/en/v4.6.0/Parameters.html)

세 경로 병렬 검색은 LangGraph로 구성하고, 상위 원문을 LLM에 주는 단계에는 문서 RAG를 쓸 수 있다. **GraphRAG가 추가되는 지점은 근거 수집**이다. 검증한 ‘적용함’과 ‘개정함’ 관계를 따라 관련 원문을 찾을 때 적용한다. 조회 경로가 일정한 동안에는 SQL로 적용 조문과 판단 문단을 가져오는 구성을 기준선으로 삼을 수 있다.

구현은 **주장·조건·이미지 영역·판단 문단의 연결 정의 → 과거 심결의 쟁점과 시각 특징 정리 → B·C 검색 품질 비교 → 관련성 라벨 확보 후 트리 랭커 평가 → 검증된 관계를 활용한 GraphRAG 비교** 순서로 잡을 수 있다. 화면에서는 광고 주장별로 이미지 근거, 유사 심결의 판단 문단, 당시 적용 조문, 이번 광고와의 차이를 함께 보여준다.
