> 중요한 것은 어떤 언어가 AI 개발에 더 우수한지가 아니라, 구현하려는 기능과 기존 시스템, 운영 환경에 어떤 기술이 적합한지를 판단하는 것이다.

AI 서비스를 개발할 때 Python을 많이 사용한다. 하지만 기존에 Java와 Spring Boot로 운영하는 서비스라면, AI 기능을 추가하기 위해 반드시 Python을 써야 할까?

Python이 AI 개발에 널리 쓰이는 이유를 살펴보고, Spring Boot + Spring AI와 Python + FastAPI를 비교해 봤다. 이를 통해 모델을 직접 개발하는 것과 기존 서비스에 AI 기능을 연결하는 것의 차이를 이해하고자 한다.

## Python이 AI 개발에 많이 쓰이는 이유

Python의 강점은 언어 자체가 AI 모델을 더 정확하게 만들기 때문이 아니라, 데이터 처리와 모델 학습·실험을 지원하는 라이브러리 생태계가 풍부하기 때문이다.

| 작업 | 주요 역할 | 대표 기술 |
|---|---|---|
| 데이터 처리 | 데이터 정제, 변환, 분석 | pandas, NumPy, Polars |
| 모델 개발 | 모델 학습, 파인튜닝, 성능 평가 | PyTorch, scikit-learn, Transformers |
| AI 서비스 구현 | LLM 연결, RAG, Agent, API 제공 | LangChain, LangGraph, FastAPI |

자체 모델을 학습하거나 파인튜닝한다면 Python 생태계의 장점이 크게 작용한다. 데이터 전처리부터 모델 학습, 평가까지 같은 언어 환경에서 실험하기 편리하기 때문이다.

하지만 외부 LLM API를 활용하는 서비스는 다르다. 사용자 질문을 LLM API에 전달하고 결과를 반환하는 작업은 Java로도 구현할 수 있다. RAG와 Tool Calling 역시 Python만의 기능이 아니다.

그래서 **모델을 직접 개발하는 일과 이미 개발된 모델을 서비스에 연결하는 일은 구분할 필요가 있다.**

## Java에서도 AI 서비스를 만들 수 있을까?

Spring AI는 Java의 Spring 생태계에서 AI 기능을 구현하도록 지원하는 프레임워크다. Python에서는 FastAPI로 API 서버를 만들고 LangChain, LangGraph 등의 라이브러리로 AI 처리 흐름을 구성할 수 있다.

| 비교 항목 | Spring Boot + Spring AI | Python + FastAPI |
|---|---|---|
| 기존 시스템 통합 | Spring 기반 서비스와 연계하기 편리 | API를 통해 별도 연동 가능 |
| LLM API 연결 | 지원 | 지원 |
| RAG | 지원 | 지원 |
| Tool Calling | 지원 | 지원 |
| AI Agent | 지원 | 지원 |
| 모델 학습·실험 | 상대적으로 생태계가 제한적 | 풍부한 라이브러리 생태계 |
| 독립 배포 | 가능 | 가능 |
| 운영 부담 | 아키텍처에 따라 달라짐 | 아키텍처에 따라 달라짐 |

여기서 중요한 건 **언어 선택과 시스템 아키텍처 선택이 별개의 문제**라는 점이다. Spring AI를 써도 별도의 AI 서비스를 만들 수 있고, Python을 쓴다고 반드시 독립적인 서버가 필요한 것도 아니다.

## TaxDesk를 두 가지 방식으로 구현한다면?

TaxDesk의 세무 상담 기능을 기존 Spring Boot 서비스에 추가한다고 가정했다. 사용자가 세무 질문을 입력하면 관련 법령 근거를 검색하고, 필요하면 계산 기능을 호출한 뒤 근거를 포함한 답변을 만드는 구조다.

### 기존 Spring Boot에 Spring AI를 추가하는 방식

**사용자 → Spring Boot → Spring AI → LLM API·Vector DB·업무 도구 → 응답**

기존 Java 서비스의 인증, 권한, 데이터 접근, 업무 로직을 그대로 활용하면서 AI 기능을 추가할 수 있다. 예를 들어 기존 Java 서비스에 세액 계산 로직이 있다면 그대로 재사용할 수 있다. Spring AI의 Tool Calling으로 모델이 고르게 할 수도 있고, 서버가 정해진 순서로 직접 호출할 수도 있다. 실제 TaxDesk는 계산 순서를 모델에 맡기지 않으려고 뒤쪽을 택했다.

별도의 서비스 간 통신을 설계할 필요는 줄지만, AI 요청의 응답 지연이나 자원 사용이 기존 서비스에 영향을 주지 않도록 고려해야 한다.

### Python 기반 AI 서비스를 별도로 만드는 방식

**사용자 → Spring Boot → HTTP API → FastAPI → AI 라이브러리 → LLM API·Vector DB → 응답**

기존 Java 서비스는 사용자 인증과 업무 기능을 맡고, 별도의 Python 서비스가 AI 요청을 처리하는 구조다. AI 기능을 독립적으로 개발하고 배포할 수 있으며 Python 기반 AI 라이브러리를 쓰기 편하다.

반면 Java와 Python 서비스 사이의 API 계약, 인증, 타임아웃, 오류 처리, 로그 추적 등을 따로 설계해야 한다.

### Java와 Python을 함께 쓰는 방식

Java는 사용자 인증, 권한 관리, 세무 계산 같은 기존 업무 로직을, Python은 AI 추론, 검색, 모델 실험을 맡도록 역할을 나눌 수도 있다. 다만 기능이 단순한 상황에서 처음부터 서비스를 두 개 만들면 오히려 운영 부담이 늘 수 있다.

중요한 건 언어를 나누는 것 자체가 아니라 **기능의 책임과 변경 주기에 따라 시스템의 경계를 정하는 것**이다.

## 기획자는 어떤 기준으로 골라야 할까?

기술적으로 구현할 수 있느냐만으로 기술 스택을 정하기는 어렵다.

| 판단 기준 | 검토할 내용 |
|---|---|
| 기존 시스템 | 재사용할 API, DB, 업무 로직이 얼마나 많은가? |
| 팀 역량 | 개발팀이 익숙하게 개발·유지보수할 수 있는 기술은 무엇인가? |
| AI 기능 | 단순 LLM 연결인지, 모델 학습이나 복잡한 Agent 구현이 필요한지 |
| 변경 주기 | AI 기능을 기존 서비스와 독립적으로 배포해야 하는가? |
| 운영 부담 | 별도 서비스의 배포·모니터링·장애 대응이 필요한가? |
| 보안·권한 | 사용자 데이터와 도구 실행 권한을 어디에서 검증할 것인가? |

AI 기능은 외부 API 응답 시간, 검색 과정, 도구 호출 등에 영향을 받는다. 그래서 기술을 고를 때는 개발 편의성뿐 아니라 운영 중에 생길 수 있는 문제도 함께 봐야 한다. 서비스가 나뉠수록 독립적인 변경과 장애 격리가 가능해지지만, 통신과 모니터링의 복잡도도 커진다.

## Python으로 만들면 AI 성능도 더 좋을까?

Python을 쓴다고 AI 답변의 정확도가 자동으로 높아지지는 않는다. 같은 LLM 모델과 프롬프트, 검색 데이터, 도구를 쓴다면 언어보다 검색 품질과 처리 흐름의 설계가 답변 품질에 더 직접적인 영향을 준다. 응답 시간 역시 외부 LLM API 호출, 데이터 검색, 네트워크 통신 등 여러 요소에 좌우된다.

실제로 비교하려면 같은 기능을 구현하고 다음을 측정해야 한다.

- **응답 시간:** 전체 응답 시간과 단계별 처리 시간
- **개발 복잡도:** 초기 구성, 기존 시스템 연동, 기능 변경에 필요한 작업
- **운영 복잡도:** 배포, 모니터링, 장애 대응
- **AI 품질:** 같은 평가 데이터에서의 정답률과 근거 정확성
- **비용:** LLM API 사용량, 서버와 추가 인프라 비용

실제 측정 없이 특정 언어가 더 빠르거나 안정적이라고 단정할 수는 없다.

## 현재의 생각

AI 개발에서 Python이 많이 쓰이는 이유는 데이터 처리와 모델 학습·실험을 위한 생태계가 풍부하기 때문이다. 하지만 모델을 직접 개발하는 것과 기존 제품에 AI 기능을 도입하는 것은 다른 문제다. 기존 Java 서비스에 LLM API, RAG, Tool Calling 기능을 추가한다면 Spring AI도 충분히 검토할 수 있는 선택지다.

기술 스택을 고를 때는 이 세 가지를 먼저 봐야 한다고 생각했다.

1. 기존 시스템의 업무 로직과 데이터를 얼마나 재사용할 수 있는가?
2. 필요한 AI 기능과 개발팀의 기술 역량에 맞는가?
3. 독립적인 구조로 얻는 이점이 추가 운영 부담보다 큰가?

**결국 중요한 건 어떤 언어가 AI 개발에 더 우수한지가 아니라, 구현하려는 기능과 기존 시스템, 운영 환경에 어떤 기술이 맞는지를 판단하는 것이다.**

공식 문서와 아키텍처 관점에서 정리한 내용이고, 두 방식의 실제 성능을 비교한 실험 결과는 아니다.
