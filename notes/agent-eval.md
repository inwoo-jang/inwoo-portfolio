에이전트가 만든 보고서를 글자 수로만 평가했더니, 내용이 부족한 결과도 통과했다. 그래서 형식은 코드로 검사하고, 의미는 LLM Judge(AI 모델을 이용한 평가)로 확인하도록 기준을 나눴다.

## 무엇이 잘못 통과하고 있었나

- 글자 수 300자 기준만 있을 때 328자짜리 일반론 보고서가 통과했다
- 화면에는 세 기업이 모두 표시됐지만, 다음 단계에는 마지막 기업의 결과만 넘어가고 있었다
- 평가 기준을 바꾸자, 오류 없이 생성된 보고서도 평가 항목 5개 중 4개를 통과하지 못했다 (근거 일치 비율 23/30 = 0.767)
- 같은 보고서를 두 번 평가했더니 통과 여부는 같았지만, 근거 일치 비율은 17/32와 17/30으로 달랐다. `temperature=0`이어도 평가는 흔들렸다
- 자료가 없는 대상은 “판단 불가”로 두는 게 맞았다. 형식을 채우려고 내용을 만들면 그게 곧 틀린 응답이다

## 그래서 역할을 나눴다

| 검사 항목 | 평가 주체 | 예시 |
|---|---|---|
| 형식·개수·범위 | 코드 | 근거 3건 이상, 인용 번호 범위, 필수 항목 존재 |
| 내용과 근거의 일치 여부 | LLM Judge | 문장의 주장을 근거가 뒷받침하는지, 한계를 구체적으로 설명했는지 |
| 통과 여부 | 코드 | Judge가 낸 문장별 판정으로 비율 계산 |

검색·분석·보고서 생성이 끝날 때마다 코드로 검사한다. 수치는 이 프로젝트에서 정한 기준이다.

| 단계 | 통과 기준 | 실패하면 |
|---|---|---|
| 검색 | 근거 3건 이상, 출처·본문 빈칸 없음 | 실패 사유를 다음 검색어에 넣고 1회 재시도 |
| 분석 | 대상마다 결과 + 인용, 또는 "판단 불가 + 이유" | 실패한 대상만 1회 재분석 |
| 보고서 | 서로 다른 인용 3개 이상, 한계 서술 있음 | 사유를 넣고 1회 재작성 |

근거 일치 비율(Faithfulness)은 이렇게 계산했다.

```text
근거로 뒷받침된 사실 주장 수 ÷ 전체 사실 주장 수 ≥ 0.8
사실 주장 0개면 미통과
```

LLM 평가 설정:

- `temperature=0`, JSON schema strict로 한 번 호출
- 보고서를 코드가 문장 단위 id로 나눠서 넘김 (평가할 문장이 누락되거나 합쳐지는 것을 방지)
- 보고서·근거 안의 문구는 지시가 아니라 평가 데이터로 취급하라고 명시

## 다음에 할 것

- 기준을 만들면, 기준을 일부러 어긴 입력을 먼저 넣어 실제로 걸러지는지 본다
- 측정값(시간, 개수)과 판정(정상/결함)은 따로 적는다
- 통과 기준 근처의 결과는 두 번 평가해 흔들리는지 확인한다
- `recursion_limit`은 재시도 횟수가 아니라 그래프 단계 상한이었다. 재시도 상한은 따로 둔다

## 자동 평가를 통과하면 사람이 검토하지 않아도 될까?

형식 검사는 코드로, 내용과 근거의 일치는 LLM Judge로 나눴다. 하지만 같은 보고서를 두 번 평가했을 때 근거 일치 비율이 달라졌다. 그렇다면 자동 평가를 통과한 결과물을 그대로 사용자에게 줘도 될까?

자동 평가 결과는 품질을 판단하는 데 도움이 되지만, 그 자체로 정확성을 보장하지는 않는다. 특히 평가 기준에 가까운 결과나 근거가 부족한 결과는 따로 검토가 필요할 수 있다. 이번에도 기준선 근처의 결과는 사람이 마지막에 봤다.

이 경험을 바탕으로 자동 검증과 사람의 검토를 이렇게 나눠 볼 수 있다고 생각했다.

| 구분 | 검증 대상 | 판단 방식 |
|---|---|---|
| 코드 검증 | 형식, 필수 항목, 개수, 수치 범위 | 정해진 규칙으로 검사 |
| LLM Judge | 내용의 충실도, 근거와 주장의 일치 | 평가 기준에 따른 모델 판정 |
| 사람의 검토 | 맥락의 적절성, 중요한 의사결정, 모호한 평가 결과 | 근거와 결과를 직접 확인하고 최종 판단 |

중요한 건 모든 결과물을 사람이 처음부터 다시 보는 게 아니라, **자동으로 검증할 수 있는 부분과 사람의 판단이 필요한 부분을 나누는 것**이라고 생각한다. 어떤 결과를 반드시 사람이 봐야 하는지는 결과물의 용도와 오류가 났을 때의 영향을 보고 정해야 한다.

## 사용자가 AI 결과물을 검토하려면 무엇이 필요할까?

자동 검증의 한계를 알게 되면서, 검증 결과를 사용자에게 어떻게 보여줄지도 중요하다는 생각이 들었다.

> [!예시] AI가 만든 기업 분석 보고서
> ‘검증 완료’라고만 표시하면 사용자가 결과를 믿을 수 있을까? 사용자가 직접 판단하려면 이런 정보가 필요할 수 있다.
>
> | 제공할 정보 | 필요한 이유 |
> |---|---|
> | 주장별 근거와 출처 | 어떤 자료를 바탕으로 썼는지 확인 |
> | 검증 결과와 미통과 항목 | 어느 부분을 다시 확인해야 하는지 파악 |
> | 판단 불가·근거 부족 표시 | AI가 확인하지 못한 부분을 구분 |
> | 수정 전후 내용 | 사용자가 무엇을 바꿨는지 확인 |
> | 최종 승인 상태 | 검토가 끝난 결과와 아닌 결과를 구분 |

이 정보를 모두 화면에 띄운다고 좋은 UX가 되는 건 아니다. 사용자가 검토해야 할 항목을 먼저 보여주고, 필요할 때 근거와 상세 평가 결과를 펼쳐 볼 수 있게 설계하는 방법을 생각해 볼 수 있다. 또 **자동 검증 통과, 사람의 검토 완료, 최종 승인**은 서로 다른 상태로 관리하는 편이 명확하다.

## 현재의 생각

AI 결과물의 품질 관리는 정확한 결과를 만드는 데서 끝나지 않는다.

- 코드로 확인할 수 있는 조건은 코드로 검증한다
- 의미와 근거의 일치는 별도 평가 기준으로 확인한다
- 자동 평가가 불확실하거나 결과의 영향이 크면 사람의 검토를 고려한다
- 사용자가 검토해야 한다면 근거와 미확인 항목을 볼 수 있어야 한다

이번 프로젝트에서는 자동 검증과 LLM Judge를 구현했고, 평가 결과가 달라지는 사례를 확인했다. 사용자 검토 화면과 승인 흐름까지 구현한 건 아니라서, 이 부분은 서비스 기획 관점에서 더 고민한 설계 방향이다.

결국 **좋은 검증 구조는 AI가 얼마나 정확한지 평가하는 것뿐 아니라, 사람이 언제 무엇을 확인해야 하는지 명확하게 만드는 것**이라고 생각한다.
