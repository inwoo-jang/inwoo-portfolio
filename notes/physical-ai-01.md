> AI Agent 개발 경험은 Physical AI에서도 재사용할 수 있다. 다만 모델이 선택한 행동을 실제 세계에서 실행하려면, 관측·좌표·시간·제어·하드웨어의 조건까지 맞아야 한다.

## 이 질문을 하게 된 계기

AI Agent를 공부하다 보면 이런 생각이 든다.

“에이전트가 검색하고 API를 호출할 수 있다면, 로봇의 이동·집기 API도 호출하면 되는 것 아닐까?”

**이미 동작하는 로봇 기능을 선택하고 조합하는 계층에서는 가능한 접근이다.** Google의 SayCan 연구는 언어 모델이 판단한 작업 관련성과, 로봇의 현재 상태에서 해당 기능을 수행할 가능성을 함께 고려해 실행할 스킬을 선택했다. 언어 모델이 모든 관절 움직임을 직접 생성한 구조는 아니었다.

그렇다면 어려움은 어디에 남아 있을까?

예를 들어 “작업대의 컵을 쟁반에 놓아줘”라는 요청을 생각해 보자. `pick_and_place()`라는 함수를 호출할 수 있어도, 그 함수 아래에서는 컵의 위치와 자세를 파악하고, 접근 가능한 경로를 찾고, 실제로 잡았는지 확인하고, 로봇의 현재 상태에 맞게 움직여야 한다. 동작 계획 도구인 MoveIt도 목표 위치뿐 아니라 충돌, 관절 제약, 속도·가속도 조건을 다룬다.

따라서 API 연결은 잘못된 접근이 아니다. **API 아래에 어떤 능력이 구현되어 있다고 가정하는지**가 중요하다.

이 글에서는 그 경계를 중심으로 AI Agent와 Physical AI의 개념, 모델, 아키텍처, 기술스택을 비교한다.

## AI Agent와 Physical AI는 서로 대체하는 단계가 아니다

이 글에서 AI Agent는 주로 **목표와 상황에 따라 다음 단계와 도구 사용을 선택하는 LLM 기반 시스템**을 뜻한다. Anthropic은 미리 정한 코드 경로를 따르는 워크플로우와, 모델이 실행 과정과 도구 사용을 동적으로 결정하는 에이전트를 구분한다.

반면 Physical AI는 **물리적 환경을 인식하고, 그 안에서 행동하거나 물리적 상호작용을 지원하는 AI**를 포괄하는 용어로 사용된다. NVIDIA는 로봇뿐 아니라 자율주행차와 스마트 공간을 포함하고, NAVER LABS는 로봇 AI·클라우드 로보틱스·하드웨어·사람과의 상호작용·운영 플랫폼을 함께 다룬다.

이 정의를 바탕으로 보면 두 용어는 분류 기준부터 다르다.

| 구분 | AI Agent | Physical AI |
|---|---|---|
| 중심 질문 | 목표를 위해 다음에 무엇을 할 것인가? | 물리 세계를 어떻게 인식하고 상호작용할 것인가? |
| 강조하는 축 | 의사결정과 실행의 구성 방식 | 작동하는 환경과 행동의 대상 |
| 이 글의 대표 예 | 문서 검색·계산·업무 API를 조합하는 에이전트 | 물체를 옮기거나 실제 공간을 이동하는 로봇 시스템 |
| 두 개념의 관계 | 물리적 스킬을 선택하는 에이전트도 가능 | 에이전트 구조를 포함할 수도, 정해진 제어 구조를 사용할 수도 있음 |

표는 위 자료를 바탕으로 정리한 개념 비교다. 실제로 Gemini Robotics 1.5는 고수준 추론·도구 사용·계획 모델과 로봇 행동 모델을 연결한 agentic system을 소개했다.

즉, **Physical AI가 반드시 AI Agent의 다음 세대인 것은 아니다. 에이전트 구조가 물리적 환경으로 확장될 수 있는 것이다.**

또한 이 글에서는 범위를 로봇, 그중에서도 물체 조작과 이동 시스템에 좁힌다. 모든 산업 자동화나 모든 로봇에 LLM이 필요한 것은 아니다.

## 최근 사례에서 읽을 수 있는 변화

### 고수준 판단과 실제 행동이 연결되고 있다

Google DeepMind가 2025년 9월 공개한 Gemini Robotics 1.5 사례에서는 Robotics-ER 1.5가 상황을 해석하고 외부 도구를 사용하며 작업을 계획한다. Robotics 1.5는 시각 정보와 지시를 로봇 행동으로 연결한다. 소개된 분리수거 사례도 지역의 분리수거 규칙을 찾는 단계와 물체를 실제로 옮기는 단계를 결합한다.

여기서 주목할 것은 “LLM이 모터를 모두 직접 제어한다”는 이야기가 아니다. **업무를 이해하는 능력과 행동을 수행하는 능력을 시스템 안에서 연결한다는 것**이다.

### 로봇 모델도 API로 제공되기 시작했다

Physical Intelligence는 2026년 10월 13일 Pi API 베타를 발표했다. 사용자가 데이터를 올리고, 제공사가 관리하는 인프라에서 모델을 미세조정한 뒤, 호스팅된 추론을 활용하는 방식이다.

하지만 같은 글은 시연 수집 → 모델 학습 → 실제 로봇 테스트 → 실패에 따른 추가 데이터 수집이라는 반복 과정과, 일부 현장의 네트워크 연결 문제도 설명한다.

내가 이 사례에서 읽은 변화는 **모델을 사용하는 진입장벽은 낮아져도, 실제 로봇과 현장을 연결하는 개발 책임까지 사라지는 것은 아니라는 점**이다.

### 국내에서도 모델 바깥의 플랫폼이 중요하다

NAVER LABS의 2026년 4월 기술 소개는 공간 이해 AI뿐 아니라, 여러 로봇을 제어·관리하는 ARC brain과 로봇용 웹 API를 제공하는 ARC mind를 함께 설명한다.

이 사례를 서비스 개발 관점에서 보면 로봇 제품에는 모델 외에도 작업 배정, 상태 관리, 시설물 연동, 사용자 인터페이스가 필요하다는 사실이 드러난다. 로봇 분야의 소프트웨어가 전부 모델 학습이나 모터 제어인 것은 아니다.

## 가장 큰 변화는 출력 형식보다 ‘상태와 시간’에 있다

텍스트 대신 숫자를 출력하면 Physical AI가 되는 것처럼 생각하기 쉽다. 하지만 개발 구조를 바꾸는 문제는 **그 숫자가 어떤 상태에서, 언제, 무엇을 의미하는지**에 있다.

### 세계의 상태를 먼저 추정해야 한다

데이터베이스의 주문 상태를 읽는 일과 카메라로 컵의 위치를 알아내는 일은 같지 않다. 후자에서는 관측으로부터 실제 상태를 추정해야 한다.

“카메라 기준 오른쪽”과 “로봇 기준 오른쪽”도 다르다. 카메라, 로봇 본체, 그리퍼가 서로 다른 좌표계를 사용한다면 이를 변환해야 한다. ROS의 `tf2`는 이런 좌표계 관계를 다루는 도구다.

예를 들어 모델이 컵의 위치를 잘 찾았어도, 그 위치를 잘못된 좌표계로 해석하면 다른 곳으로 움직일 수 있다. 이때 필요한 수정은 프롬프트가 아니라 좌표 변환이나 센서 보정일 수 있다.

### 모델이 추론하는 동안에도 환경은 변한다

Physical Intelligence의 「Real-Time Action Chunking with Large Models」는 행동을 여러 단계씩 묶어 생성하는 VLA에서 추론 지연과 동작의 연속성을 다룬다. 이전 동작을 실행하는 동안 다음 동작을 계산하더라도, 두 동작 묶음이 매끄럽게 연결되지 않으면 문제가 생긴다.

따라서 로봇에서는 “답변이 조금 늦다”가 아니라 **이미 바뀐 상태에 대한 명령을 뒤늦게 실행한다**는 문제가 발생할 수 있다.

고수준 작업 계획, 행동 모델의 추론, 하위 제어를 모두 같은 주기로 실행한다고 가정해서도 안 된다. `ros2_control`은 하드웨어 상태 읽기 → 제어기 갱신 → 명령 쓰기를 반복하며, 제어 루프의 시간 흔들림인 jitter를 줄이는 문제를 별도로 다룬다.

### 명령을 보냈다는 사실과 작업을 끝냈다는 사실은 다르다

ROS 2의 Action은 오래 걸리는 동작을 위해 목표, 진행 피드백, 최종 결과, 취소 요청을 구분한다. 이동 목표를 전달했다고 해서 이미 목적지에 도착한 것은 아니기 때문이다.

여기서 작업의 취소 요청과 별도의 안전 정지 기능을 같은 것으로 간주하지 않는다. 안전 계층의 설계는 3편에서 다룬다.

이 구조를 참고한다면 업무 화면에서도 `요청 접수`, `실행 중`, `결과 확인`, `중단·실패`를 구분하는 편이 적절하다. 이는 특정 제품의 표준 상태값이 아니라 이 글에서 제안하는 설계 방식이다.

디지털 서비스도 비동기 작업, 부분 실패, 되돌릴 수 없는 행동을 다룬다. 따라서 “디지털은 항상 롤백 가능하고 로봇만 위험하다”는 구분은 정확하지 않다. 이 글에서 강조하는 차이는 **물리적 실행에서는 실제 상태의 관측과 실행 타이밍이 동작 결과에 직접 연결된다는 것**이다.

## LLM·VLM·VLA·World Model은 같은 층의 기술이 아니다

명칭을 한 줄에 놓으면 모두 경쟁 모델처럼 보이지만, 실제로는 역할과 분류 기준이 다르다.

| 개념 | 중심 역할 | 컵을 옮기는 예에서의 역할 |
|---|---|---|
| LLM | 언어 이해·추론·작업 분해 | 요청을 해석하고 필요한 작업을 정리한다. |
| VLM | 영상과 언어를 함께 처리 | 영상에서 어떤 물체를 뜻하는지 해석한다. |
| VLA | 시각·언어와, 모델에 따라 로봇 상태를 행동에 연결 | 관측과 지시를 받아 로봇 동작을 출력한다. |
| World Model | 환경의 상태와 변화, 또는 행동에 따른 결과를 모델링 | 특정 움직임 이후 물체와 주변이 어떻게 변할지 예측한다. |
| Spatial Intelligence | 위치·방향·거리·공간 관계를 이해하는 능력 | 컵과 쟁반의 관계, 접근 가능한 방향을 판단한다. |
| Controller | 목표 동작을 실제 장치 동작으로 구현 | 현재 관절 상태와 목표를 바탕으로 하드웨어를 제어한다. |

위 표는 Gemini Robotics, Cosmos, 로봇 제어 문서의 역할을 비교해 재구성한 것이다. 특히 공간 지능은 특정 모델 아키텍처 하나를 뜻하지 않으며, 제어기는 LLM 계열 모델과 같은 분류가 아니다.

### VLA의 Action은 무엇일까?

VLA가 반드시 “컵을 잡아”라는 문장이나 모터 토크를 출력하는 것은 아니다. 로봇 행동은 관절 목표값, 그리퍼 끝의 위치·방향, 현재 상태 기준의 변화량 등으로 표현할 수 있다. LeRobot 문서도 관절 공간과 말단장치 공간, 절대값과 상대값을 구분한다.

OpenVLA는 행동을 토큰으로 예측한 뒤 연속값 행동으로 복원한다. 반면 GR00T N1은 VLM과 연속 행동을 생성하는 Diffusion Transformer를 결합한 구조를 소개했다.

중요한 것은 출력 형식 자체가 아니라 **모델의 행동 표현과 로봇이 받아들이는 명령의 의미가 일치하는가**다.

### 모든 모델을 하나씩 붙여야 할까?

그렇지 않다. 위 표는 역할을 구분한 것이지 필수 설치 목록이 아니다.

이미 구현된 로봇 스킬을 선택하는 구조도 있고, 관측에서 행동으로 연결되는 부분을 VLA로 학습하는 구조도 있다. 하나의 모델이 여러 역할을 통합할 수도 있다. NVIDIA는 2026년 5월 Cosmos 3에서 시각 추론·생성·행동 예측을 결합하는 방향을 발표했다.

따라서 “World Model이 들어갔는가?”보다 **이 시스템에서 예측이 어떤 의사결정에 쓰이며, 어떤 역할은 다른 구성요소가 담당하는가?**를 먼저 확인해야 한다.

## 구현 구조는 크게 두 경로로 이해할 수 있다

다음은 공개 연구와 개발 문서를 바탕으로 단순화한 설명용 구조다. 모든 제품이 이 순서를 그대로 따르는 것은 아니다.

### 경로 A. AI가 이미 구현된 로봇 스킬을 선택한다

```text
사용자 요청
    ↓
LLM/VLM: 요청 해석·작업 분해
    ↓
스킬 선택: 현재 상태에서 실행 가능한가?
    ↓
로봇 스킬: 이동하기 / 집기 / 놓기
    ↓
필요한 동작 계획·제어·하드웨어 실행
    ↓
실행 결과와 센서 관측을 상위 판단에 반영
```

SayCan은 이 경로를 이해하기 좋은 연구다. 언어적으로 유용해 보이는 행동만 고르지 않고, 현재 환경에서 수행할 수 있는지도 고려했다.

이 경로에서는 기존 Agent 개발 경험을 활용해 작업 순서, 스킬 인터페이스, 상태 전환, 예외 처리를 설계할 수 있다. 단, **스킬 자체를 만드는 문제와 스킬을 선택하는 문제는 구분해야 한다.**

### 경로 B. 관측과 지시에서 행동을 생성하도록 학습한다

```text
카메라 영상 + 지시 + 필요한 로봇 상태
    ↓
VLA / 학습된 행동 정책
    ↓
행동값 또는 여러 시점의 행동 묶음
    ↓
명령 형식 변환·실행 계층·하위 제어
    ↓
로봇 동작 → 새로운 관측 → 다음 추론
```

OpenVLA, openpi, LeRobot은 이런 학습·추론 경로를 살펴볼 수 있는 공개 자료다. 특히 openpi는 사전학습 모델을 제공하면서도 새로운 로봇 플랫폼에 적응시키는 모든 시도가 성공하리라고 기대하지는 않는다고 명시한다.

관측부터 행동 출력까지를 통합 학습한다는 의미의 *end-to-end*도 하위 실행 계층이 필요 없다는 뜻은 아니다. 출력한 행동을 로봇의 명령 표현으로 맞추고 실제 장치에서 실행하는 연결은 여전히 필요하다.

여기서 행동 정책, 즉 *policy*는 관측에서 행동을 결정하는 모델이나 규칙을 뜻한다. 승인 정책·보안 정책에서 말하는 조직의 규정과는 의미가 다르다.

두 경로는 경쟁 관계로만 볼 필요가 없다. 상위 에이전트가 업무를 분해하고, 일부 스킬은 기존 프로그램이, 다른 스킬은 학습된 모델이 수행하도록 구성할 수 있다. Gemini Robotics의 고수준 추론과 행동 모델 결합도 이런 역할 분담을 보여주는 사례다.

### 더 큰 VLA를 쓰는 것이 항상 정답은 아니다

OpenVLA의 2024년 비교 실험에서는 좁고 정밀한 일부 작업에서 Diffusion Policy가 강점을 보였고, 다양한 언어 지시와 물체를 연결하는 작업에서는 OpenVLA가 강점을 보였다. 특정 실험의 결과이므로 모든 모델에 일반화할 수는 없지만, 기술 선택의 기준이 모델 크기 하나로 정해지지 않는다는 점은 참고할 만하다.

따라서 작업의 변화 범위와 필요한 정밀도를 먼저 정의하고, 기존 스킬·작업 특화 정책·범용 VLA 중 어느 접근을 검토할지 정해야 한다.

## 기술스택은 ‘교체’보다 ‘계층 추가’에 가깝다

기존 서버와 AI 도구를 모두 버리고 ROS 2로 옮기는 문제가 아니다. 각 도구가 담당하는 문제부터 나누어 보는 편이 낫다.

| 맡기는 문제 | 대표 기술·도구 | 구분해야 할 역할 |
|---|---|---|
| 사용자 요청·업무 상태·제품 기능 | 기존 API 서버, DB, 작업 오케스트레이션 | 제품과 업무를 관리한다. 아래의 로봇 실행 계층과 연결할 수 있다. |
| 행동 모델 학습·추론 | Python, PyTorch, LeRobot, openpi | 로봇 데이터와 학습된 행동 정책을 다룬다. |
| 센서·상태·장기 동작 통신 | ROS 2 | Topic·Service·Action 등으로 노드 사이의 데이터를 주고받는다. |
| 로봇 팔 동작 계획 | MoveIt 2 | 목표 자세, 충돌, 관절 제약, 궤적을 다룬다. |
| 하드웨어 제어 연결 | ros2_control 또는 장치의 제어 인터페이스 | 상태를 읽고 제어기를 갱신하며 명령을 하드웨어로 전달한다. |
| 가상 환경·센서·로봇 재현 | Isaac Sim | 로봇 시뮬레이션, 테스트, 합성 데이터 생성을 지원한다. |
| 로봇 학습 환경과 훈련 | Isaac Lab | 강화학습·모방학습 등 행동 정책의 훈련 흐름을 지원한다. |

대표 도구를 정리한 것이며, 모두 함께 써야 한다는 뜻은 아니다. 예를 들어 LeRobot의 Python 기반 하드웨어 인터페이스로 실습을 시작할 수도 있다. 특정 제조사의 SDK나 다른 실행 구조를 사용하는 프로젝트도 고려해야 한다.

### ROS 2는 Agent 프레임워크의 대체재가 아니다

에이전트가 “다음에는 컵을 집자”고 결정하는 일과, 카메라·관절·작업 진행 상태를 전달하는 일은 다른 문제다.

ROS 2는 연속적인 센서 데이터에 Topic, 짧은 요청·응답에 Service, 진행 피드백이 필요한 긴 작업에 Action을 구분한다. 따라서 “로봇 API를 붙인다”는 말을 실제로 구현하려면 어떤 통신과 작업 수명주기가 필요한지 결정해야 한다.

### Isaac Sim과 Isaac Lab도 같은 도구가 아니다

Isaac Sim은 환경과 센서, 로봇을 시뮬레이션하는 쪽이고, Isaac Lab은 로봇 정책을 훈련하는 프레임워크다. 함께 활용할 수 있지만 역할이 다르며, 구체적인 백엔드·버전 호환성은 선택한 릴리스 문서를 확인해야 한다.

### 클라우드와 로컬은 역할별로 나누어야 한다

Pi API처럼 호스팅된 모델 추론을 이용하는 사례가 있으므로 “로봇 AI는 전부 기기 안에서 실행해야 한다”고 단정할 수는 없다. 반대로 네트워크 기반 추론을 사용한다고 로컬 실행·제어까지 사라지는 것도 아니다.

설계한다면 작업 계획, 정책 추론, 하위 제어를 나누고 각 계층의 지연 허용치와 연결 장애 시 행동을 따로 정해야 한다. 어떤 동작은 지연을 허용할 수 있지만, 어떤 동작은 현재 상태와 맞지 않는 늦은 명령을 받아서는 안 되기 때문이다.

## 데이터도 ‘질문–답변’에서 ‘관측–행동’으로 확장된다

LeRobot은 카메라 영상과 상태·행동을 동기화한 데이터 형식을 제공한다. 개발 흐름도 사람이 조작하고, 시연을 기록하고, 정책을 학습한 뒤 배포하는 과정으로 설명한다.

이처럼 로봇 학습이 반드시 강화학습을 뜻하는 것은 아니다. 시연을 따라 하도록 학습하는 모방학습도 중요한 경로다.

로봇의 학습 데이터를 이해하려면 “정답 행동”만 보는 것으로는 부족하다. 어떤 장면에서, 어떤 상태로, 어떤 동작을 했는지가 연결되어야 한다.

다음은 실제 표준 스키마가 아니라 데이터를 읽을 때 확인할 항목을 정리한 예시다.

| 확인할 정보 | 필요한 이유 |
|---|---|
| 영상·로봇 상태·시각 정보 | 행동을 결정할 당시의 상황을 재구성한다. |
| 행동의 표현·단위·관절 순서 | 숫자의 의미를 학습과 실행에서 일치시킨다. |
| 로봇 구성·카메라 배치·보정 정보 | 다른 장치로 옮길 때 무엇이 달라졌는지 확인한다. |
| 작업 지시·결과·개입 기록 | 어떤 작업을 시도했고 어디서 도움이 필요했는지 구분한다. |

LeRobot의 행동 표현 문서는 관절 공간과 말단장치 공간의 변환뿐 아니라, 상대·절대 행동 표현과 정규화 순서까지 다룬다. **같은 숫자 배열이라도 해석 방식이 다르면 다른 동작이 될 수 있다.**

사람의 동영상을 많이 보는 것만으로 이 문제가 모두 해결되는 것도 아니다. GR00T N1의 기술 설명은 사람 영상이 의미와 움직임에 대한 정보를 제공하지만, 로봇의 모터 제어 신호를 직접 제공하지는 않는다고 구분한다.

따라서 데이터 엔지니어링의 중요성은 줄어들지 않는다. 다루는 데이터가 문서와 테이블에서, 시간에 맞춰 연결된 영상·센서·행동으로 넓어진다.

## AI 개발자가 새로 배워야 하는 것은 무엇일까?

모든 개발자가 모터를 설계하거나 제어 이론을 같은 깊이로 공부할 필요는 없다. 필요한 깊이는 맡는 계층에 따라 달라진다.

다음은 확인한 기술 구조를 바탕으로 정리한 역량 지도이며, 채용시장 통계나 필수 자격 목록은 아니다.

| 기존 경험 | 연결하기 좋은 영역 | 새로 이해해야 할 부분 |
|---|---|---|
| LLM·Agent·백엔드 | 작업 계획, 로봇 스킬 호출, 운영 서비스 | 비동기 실행 상태, 센서 관측의 최신성, 좌표계 기초 |
| ML·컴퓨터 비전 | 인식, VLA, 로봇 학습 | 행동 표현, 로봇 시연 데이터, 운동학, 학습 후 장치 적응 |
| 데이터·MLOps | 학습 파이프라인, 장치별 배포, 기록 재현 | 멀티모달 시간 정렬, 로봇·보정 구성의 버전 관리 |
| 제어·시스템 개발 | 동작 실행, 드라이버, 실시간 제어 | 동역학, 제어 주기, 하드웨어 통신과 자원 제약 |
| 서비스 기획·운영 | 업무 배정, 상태 화면, 예외 처리 | 실제 완료의 조건, 물리적 수행 한계, 현장 인계 방식 |

이 중 공통으로 먼저 익힐 개념을 고르면 **좌표계, 상태 추정, 행동 표현, 실행 지연, 관측 피드백**이다. 하드웨어를 직접 만들지 않더라도 그 조건을 인터페이스 수준에서는 이해해야 한다.

특히 `관절 각도`와 `그리퍼의 위치·방향`은 같은 데이터가 아니다. 관절 상태에서 그리퍼의 위치를 구하는 순기구학과, 원하는 그리퍼 자세에 맞는 관절 구성을 찾는 역기구학을 구분하면 모델 출력과 로봇 명령의 관계를 이해하기 쉬워진다.

### 학습을 시작한다면 모델 학습보다 인터페이스부터

지금 시작한다면 모델을 학습시키기 전에 로봇과 주고받는 인터페이스부터 익혀야 한다.

1. 공개 로봇 데이터에서 영상·상태·행동이 어떻게 함께 기록되는지 본다
2. 가상 로봇으로 목표 전달 → 진행 피드백 → 취소 → 결과 확인을 직접 구현해 본다
3. 상위 Agent가 이미 구현된 스킬을 고르게 만든다
4. 기존 스킬로 안 되는 동작이 생겼을 때 비로소 학습 모델을 검토한다

Agent와 서비스를 만들어 본 입장에서는 이 순서가 모델 문제와 실행 시스템 문제를 섞지 않고 배우기 좋아 보인다. 다만 시뮬레이션에서 돌아간다고 실제 로봇에서도 돌아가는 건 아니다. 그 차이는 다음 편에서 다룬다.

## 기획할 때는 기능 이름보다 실행 조건을 먼저 적는다

“로봇이 컵을 옮긴다”는 기능명만으로는 개발 범위가 정해지지 않는다.

이 기능을 기획한다면 다음처럼 실행 조건부터 정리해야 한다.

| 구분 | 먼저 확인할 내용 |
|---|---|
| 대상과 환경 | 어떤 컵·쟁반·작업대까지 지원하는가? |
| 시작 조건 | 대상이 관측되고, 필요한 로봇 상태가 유효한가? |
| 실행 상태 | 접수·실행·중단·실패를 어떻게 구분하는가? |
| 완료 조건 | 명령이 끝났는가, 컵이 실제로 쟁반에 놓였는가? |
| 예외 처리 | 대상이 사라지거나 관측이 오래되면 누가 어떻게 대응하는가? |
| 변경 관리 | 모델·하드웨어·카메라 구성이 바뀌면 무엇을 재확인하는가? |

여기서 기획자의 역할은 제어 알고리즘을 대신 설계하는 것이 아니다. **사용자의 요청이 어떤 조건에서 실행 가능하며, 시스템이 무엇을 완료로 인정할지 합의하는 것**이다.

모델의 출력, 실행기의 상태, 현장 담당자의 확인이 서로 다른 의미를 사용하면 좋은 모델을 연결해도 서비스가 완성되지 않는다.

## 현재의 생각

리서치를 통해 내린 결론은 “AI 개발과 로봇 개발은 완전히 다른 분야”도, “이제 API만 붙이면 누구나 로봇을 만들 수 있다”도 아니다.

**AI 개발 경험은 상위 계획, 모델 활용, 데이터 처리, 서비스 운영에 이어질 수 있다. 다만 행동이 물리 세계로 연결되는 지점부터는 관측·좌표·시간·제어·장치 구성을 함께 이해해야 한다.**

그래서 기술스택을 선택할 때의 첫 질문도 달라진다.

“어떤 LLM을 사용할까?”보다 먼저, **“현재 로봇이 이미 수행할 수 있는 행동은 무엇이며, 새로 개발해야 할 능력은 어느 계층에 있는가?”**를 확인해야 한다.
