AI로 코드를 빠르게 만들 수 있다면, 이미 쌓인 코드를 정리하는 데도 쓸 수 있을까? OpenAI의 Core Experimentation 팀은 Codex를 활용해 미사용 코드와 종료된 실험을 찾아내고, CI에서 오래 걸리는 작업을 개선했다.

사례를 읽으면서 가장 궁금했던 건 AI가 오래된 코드를 얼마나 많이 찾아냈느냐보다 **그 코드가 왜 아직 남아 있는지 어떻게 확인했느냐**였다.

## 호출 기록이 없는 코드는 지워도 될까?

OpenAI의 Codex는 과거 PR, Slack 대화, 내부 프로젝트 기록을 살펴보고 운영 프로파일링 데이터에서 해당 코드가 실제로 실행됐는지 확인했다. 코드 검색으로 참조를 찾고, 변경 이력으로 도입 이유를 파악하고, 운영 데이터로 사용 흔적을 확인한 것이다.

여기서 운영 데이터를 볼 때는 **어떤 기간과 상황을 관측했는지**가 중요하다. 최근 몇 주간 실행되지 않은 코드라도 월말 배치나 장애 대응 과정에서만 쓰일 수 있다. 코드 검색에서 참조를 못 찾더라도 프레임워크 설정이나 리플렉션을 통해 호출될 수 있다.

내가 AI에 이 작업을 맡긴다면 후보마다 **어디를 확인했는지, 어떤 기간을 봤는지, 아직 확인하지 못한 호출 경로가 있는지**를 적게 하겠다. 그중 근거가 충분한 후보부터 작은 PR로 올리고, 해당 기능을 아는 개발자가 유지해야 할 동작을 확인할 수 있게 하겠다.

## 끝난 실험의 Feature Flag는 언제 정리할까?

Feature Flag는 기능을 켜거나 끄고, 사용자나 환경에 따라 서로 다른 동작을 적용하는 데 쓰인다. 실험이 끝나거나 기능이 전체 사용자에게 출시된 뒤에도 플래그와 이전 코드 분기가 남으면, 이후 기능을 수정할 때 확인해야 할 경우의 수가 늘어난다.

정리 전에는 **환경별 설정, 최근 평가 기록, 코드 참조, 다른 플래그의 의존 여부**를 함께 확인할 수 있다. 모든 환경에서 값이 같더라도 다른 플래그의 선행 조건이거나 장애 때 기능을 끄는 용도라면 여전히 역할이 있다.

OpenAI 사례에서도 여러 기능 플래그에 연결된 테스트용 플래그가 CPU 비용을 유발했다. Codex는 관리 콘솔에서 이 플래그가 `Permanent`로 표시된 것을 확인하고 사람에게 검토를 요청했다. 팀은 검토 후 플래그를 제거했고, 주요 영향 서비스의 CPU 사용량이 **약 0.42% 줄었을 것으로 추정**했다.

플래그를 만들 때 정리 조건까지 정해두면 나중에 도입 이유를 다시 조사하는 일을 줄일 수 있다. 예를 들어 출시용 플래그를 추가하면서 **담당자, 제거 조건, 정리 티켓**을 함께 남기는 방식이다. Uber의 Piranha 사례는 정리할 플래그와 유지할 분기가 정해졌을 때 코드 변경을 자동화하는 방법을 보여준다.

## CI가 느리다면 어디서 시간이 걸리는지 먼저 본다

CI 결과가 늦게 나오는 이유는 작업이 실행을 기다리기 때문일 수도 있고, 테스트 자체가 오래 걸리기 때문일 수도 있다. GitHub Actions에서는 워크플로와 작업별 대기 시간, 실행 시간, 실패율을 확인할 수 있다. AI에 실행 이력을 분석하게 한다면, 반복해서 오래 걸리는 작업을 찾고 개선 후보마다 예상 절감 시간과 계산 근거를 붙이게 할 수 있다.

OpenAI는 약 30개의 CI 최적화 PR을 반영한 뒤 **CI 완료 시간 중앙값이 약 10분에서 4.5분으로**, **90백분위가 12.5분에서 6분으로** 줄었다고 보고했다. 이후 별도 개선에서는 누락된 모의 객체를 추가해 테스트 63개를 모두 유지하면서 해당 테스트 묶음의 실행 시간을 약 593초에서 30초로 줄였다.

내가 CI 개선 효과를 확인한다면 완료 시간의 중앙값과 90백분위를 보고, 실패율과 기존 검증 범위도 함께 확인하겠다. 평소에 빨라졌는지, 유난히 오래 기다리던 실행도 개선됐는지 각각 볼 수 있기 때문이다.

## 저렴한 모델로 어디까지 조사할 수 있을까?

OpenAI가 같은 저장소 범위에서 오래된 실험을 조사하게 했을 때, GPT-6.1 Sol Ultra는 검토를 거친 발견 131건을 API 비용 $15.12에 제시했다. GPT-6 Astra Ultra는 142건을 $109.06에 제시했다. 이 실험에서 Sol Ultra는 Astra Ultra 대비 **약 92%의 발견 건수를 약 14%의 API 비용**으로 기록했다.

두 모델의 차이는 주로 다른 플래그가 의존하는 고정값 플래그에서 나왔다. 실제로 적용한다면 저비용 모델로 후보를 넓게 찾고, 의존관계가 복잡하거나 운영 영향이 큰 후보는 추가 검토를 거치겠다. 모델을 비교할 때는 **어떤 유형의 후보를 놓쳤는지, 사람이 근거를 다시 확인하는 데 얼마나 걸렸는지**도 기록하고 싶다.

## 내가 적용한다면

종료된 실험 하나나 반복해서 느린 CI 작업 하나부터 시작하겠다. AI가 근거를 모아 작은 PR을 제안하면, PR에는 **왜 바꾸는지, 어떤 동작을 유지해야 하는지, 반영 후 무엇을 확인할지**를 남긴다.

플래그를 정리했다면 출시된 기능이 환경별로 그대로 동작하는지 확인하고, CI를 개선했다면 같은 워크플로의 완료 시간과 실패율을 비교한다. 이렇게 확인한 결과가 있어야 다음에 어떤 정리 작업에 시간을 쓸지도 결정할 수 있다.
