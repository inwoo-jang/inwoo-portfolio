> RAG는 외부 지식을 활용하는 데 유용하지만, 검색 단계를 추가한다고 답변이 반드시 정확해지는 것은 아니다. 필요한 정보의 형태와 규모, 질문의 특성에 따라 RAG보다 단순한 방식이 더 적절할 수 있다.

## 이 질문을 하게 된 계기

9월 RAG 캡스톤에서 검색한 자료를 바탕으로 AI가 보고서를 쓰는 파이프라인을 구현했다. 검색된 근거가 없으면 LLM을 호출하지 않고, 존재하지 않는 인용 ID는 코드로 지우는 규칙을 정했다. 구현하면서 검색 결과가 없거나 관련성이 낮은 문서가 검색되는 문제도 겪었다.

이후 RAG 관련 연구를 보면서 새로운 질문이 생겼다. **검색 시스템을 추가하는 것이 항상 더 좋은 선택일까?** 문서가 많지 않다면 전체 문서를 모델에 주는 편이 낫지 않을까? 실시간 데이터는 검색보다 API로 조회하는 게 정확하지 않을까? 검색된 문서가 오히려 틀린 답을 유도할 수도 있지 않을까?

RAG를 어떻게 구현하는지보다, **어떤 상황에서 RAG를 골라야 하는지**를 살펴봤다.

## RAG는 어떤 문제를 해결하는가?

RAG(Retrieval-Augmented Generation)는 외부 데이터에서 질문과 관련된 정보를 검색해 LLM 입력에 넣고 답을 만드는 방식이다. LLM의 사전학습 지식만으로 답하기 어려운 내부 문서나 최신 자료를 쓸 때 유용하다.

1. 문서를 모아 검색할 수 있는 형태로 준비한다
2. 사용자 질문과 관련된 문서를 검색한다
3. 검색된 문서를 모델에 전달한다
4. 모델이 그 정보를 바탕으로 답을 만든다

다만 RAG는 외부 지식을 쓰는 여러 방법 중 하나다.

| 상황 | 우선 검토할 방식 | 판단 이유 |
|---|---|---|
| 일반적인 설명이나 글 작성 | LLM 단독 | 별도 외부 지식이 필요 없을 수 있음 |
| 소량의 문서 요약·분석 | Long Context | 문서 전체의 맥락을 유지 |
| 대량의 내부 문서 검색 | RAG | 필요한 자료를 골라 전달 |
| 현재 주문 상태·계좌 잔액 | API / DB 조회 | 정확한 실시간 상태값 확인 |
| 정해진 산식에 따른 계산 | 코드 / 계산 엔진 | 계산의 재현성과 정확성 |
| 문서 검색과 실시간 데이터가 모두 필요한 업무 | RAG + API / DB | 정보 유형에 따라 조회 방식 분리 |

절대적인 기술 선택 기준은 아니다. 중요한 건 **답에 필요한 정보가 어디에 있고, 어떤 방식으로 가져와야 정확하게 쓸 수 있는가**다.

## RAG 대신 문서 전체를 전달하면 안 될까?

EMNLP 2024의 *Retrieval Augmented Generation or Long-Context LLMs?* 연구는 RAG와 긴 컨텍스트를 직접 쓰는 방식을 비교했다. 자원이 충분한 조건에서 Long Context가 평균적으로 더 높은 성능을 보였지만, RAG는 비용 면에서 이점이 있었다. 질문에 따라 둘 중 하나를 고르는 Self-Route 방식도 제안했다.

모든 상황에서 Long Context가 낫다는 뜻은 아니다. 모델, 문서 길이, 질문 유형, 비용 조건에 따라 결과는 달라진다. 하지만 **RAG가 반드시 필요한 건 아니라는 점**은 보여 준다.

> [!예시] 20페이지 계약서에서 불리한 조항 찾기
> 관련성 높은 문단 몇 개만 검색하면 충분할까? 불리한 조항이 문서 여러 곳에 흩어져 있거나 다른 조항과 이어져 있다면, 검색 과정에서 일부가 빠질 수 있다. 반대로 수만 건의 계약서에서 특정 조항을 찾는다면 전체 문서를 매번 모델에 줄 수 없다.

그래서 문서 전체의 크기뿐 아니라 **답에 필요한 정보가 얼마나 넓게 흩어져 있는지**도 봐야 한다.

## 검색 결과는 많을수록 좋을까?

ICLR 2025의 *Long-Context LLMs Meet RAG* 연구는 검색 문서 수를 늘리면 처음에는 성능이 오르지만, 일정 수준을 넘으면 오히려 떨어지는 현상을 관찰했다. 관련 있어 보이지만 실제로는 맞지 않는 자료(Hard Negative)가 모델의 판단을 방해하기 때문이다.

> [!예시] 세무 상담 AI가 이런 자료를 검색했다면
> - A: 현재 적용되는 세법 규정
> - B: 이전 과세기간에 적용되던 규정
> - C: 다른 사업자 유형에 적용되는 규정
> - D: 비슷한 세목이지만 적용 요건이 다른 규정
>
> 넷 모두 검색어와 관련은 있다. 하지만 적용 시점이나 사업자 유형을 구분하지 못하면, 관련 문서가 많아진 것이 오히려 답의 정확성을 떨어뜨린다.

검색 결과를 5개에서 10개로 늘리는 게 해결책이라고 단정할 수 없다. **검색 결과의 개수보다 실제 질문에 적용할 수 있는 근거인지가 중요하다.**

## 문서가 적다면 RAG가 불필요할 수도 있다

Anthropic은 2024년 *Introducing Contextual Retrieval*에서 지식 베이스가 비교적 작다면 RAG 대신 전체 자료를 프롬프트에 넣는 방식도 고려할 수 있다고 설명했다. 당시 20만 토큰 미만을 예로 들었지만, 그 시점의 모델과 프롬프트 캐싱을 고려한 제안이지 모든 서비스의 기준은 아니다.

같은 글에서는 기존 RAG가 청크를 나누면서 문맥을 잃는 문제도 다뤘다.

> [!예시] 문맥을 잃은 청크
> 검색된 문장에 “해당 분기에는 전년 대비 3% 증가했다.”라고만 적혀 있다면, 무엇이 늘었는지 알 수 없다. 문서 제목과 앞뒤 문맥이 함께 있어야 제대로 해석할 수 있다.

Anthropic은 청크에 문맥 정보를 덧붙이는 Contextual Retrieval을 제안했다. 실험에서 관련 문서 검색 실패율은 5.7%에서 2.9%로, Reranking을 결합한 조건에서는 1.9%로 낮아졌다. 다만 그 연구 환경의 결과다.

여기서 주목한 건 특정 검색 기술의 우수성보다 **RAG가 정보를 찾는 과정에서 원래 문맥을 잃을 수 있다는 점**이다. 검색 구조를 고도화하기보다 전체 문서를 그대로 주는 편이 맞는 작업도 있다.

## RAG가 오히려 독이 되는 상황

| 문제 | 생기는 위험 | 예시 |
|---|---|---|
| 잘못된 문서 검색 | 잘못된 근거로 답변 | 과거 법령을 현재 규정으로 안내 |
| 검색 누락 | 필요한 정보를 확인하지 못함 | 예외 조항 누락 |
| 문맥 손실 | 부분적으로 맞지만 전체적으로 틀림 | 조문과 적용 조건이 분리됨 |
| 데이터 최신성 | 변경 전 정보 사용 | 개정 전 규정이 인덱스에 남음 |
| 권한 관리 | 접근 범위를 벗어난 정보 노출 | 다른 고객사의 문서 검색 |
| 운영 복잡도 | 비용과 지연 시간 증가 | 단순 FAQ에도 복잡한 검색 파이프라인 적용 |

### 검색이 성공해도 답은 틀릴 수 있다

RAG에서 특히 구분해야 할 건 검색 품질과 답변 품질이다.

- **Retrieval Relevance:** 검색된 문서가 질문과 관련 있는가?
- **Faithfulness:** 답의 주장이 검색된 근거로 뒷받침되는가?
- **Answer Correctness:** 답이 실제 사실과 적용 조건에 맞는가?

셋은 서로 다르다. AI가 실제 세법 조항을 인용했더라도, 그 조항의 적용 대상이 질문한 사업자와 다르다면 답은 틀린다. 근거 문서를 찾았다는 사실만으로 정답이 보장되지는 않는다. 검색된 문서에 필요한 정보가 없다면 추측하지 않고 답을 보류하거나 추가 정보를 요청해야 할 수도 있다.

그래서 RAG를 설계할 때는 검색 정확도뿐 아니라 **검색된 근거가 답을 실제로 뒷받침하는지**까지 확인해야 한다.

## RAG 도입은 어떻게 판단해야 할까?

| 판단 순서 | 확인할 것 |
|---|---|
| 외부 지식이 필요한 문제인가? | 필요 없다면 RAG를 더할 이유가 적다. 정해진 계산이나 규칙 검증은 코드가 맞을 수 있다 |
| 필요한 데이터는 어떤 형태인가? | 구조화된 실시간 데이터는 API·DB, 소량 문서는 Long Context, 대량 문서는 RAG, 둘 다 필요하면 조합 |
| 답에 필요한 문맥은 어느 정도인가? | 문서 일부로 답할 수 있으면 RAG가 유리하고, 여러 조항의 관계나 전체 흐름이 필요하면 일부 청크 검색은 불리하다 |
| 정확성과 운영 비용을 함께 비교했는가? | 수집·전처리·임베딩·인덱스 갱신·검색·재정렬, 장애 대응과 평가 비용까지 포함한다 |

데이터가 크다는 이유만으로 RAG가 최선인 것도 아니다. 결국 **필요한 품질을 충족하면서 운영 복잡도를 감당할 수 있는 방식인지**가 중요하다.

## TaxDesk에 적용한다면?

실제 TaxDesk는 법령 요약 문서 검색(RAG)과 서버의 조회·판정·계산 코드로 이뤄져 있다. 아래 표는 기능을 넓힌다면 기능마다 어떤 방식을 먼저 볼지 생각해 본 설계 방향이고, 실제 비교 실험 결과는 아니다.

| 기능 | 우선 검토할 방식 | 판단 이유 |
|---|---|---|
| 세법 규정 질의응답 | RAG | 관련 법령과 해석 자료 검색 |
| 특정 세율 조회 | 검증된 데이터·API / 규칙 | 적용 시점과 정확한 값 확인 |
| 세액 계산 | 계산 로직 | 산식과 예외 조건의 재현성 |
| 유사 상담 사례 검색 | RAG | 관련 사례와 근거 탐색 |
| 단일 문서 요약 | Long Context | 원문 맥락 유지 |
| 세법 적용 가능성 검토 | RAG + 조건 검증 | 검색된 법령의 적용 요건 확인 |

세법 상담이라면 RAG로 관련 규정을 찾고, 정확한 수치나 계산은 검증된 데이터와 계산 로직을 쓸 수 있다. RAG로 최신 법령을 찾더라도 적용 시점, 사업자 유형, 예외 조건은 따로 확인해야 한다.

AI 서비스라고 모든 기능을 LLM과 RAG로 처리할 필요는 없다. **업무에 필요한 판단과 데이터의 성격에 따라 기술의 역할을 나누는 것**이 더 중요하다고 생각한다.

## RAG가 실제로 필요한지 어떻게 검증할까?

같은 질문으로 여러 방식을 비교하는 실험을 설계할 수 있다.

| 비교안 | 방식 | 확인할 내용 |
|---|---|---|
| A | LLM 단독 | 외부 지식 없이 답할 수 있는 범위 |
| B | Long Context | 문서 전체를 줬을 때의 답변 품질 |
| C | 기본 RAG | 검색된 상위 K개 청크 활용 |
| D | 개선 RAG | Hybrid Search, Reranking 등 적용 |

넷 모두 같은 외부 정보에 접근하는 건 아니라서 비교 목적을 분명히 해야 한다. LLM 단독은 외부 지식이 없는 기준선으로 쓰고, Long Context와 RAG는 가능한 한 같은 문서 집합과 평가 질문으로 비교한다.

| 질문 유형 | 검증 목적 |
|---|---|
| 일반 질문 | 정확한 근거 검색 |
| 예외 조건 | 단서·예외 조항 누락 여부 |
| 시간 조건 | 과거와 현재 규정 구분 |
| 다중 근거 | 여러 문서의 정보 결합 |
| 답변 불가 | 근거가 없을 때 추측하지 않는가 |

특히 **답변 불가 질문**을 넣어야 한다. ACL 2025의 *UAEval4RAG* 연구도 RAG가 답할 수 없는 질문을 제대로 처리하는지 평가해야 한다는 문제를 다뤘다. 정답이 있는 질문만 평가하면, 근거가 없을 때 모델이 얼마나 자주 틀린 답을 만드는지 알 수 없다.

| 평가 영역 | 지표 |
|---|---|
| 검색 품질 | Recall@k, Context Precision |
| 답변 품질 | Answer Correctness, Faithfulness |
| 예외 대응 | 답변 불가 질문의 적절한 보류율 |
| 응답 성능 | 평균·p95 응답 시간 |
| 비용 | 성공 요청당 비용 |
| 데이터 관리 | 문서 최신성, 버전 오류 발생률 |

모델, 평가 질문, 데이터 버전 등 비교 조건은 가능한 한 맞추고, 바꾼 설정은 기록해야 한다. 한 번의 결과로 우열을 확정하기보다 질문 유형별 성능과 반복 실행 결과를 봐야 한다. 아직 이 비교 실험은 하지 않았다.

## 현재의 생각

처음 RAG를 구현할 때는 외부 문서를 검색해 모델에 주면 더 정확한 답을 만들 수 있다고 생각했다. 하지만 캡스톤에서 검색 결과가 없거나 관련성이 낮은 자료가 검색되는 문제를 겪었고, 연구를 보면서 검색 단계 자체가 새로운 실패 원인이 될 수 있다는 걸 알게 됐다.

RAG가 필요한 상황은 분명하다. 대규모 문서에서 관련 근거를 찾거나, 모델이 학습하지 않은 내부 지식을 쓰는 경우다. 하지만 이런 상황에서는 다른 방식을 먼저 볼 수 있다.

- 문서가 적고 전체 맥락이 중요한 경우
- 정확한 실시간 상태값이 필요한 경우
- 정해진 규칙과 산식으로 계산할 수 있는 경우
- 검색 과정에서 중요한 정보가 빠지는 경우
- 품질 개선보다 운영 복잡도와 비용 증가가 더 큰 경우

RAG를 도입하는 것 자체가 목표가 되어서는 안 된다. **해결하려는 업무 문제를 먼저 정의하고, 그 문제에 필요한 정보를 가장 적절하게 주는 방식을 골라야 한다.** AI 서비스 기획자라면 RAG의 원리뿐 아니라 언제 쓰고 언제 쓰지 않을지를 판단할 수 있어야 한다고 생각한다.
