> AI 서비스의 응답 설계는 단순히 처리 속도를 높이는 문제가 아니다. 사용자가 기다려야 하는 작업인지, 기다리는 동안 다른 일을 할 수 있는지, 처리 상태를 어떻게 확인할 수 있는지를 결정하는 문제다.

## 퀴켓에서 비동기 흐름을 설계하며

퀴켓(Quicket)에서는 사용자가 퀴즈 생성을 요청한 뒤, 생성이 끝날 때까지 그 화면에 머무르지 않고 홈으로 이동할 수 있도록 설계했다. 퀴즈 생성에는 시간이 걸리지만, 그동안 사용자가 화면을 계속 보고 있어야 할 이유는 없다고 판단했기 때문이다.

이 경험을 AI 서비스로 넓히면 몇 가지 고민이 생긴다.

- 사용자가 반드시 결과를 기다려야 하는 작업인가?
- 결과를 기다리는 동안 다른 기능을 쓸 수 있어야 하는가?
- 생성 중인 내용을 실시간으로 보여주는 것이 유용한가?
- 작업이 실패하거나 사용자가 화면을 벗어나면 어떻게 처리해야 하는가?

결국 중요한 건 모든 작업을 빠르게 처리하는 것보다 **작업의 특성에 맞는 응답 방식과 사용자 경험을 설계하는 것**이라고 생각한다.

## 동기·비동기·Streaming·Queue는 무엇이 다를까?

네 가지 개념은 비슷해 보이지만 해결하는 문제가 다르다.

| 개념 | 핵심 역할 |
|---|---|
| 동기(Synchronous) | 앞선 작업의 결과를 기다린 뒤 다음 작업을 진행 |
| 비동기(Asynchronous) | 작업 완료를 기다리지 않고 다른 작업을 진행할 수 있도록 분리 |
| Streaming | 전체 결과가 완성되기 전에 생성된 내용을 순차적으로 전달 |
| Queue / Worker | 작업을 대기열에 넣고 별도 실행 주체가 처리 |

동기·비동기는 **사용자 경험 관점**과 **서버 처리 관점**을 나눠서 봐야 한다. 사용자가 화면에서 기다리는 것과 서버가 HTTP 요청을 유지한 채 응답을 기다리는 것은 반드시 같은 의미가 아니다. 서버는 작업을 비동기로 접수했더라도 프론트엔드에서는 완료될 때까지 로딩 화면을 보여줄 수 있다. 반대로 Streaming은 하나의 HTTP 연결을 유지하면서도 데이터를 점진적으로 전달할 수 있다.

### Queue와 Worker는 왜 필요할까?

> [!예시] 100페이지 분량의 문서를 AI로 분석한다면
> 1. **사용자** — 문서 분석 요청
> 2. **API 서버** — 요청 접수, 작업 ID 발급
> 3. **Queue** — 처리할 작업을 대기열에 등록
> 4. **Worker** — 작업을 가져와 문서 분석과 AI 호출 수행
> 5. **결과 저장** — 완료된 결과를 저장하고 사용자가 조회할 수 있게 제공
>
> 사용자는 분석이 끝날 때까지 화면을 열어 둘 필요가 없다.

작업이 몰렸을 때 대기열로 처리량을 조절하고, Worker를 따로 늘릴 수도 있다. 다만 Queue를 도입한다고 작업 자체가 빨라지지는 않는다. 오히려 대기 시간이 늘 수도 있고, 중복 실행·실패·재시도·Worker 장애를 관리해야 한다.

그래서 **Queue는 비동기의 필수 요소가 아니라, 작업량과 안정적인 처리를 고려해 도입하는 구조**라고 이해했다.

### Streaming은 무엇을 해결할까?

Streaming은 AI가 답변을 모두 만든 뒤 한 번에 전달하는 대신, 생성된 내용을 순차적으로 보여주는 방식이다. 일반적인 AI 챗봇처럼 사용자가 답변을 바로 읽기 시작할 수 있는 서비스에 맞다. 대표적인 구현 방식으로 SSE(Server-Sent Events)나 HTTP 스트리밍이 있다.

하지만 Streaming이 실제 작업 완료 시간을 줄여 주는 건 아니다. 사용자가 첫 결과를 더 빨리 볼 수 있다는 점에서 **체감 대기 시간**을 개선한다. 또 답변이 나오던 중 오류가 나면, 이미 출력된 내용을 남길지, 실패 상태로 표시할지, 재생성을 허용할지도 정해야 한다.

## 작업에 따라 응답 방식은 달라진다

모든 AI 서비스에 Streaming이나 Queue를 적용할 필요는 없다.

| 사용 사례 | 우선 검토할 방식 | 판단 이유 |
|---|---|---|
| 짧은 데이터 조회 | 일반 요청·응답 | 즉시 결과 확인이 중요 |
| AI 챗봇 | Streaming | 생성 중인 답변을 바로 읽을 수 있음 |
| 대량 문서 분석 | 비동기 + Queue/Worker | 오래 걸리는 작업을 분리하고 처리량 관리 |
| 이미지·영상 생성 | 비동기 + 상태 조회 | 완성된 결과물을 나중에 확인 가능 |
| 대량 알림 발송 | 비동기 + Queue/Worker | 개별 작업의 실패와 재시도 관리 |

이 방식들은 서로 배타적이지 않다. 비동기 작업으로 실행하면서 진행 상태를 Streaming으로 전달할 수도 있다.

기획 단계에서는 이런 기준으로 판단할 수 있다.

- **작업 시간:** 결과를 받기까지 얼마나 기다려야 하는가?
- **사용자 의존성:** 결과가 나와야만 다음 행동을 할 수 있는가?
- **중간 결과의 가치:** 생성 중인 내용을 보여주는 게 실제로 유용한가?
- **요청량:** 동시에 요청이 몰리면 어떻게 처리하는가?
- **실패 위험:** 중단·재시도·중복 실행이 어떤 영향을 미치는가?
- **운영 비용:** 별도 Queue·Worker를 운영할 만큼 필요한가?

결국 기술을 고르는 기준은 응답 속도가 아니라 **사용자 행동과 작업의 특성**이다.

## 기획자는 어디까지 정의해야 할까?

기획자가 Queue나 Worker의 구현 방법까지 정할 필요는 없을 수 있다. 다만 사용자에게 어떤 상태를 보여주고, 각 상태에서 어떤 행동을 허용할지는 정의해야 한다.

| 상태 | 사용자에게 보여줄 정보와 정책 |
|---|---|
| QUEUED (대기) | 요청 접수 여부, 대기 안내 |
| RUNNING (처리 중) | 진행 상태, 화면 이동 가능 여부 |
| SUCCEEDED (완료) | 결과 확인, 완료 알림 |
| FAILED (실패) | 실패 안내, 재시도 가능 여부 |
| CANCEL_REQUESTED (취소 요청) | 취소 처리 중 안내, 중복 요청 방지 |
| CANCELED (취소 완료) | 취소 결과, 재요청 가능 여부 |

상태를 정했다면 더 고려할 문제가 있다.

**진행률을 어떻게 표현할 것인가?** AI 작업은 완료 시점을 정확히 예측하기 어려운 경우가 있다. 실제 처리량을 측정할 수 없다면 임의로 ‘70% 완료’를 표시하기보다 ‘문서 분석 중’, ‘답변 생성 중’처럼 확인 가능한 단계 중심으로 안내하는 게 적절할 수 있다.

**화면 이탈과 작업 취소를 구분해야 한다.** 사용자가 페이지를 닫거나 다른 화면으로 이동했다고 서버의 AI 작업까지 자동으로 멈추는 건 아니다. 화면을 벗어나도 계속 실행할 작업인지, 취소를 요청하면 실제 작업까지 멈출 것인지 정책이 필요하다.

**실패와 재시도의 범위를 정해야 한다.** AI 호출을 다시 실행하면 비용이 또 든다. 외부 시스템에 데이터를 저장하거나 수정하는 작업이라면 중복 실행으로 부작용이 생길 수도 있다. 자동 재시도 여부, 최대 시도 횟수, 중복 요청 처리 기준을 개발팀과 함께 검토해야 한다. 같은 요청이 반복돼도 의도하지 않은 중복 결과나 부작용이 생기지 않게 하는 **멱등성(Idempotency)** 도 중요한 고려사항이다.

## 현재의 판단

AI 서비스에서 응답 시간이 길다는 이유만으로 비동기나 Queue를 도입할 필요는 없다고 생각한다.

사용자가 생성 중인 결과를 읽을 수 있다면 Streaming이 맞을 수 있고, 완료까지 화면을 유지할 필요가 없다면 비동기 흐름이 나을 수 있다. 요청량이 많거나 안정적인 재처리가 중요하다면 Queue와 Worker를 검토할 수 있다.

다만 어떤 구조를 고르든 사용자는 자신의 요청이 접수됐는지, 지금 어떤 상태인지, 실패했을 때 무엇을 할 수 있는지 알아야 한다.

**기획자의 역할은 특정 기술을 먼저 고르는 것이 아니라, 사용자에게 필요한 경험과 서비스의 처리 조건을 정의하고 그에 맞는 기술 구조를 개발팀과 함께 판단하는 것**이라고 생각한다.
