> 파라미터가 많고 추론 능력이 높은 모델이 반드시 서비스에 가장 적합한 것은 아니다. 중요한 것은 모델의 절대적인 성능보다, 필요한 품질을 어느 정도의 비용과 시간으로 달성할 수 있는가이다.

## 문제 제기: 가장 성능 좋은 모델을 쓰면 되는 것 아닐까?

AI 모델을 고를 때 처음 떠오르는 기준은 성능이다. 파라미터가 많은 모델이 더 똑똑하지 않을까? 추론을 오래 할수록 정확한 답을 만들지 않을까? 그렇다면 가장 성능이 좋은 모델을 쓰면 되는 것 아닐까?

어느 정도는 맞다. 복잡한 추론이나 어려운 문제에서는 고성능 모델이 유리할 수 있다. 하지만 모든 서비스가 같은 수준의 추론 능력을 필요로 하지는 않는다. 단순한 정보 추출에도 가장 큰 모델을 써야 할까? 성능 차이가 크지 않은데 응답 시간이 길고 비용이 몇 배 높다면 여전히 좋은 선택일까?

AI 서비스를 운영한다면 정확도뿐 아니라 응답 시간, 호출 비용, 실패 후 재시도, 사람의 검토 비용까지 봐야 한다. 결국 궁금한 건 **가장 좋은 모델이 무엇인가보다, 우리 서비스에 맞는 모델을 어떤 기준으로 고를 것인가**다.

모델 성능이 높아도 실제 서비스에는 다른 제약이 있다.

> [!예시] 세 모델을 비교한다면 (가상의 수치)
> | 모델 | 업무 성공률 | 요청당 비용 |
> |---|---:|---:|
> | A. 경량 모델 | 85% | 10원 |
> | B. 중간 모델 | 95% | 25원 |
> | C. 고성능 모델 | 98% | 80원 |
>
> 성공률만 보면 C가 가장 좋아 보인다. 하지만 성공률이 95%에서 98%로 3%p 오르는 동안 요청당 비용은 25원에서 80원으로 늘어난다.

이 차이는 감수할 가치가 있을까? 업무에 따라 답이 다르다. 오류의 영향이 작은 단순 분류라면 B로 충분할 수 있다. 반면 잘못된 결과가 큰 금전 손실이나 안전 문제로 이어진다면 C의 추가 비용이 정당화될 수 있다.

중요한 건 **성능 향상의 크기와, 그 향상이 만드는 업무적 가치를 함께 평가하는 것**이다.

## 파라미터 수: 큰 모델이 항상 좋은 것은 아닌 이유

파라미터(Parameter)는 모델이 학습하는 가중치 같은 수치 요소다. 모델 규모를 키우면 더 복잡한 패턴을 배울 수 있는 능력이 커질 수 있다. 하지만 파라미터 수가 많다는 사실만으로 실제 성능이 높다고 판단할 수는 없다.

### Chinchilla — 모델 크기보다 학습 자원 배분도 중요하다

DeepMind의 *Training Compute-Optimal Large Language Models*(2022)는 모델 크기와 학습 데이터량의 관계를 분석했다. 연구진은 700억 파라미터의 Chinchilla를 학습해 2,800억 파라미터의 Gopher와 비교했다. Chinchilla는 파라미터 수가 약 4분의 1이었지만, 연구에서 평가한 대부분의 작업에서 Gopher보다 높은 성능을 보였다. 같은 학습 연산 예산에서 모델 크기뿐 아니라 학습 데이터량을 적절히 나누는 게 중요하다는 결과였다.

여기서 알게 된 건 **파라미터 수가 곧 모델의 성능 순위는 아니라는 점**이다. 학습 데이터의 양과 질, 모델 구조, 학습 방식에 따라 결과가 달라진다.

### 파라미터 수를 직접 비교하기 어려운 이유

최근 모델에는 Mixture of Experts(MoE) 구조도 쓰인다. MoE는 입력에 따라 여러 전문가 네트워크 중 일부만 골라 활성화하는 방식이다. 그래서 전체 파라미터 수와 실제 추론에 쓰이는 활성 파라미터 수가 다를 수 있다. 전체 파라미터가 더 많은 MoE 모델이라도 토큰 하나를 처리할 때 쓰는 계산량은 다른 구조의 모델보다 적을 수 있다.

다만 실제 처리 속도와 비용은 메모리 사용량, 하드웨어, 배치 처리, 구현 방식에도 영향을 받는다. 결국 파라미터 수만 보고 정확도, 속도, 비용을 판단해서는 안 된다.

## 추론 능력: 추론을 늘리면 항상 정확해지는가?

추론 모델(Reasoning Model)은 문제를 풀기 위해 추가 추론 과정을 거칠 수 있다. 복잡한 수학 문제, 다단계 의사결정, 코드 분석에서는 이런 추론이 성능 향상에 도움이 될 수 있다. 하지만 추론을 오래 한다고 모든 작업에서 결과가 좋아지지는 않는다.

NeurIPS 2025의 *Does Thinking More Always Help?* 연구는 이른바 Overthinking 문제를 다룬다. 추가 추론이 항상 성능 개선으로 이어지지 않고, 지나친 추론이 오히려 결과를 나쁘게 만들 수 있는 현상을 분석했다. 추론을 늘리면 처음에는 성능이 오르다가 어느 시점 이후에는 개선 폭이 줄거나 성능이 떨어질 수 있다. 추론이 길어질수록 응답 시간과 생성 토큰 비용도 늘어난다.

| 작업 | 요구되는 능력 | 우선 검토할 모델 |
|---|---|---|
| 주문번호 추출 | 정해진 형식의 정보 추출 | 경량 모델 또는 코드 |
| 복잡한 세법 적용 판단 | 다수 조건·예외·근거 비교 | 고성능 추론 모델 |

주문번호 추출에는 복잡한 추론이 필요 없을 수 있다. 반면 여러 법령의 적용 요건과 예외를 비교하는 작업에서는 추가 추론이 도움이 될 수 있다. 다만 추론 모델을 쓴다고 정확한 법률 판단이 보장되지는 않는다. 필요한 근거가 정확하게 주어지고, 적용 조건을 검증하는 과정도 있어야 한다.

그래서 **추론 수준은 가능한 한 높게 두는 게 아니라, 작업의 난이도와 요구 품질에 맞춰 정해야 한다**고 생각한다.

## 비용: 토큰당 가격과 성공 업무당 총비용의 차이

모델 비용을 볼 때 가장 먼저 확인하기 쉬운 건 입력·출력 토큰 가격이다. 하지만 실제 서비스 비용은 토큰 가격만으로 정해지지 않는다.

- 입력·출력 토큰 사용량
- 추론 과정에서 생기는 추가 토큰
- 외부 검색과 도구 호출
- 실패 후 재시도
- 결과 검증과 사람의 검토
- 오류 수정과 복구
- 시스템 운영 비용

그래서 요청 한 번의 비용보다 **성공한 업무 한 건을 끝내는 데 드는 총비용**을 비교해야 한다.

```text
Cost per Successful Task
= 전체 업무 처리 비용 / 성공한 업무 건수
```

> [!예시] 앞의 가상 모델로 계산하면
> 재시도와 별도 운영 비용이 없다고 가정한 단일 실행 기준이다.
>
> | 모델 | 요청당 비용 | 성공률 | 성공 업무당 비용 |
> |---|---:|---:|---:|
> | A | 10원 | 85% | 약 11.8원 |
> | B | 25원 | 95% | 약 26.3원 |
> | C | 80원 | 98% | 약 81.6원 |

실제로 실패한 작업을 재시도하거나 사람이 검토해야 한다면 총비용은 달라진다. A가 자주 실패해서 사람이 직접 고쳐야 한다면, 호출 비용은 싸도 실제 업무 처리 비용은 높아질 수 있다. 반대로 고성능 모델이 정확도를 높여 재작업을 줄인다면 추가 모델 비용을 상쇄할 수도 있다.

그래서 **싼 모델이 항상 경제적인 것도, 비싼 모델이 항상 비효율적인 것도 아니다.**

## 모델 선택 기준: 품질·안전 기준을 먼저 정하고, 비용·지연을 최적화

품질과 안전 기준은 **넘어야 하는 선**이고, 비용과 응답 시간은 그 선을 넘은 후보 중에서 **최적화할 대상**이다.

| 판단 기준 | 확인할 질문 |
|---|---|
| 업무 난이도 | 복잡한 추론이 필요한가, 단순 분류·추출인가? |
| 품질 | 어떤 오류까지 허용할 수 있는가? |
| 응답 속도 | 사용자가 얼마나 기다릴 수 있는가? |
| 비용 | 성공한 업무 한 건에 얼마까지 쓸 수 있는가? |
| 운영 안정성 | 재시도·장애·도구 호출을 안정적으로 처리하는가? |
| 데이터·보안 | 개인정보·접근 권한·데이터 처리 요건을 충족하는가? |

무엇을 가장 중요하게 볼지는 서비스마다 다르다. 실시간 상담이라면 응답 속도가 중요하고, 복잡한 기업 분석 보고서라면 조금 느려도 정확성과 근거 충실성이 더 중요할 수 있다. 그래서 모든 지표를 같은 비중으로 비교하기보다 **반드시 충족할 조건과 최적화할 지표를 나누는 것**이 필요하다.

OpenAI의 에이전트 구축 가이드는 먼저 강력한 모델로 성능 기준선을 잡은 뒤, 일부 작업을 더 작고 빠른 모델로 대체하는 접근을 소개한다. 이를 기획 관점에서 이렇게 정리할 수 있다.

1. **업무와 성공 기준 정의:** 모델이 할 작업과 필요한 품질을 정한다
2. **성능 기준선 측정:** 고성능 모델로 그 작업에서 달성 가능한 품질을 확인한다
3. **경량 모델 비교:** 같은 평가 데이터로 더 작은 모델의 결과를 측정한다
4. **추론 수준 비교:** 추론을 늘렸을 때 실제 성능이 나아지는지 확인한다
5. **비용·속도·안전성 검증:** 품질 향상과 추가 비용 사이의 관계를 확인한다
6. **최종 선택:** 필수 품질 조건을 만족하는 후보 중 운영 효율이 높은 구성을 고른다

주의할 점은 **고성능 모델의 출력이 곧 정답은 아니라는 것**이다. 평가에는 따로 정한 정답, 검증 가능한 결과, 업무 전문가의 판단을 써야 한다.

## 모델 라우팅: 모든 업무에 같은 모델을 써야 하는가?

한 서비스 안에서도 작업마다 필요한 능력이 다르다. TaxDesk를 예로 들면 이렇게 나눠 볼 수 있다.

| 작업 | 우선 검토할 방식 | 이유 |
|---|---|---|
| 질문 유형 분류 | 경량 LLM 또는 규칙 | 비교적 단순한 분류 |
| 관련 법령 검색 | 검색 시스템 / RAG | 근거 문서 조회 |
| 복잡한 적용 요건 분석 | 고성능 추론 모델 | 여러 조건과 예외 비교 |
| 세액 계산 | 검증된 계산 로직 | 정확하고 재현 가능한 계산 |
| 답변 형식 검증 | 코드 | 형식·필수 항목 확인 |

이처럼 기능별로 서로 다른 모델과 일반 코드·검색 기술을 조합할 수 있다. Model Routing 또는 Task-based Routing 관점이다.

다만 모든 작업을 여러 모델로 나누는 게 늘 좋은 건 아니다. 라우팅 단계가 늘면 구조가 복잡해지고, 모델을 잘못 고르면 품질이 떨어진다. 여러 모델을 관리하고 평가하는 운영 부담도 생긴다. 먼저 단일 모델 구조를 기준선으로 두고, 나눴을 때 실제 이점이 있는지 확인해야 한다.

TaxDesk에 적용해 볼 수 있는 설계 방향이고, 이 구성을 실제 운영 환경에서 검증한 결과는 아니다.

## 비교 실험: 고성능·경량·추론 수준별 평가

| 비교안 | 구성 | 확인할 내용 |
|---|---|---|
| A | 경량 모델 | 낮은 비용으로 목표 품질을 달성하는가? |
| B | 중간 모델 | 성능과 비용의 균형이 좋은가? |
| C | 고성능 모델 | 추가 비용만큼 품질이 나아지는가? |
| D | 추론 수준 변경 | 추가 추론의 효과가 있는가? |
| E | 작업별 모델 라우팅 | 단일 모델보다 효율적인가? |

가능한 한 같은 질문, 입력 데이터, 출력 형식, 평가 기준을 써야 한다. 다만 모델마다 지원하는 추론 설정과 컨텍스트 길이가 달라 모든 조건을 똑같이 맞출 수는 없다. 맞추지 못한 조건은 따로 기록한다.

단순한 질문만 쓰면 고성능 모델의 장점이나 경량 모델의 한계를 확인하기 어렵다. 평가 질문을 난이도별로 나눈다.

- **단순 작업:** 분류, 정보 추출, 형식 변환
- **일반 작업:** 문서 요약, 간단한 질의응답
- **복잡한 작업:** 여러 조건을 결합하는 분석
- **예외 작업:** 불충분하거나 충돌하는 정보 처리
- **답변 불가:** 근거가 없을 때 추측하지 않는가?

한 번의 결과로 판단하지 않고, 반복 실행해서 결과가 얼마나 흔들리는지도 본다.

| 영역 | 지표 |
|---|---|
| 결과 품질 | Task Success Rate, Accuracy |
| 근거 품질 | Faithfulness, 근거 일치율 |
| 속도 | 평균·p95 응답 시간 |
| 비용 | Cost per Successful Task |
| 안정성 | 오류율, 재시도율 |
| 사용자 업무 | 검토 시간, 수정률, 재작업률 |

모든 지표가 모든 서비스에 필요한 건 아니다. 단순 정보 추출이라면 정확도, 처리 시간, 비용이 핵심이고, 근거 기반 분석이라면 근거 충실성과 잘못된 판단의 영향까지 봐야 한다.

### 실험할 때 함께 물어볼 것

**정확도가 1%p 높아지면 얼마까지 더 낼 수 있을까?** 정확도 개선의 가치는 업무마다 다르다. 단순 콘텐츠 분류와 금융·의료 같은 고위험 판단 지원을 같은 기준으로 비교할 수 없다. 오류가 날 확률뿐 아니라 오류가 났을 때의 영향도 봐야 한다.

**고성능 모델 대신 검증 구조를 강화하는 편이 나을까?** 경량 모델로 초안을 만들고 코드 검사나 평가 모델로 검증하는 방식도 있다. 하지만 검증 단계가 늘면 호출 비용과 응답 시간이 늘고, 평가 모델 자체도 틀릴 수 있다. 단일 고성능 모델과 경량 모델·검증 구조를 실제로 비교해야 한다.

**모델이 발전하면 기존 선택도 바꿔야 할까?** 모델의 성능과 가격은 계속 바뀐다. 지금 가장 효율적인 모델이 몇 달 뒤에도 최선이라는 보장은 없다. 그래서 평가 데이터와 기준을 유지해 두고, 새 모델이 나오면 같은 조건에서 비교할 수 있어야 한다.

**모델 성능보다 서비스 구조가 더 중요할 수도 있을까?** 답이 틀린 원인이 모델의 추론 능력이 아니라 검색된 데이터의 부정확성이나 잘못된 도구 호출일 수도 있다. 그렇다면 더 강한 모델을 써도 해결되지 않는다. 모델을 바꾸기 전에 오류가 난 단계부터 확인해야 한다.

## 현재의 생각: 가장 강한 모델이 아니라 필요한 성능을 효율적으로 달성하는 모델

처음에는 모델 성능이 높아질수록 서비스 품질도 자연스럽게 좋아질 거라고 생각하기 쉬웠다. 하지만 모델 선택은 성능 순위 비교가 아니었다. 파라미터가 많다고 반드시 성능이 높은 것도, 추론을 오래 한다고 모든 작업의 정확도가 오르는 것도 아니다. 반대로 고성능 모델이 필요한 상황에서 비용만 보고 경량 모델을 고르면, 오류와 재작업 때문에 더 큰 비용이 들 수도 있다.

그래서 모델을 고르기 전에 이 세 가지를 먼저 정해야 한다고 생각한다.

- **필요한 품질:** 어떤 작업을 어느 수준까지 정확하게 처리해야 하는가?
- **허용 가능한 비용과 시간:** 목표 품질을 위해 얼마를 쓰고 얼마나 기다릴 수 있는가?
- **실패했을 때의 영향:** 잘못된 결과가 나오면 어떤 문제가 생기고, 어떻게 발견하고 복구할 것인가?

그다음 여러 모델과 추론 설정을 같은 평가 기준으로 비교한다.

**LLM 모델 선택에서 성능과 비용은 양자택일의 문제가 아니다. 서비스가 요구하는 품질과 안전 기준을 먼저 충족한 뒤, 응답 시간과 성공 업무당 총비용을 최적화해야 한다.**

결국 **가장 성능이 높은 모델이 아니라, 서비스에 필요한 품질을 안정적으로 달성하면서 총비용과 운영 부담을 감당할 수 있는 모델이 맞는 선택**이라고 생각한다. AI 서비스 기획자에게 중요한 건 어떤 모델이 가장 뛰어난지 아는 것뿐 아니라, 그 모델을 골라야 하는 이유를 업무 기준과 측정 결과로 설명할 수 있는 능력일 것이다.
