> 중요한 것은 에이전트의 수가 아니라, 어떤 상황에서 Multi-Agent가 필요하며 도입한다면 어떤 구조로 협업하도록 설계해야 하는가이다.

## Multi-Agent를 구현하며 생각한 것

Multi-Agent 구조를 구현하면서, 에이전트를 여러 개로 나누는 것이 항상 효율적인 선택인지 생각해 봤다.

- 역할별로 에이전트를 나누면 복잡한 작업을 체계적으로 처리할 수 있지만, 그만큼 모델 호출과 에이전트 간 정보 전달이 늘어난다
- 역할과 책임이 명확하지 않으면 중복 작업을 하거나 서로 다른 판단을 내릴 수 있다
- 업무 흐름에 따라서는 하나의 에이전트가 여러 도구를 쓰는 편이 더 단순하고 효율적일 수 있다

## Single-Agent와 Multi-Agent의 선택 기준

여러 기능을 수행해야 한다는 이유만으로 에이전트를 여러 개 만들 필요는 없다.

| 구조 | 적합한 상황 |
|---|---|
| 고정 워크플로 | 실행 순서와 조건이 명확하고 자율적인 판단이 필요 없는 경우 |
| Single-Agent + Tools | 하나의 에이전트가 여러 도구를 선택하고 결과를 종합할 수 있는 경우 |
| Single-Agent + 검증 로직 | AI의 판단과 별도로 규칙 검증이나 승인 절차가 필요한 경우 |
| Multi-Agent | 독립적인 전문 판단, 역할별 맥락 분리, 병렬 처리가 실질적인 이점을 주는 경우 |

특히 Single-Agent의 성능이 낮다는 이유만으로 에이전트를 추가하는 게 맞는지는 의문이다. 검색 품질, 프롬프트, 도구 선택, 컨텍스트 관리의 문제라면 기존 구조를 고치는 것만으로 해결될 수도 있다.

## Multi-Agent가 필요한 시점

도입은 단일 에이전트의 한계를 확인한 뒤에 검토하는 게 합리적이라고 생각한다.

### 단일 에이전트가 감당할 맥락이 지나치게 복잡할 때

서로 다른 업무 규칙과 도구를 동시에 다루다가 작업 누락이나 잘못된 도구 선택이 반복된다면 역할 분리를 고려할 수 있다. 다만 프롬프트나 컨텍스트 구성 개선으로 해결되는 문제인지 먼저 확인해야 한다.

### 독립적인 작업을 병렬로 돌릴 수 있을 때

서로의 결과를 기다리지 않아도 되는 조사·분석이라면 여러 에이전트를 동시에 실행해 전체 시간을 줄일 가능성이 있다. 단, 결과 통합과 조정에도 시간이 들기 때문에 실제로 응답 시간이 줄어드는지는 검증해야 한다.

### 서로 다른 전문 판단이 필요할 때

에이전트마다 다른 도구·정보·판단 기준을 써야 한다면 역할 분리가 유리할 수 있다. 그러나 같은 모델과 같은 근거를 쓰는 에이전트가 여러 개 있다고 해서 판단의 독립성이나 정확성이 보장되지는 않는다.

### 역할별 맥락과 실행 권한을 나눠야 할 때

특정 업무에 필요한 정보와 도구만 접근하도록 역할을 나눌 수 있다. 다만 권한 통제는 에이전트의 역할 설명만으로 보장되지 않는다. 별도의 검증과 실행 통제가 필요하다.

결국 **Multi-Agent가 필요한 시점은 업무가 복잡해졌을 때가 아니라, 단일 에이전트의 한계가 확인되고 역할 분리가 그 한계를 해결할 수 있을 때**라고 판단한다.

## 오케스트레이션 구조

Multi-Agent를 쓰기로 했더라도, 에이전트를 어떻게 협업시킬지는 별개의 설계 문제다. 오케스트레이션(Orchestration)은 에이전트의 실행 순서, 작업 분배, 제어권 전달, 결과 통합을 관리하는 방식이다.

| 패턴 | 구조 및 특징 | 적합한 상황 |
|---|---|---|
| Supervisor / Manager | 중앙 관리 Agent가 작업 분배 및 결과 통합 | 여러 전문 업무를 통합해야 하는 경우 |
| Sequential / Pipeline | 앞선 Agent의 결과를 다음 Agent에 전달 | 조사 → 분석 → 검토 |
| Parallel / Fan-out | 독립 작업을 동시 실행하고 결과 통합 | 여러 데이터 소스 조사 |
| Router / Routing | 요청 유형에 따라 담당 Agent 선택 | 세무·노무 등 전문 영역 분기 |
| Handoff / Decentralized | Agent 간 실행 주도권 전달 | 상담 중 전문 담당자로 전환 |
| Reflection / Evaluator–Optimizer | 생성과 평가를 반복하며 결과 개선 | 코드 검토, 보고서 품질 개선 |

이 패턴들은 배타적이지 않고 한 시스템 안에서 조합할 수 있다. 예를 들어 Supervisor가 전문 에이전트들을 병렬로 실행하거나, Router가 담당 에이전트를 고른 뒤 순차 작업을 시킬 수 있다.

어떤 구조를 고를지는 이런 질문으로 판단한다.

- **중앙 통제가 필요한가?** 최종 의사결정과 결과 통합이 중요하다면 Supervisor
- **작업 사이에 의존성이 있는가?** 앞 단계 결과가 필요하면 Sequential, 독립적이면 Parallel
- **업무 유형에 따라 담당자가 달라지는가?** 요청 분류가 명확하다면 Router
- **실행 중 담당 주체가 바뀌는가?** 상황에 따라 제어권을 넘겨야 한다면 Handoff
- **반복적인 품질 검증이 필요한가?** 명확한 평가 기준과 종료 조건이 있다면 Reflection

오케스트레이션을 LLM이 자율적으로 정하게 할지, 코드와 상태 머신으로 통제할지도 정해야 한다. 업무 분기와 실행 순서가 명확하다면 굳이 LLM이 다음 단계를 정할 필요가 없다. 규칙으로 제어하면 동작을 예측하고 테스트하기 쉽고, 불필요한 모델 호출도 줄어든다.

**Multi-Agent를 쓰더라도 모든 의사결정을 AI에 맡기는 것이 최선은 아니다.**

## 도입할 때 부딪힐 문제

- **역할 중복과 판단 충돌:** 책임이 불분명하면 같은 작업을 반복하거나 서로 다른 결론을 낸다. 판단이 충돌할 때 최종 결정권을 누구에게 둘지도 정해야 한다
- **정보 전달 과정의 오류:** 각 에이전트가 제대로 작업했어도, 결과를 요약해 넘기는 과정에서 중요한 조건이나 근거가 빠질 수 있다
- **비용과 응답 시간 증가:** 모델 호출뿐 아니라 에이전트 간 통신, 결과 검토, 재시도에도 비용이 든다. 병렬 처리를 해도 전체 비용은 늘 수 있다
- **오류 추적과 운영 복잡도:** 결과가 틀렸을 때 어느 에이전트에서, 혹은 전달 과정에서 문제가 생겼는지 알 수 있어야 한다. 에이전트별 입력·출력, 도구 호출, 작업 전달, 실행 시간과 오류를 추적할 구조가 필요하다

## 복잡도를 어떻게 정당화할까?

구조 선택이 실제 개선으로 이어지는지 보려면 같은 업무를 서로 다른 구조로 비교해야 한다.

- A: Single-Agent + Tools
- B: Single-Agent + 별도 검증 로직
- C: Multi-Agent

같은 테스트 케이스와 평가 기준을 쓰고, 모델·도구·실행 조건의 차이도 통제한다.

| 평가 지표 | 확인할 내용 |
|---|---|
| 업무 완료율 | 사용자 요구사항을 정상적으로 완료했는가? |
| 오류율 | 최종 결과에 잘못된 정보나 판단이 있는가? |
| 응답 시간 | 요청부터 최종 완료까지 얼마나 걸렸는가? |
| 작업당 비용 | 토큰, API 호출 등에 얼마가 드는가? |
| 재작업률 | 실패 후 수정이나 재실행이 얼마나 필요한가? |
| 정보 전달 오류율 | 에이전트 간 전달 과정에서 정보가 누락·왜곡되는가? |
| 운영 복잡도 | 오류 분석과 유지보수에 얼마나 많은 자원이 드는가? |

특히 **성공적으로 완료된 업무 1건당 총비용**을 비교하는 게 중요하다고 생각한다. 예를 들어 Multi-Agent가 완료율을 85%에서 92%로 높여도 작업당 비용이 3배 넘게 늘어난다면, 그 개선이 실제 업무에서 얼마나 가치 있는지 따져야 한다.

오류의 피해가 큰 업무라면 추가 비용이 정당화될 수 있지만, 단순 반복 업무라면 Single-Agent가 더 효율적일 수 있다. 성공률만으로 구조의 우수성을 판단하기보다, 업무의 중요도와 실패 비용, 사용자에게 주는 가치를 함께 봐야 한다.

## 현재의 생각

Multi-Agent는 복잡한 업무를 나누고 독립 작업을 병렬로 처리할 수 있는 유용한 구조지만, 항상 Single-Agent보다 우수하다고 볼 수는 없다.

먼저 단일 에이전트가 해결하지 못하는 문제가 무엇인지 확인하고, 기존 도구와 워크플로 개선으로 풀리는지 검토해야 한다. 도입이 필요하다고 판단한 뒤에도 업무의 의존성, 의사결정 권한, 역할 간 정보 전달 방식을 보고 오케스트레이션 구조를 골라야 한다. 그리고 그 성능 개선이 늘어나는 비용과 운영 복잡도를 정당화하는지 검증해야 한다.

**좋은 AI 아키텍처는 가장 많은 에이전트를 쓰는 구조가 아니라, 해결하려는 문제에 필요한 만큼의 복잡도로 안정적이고 효율적인 결과를 만드는 구조라고 생각한다.**
