API가 이미 있는데 MCP는 왜 필요할까? API를 직접 만드는 것보다 이미 만들어진 MCP 서버를 연결하는 것이 편해서 사용하는 걸까? “AI를 위한 공통 프로토콜”이라는 설명만으로는 기존 API와의 차이가 쉽게 와닿지 않는다.

MCP를 이해하려면 **업무 기능을 만드는 일**과 **그 기능을 AI 애플리케이션에 연결하는 일**을 나눠 볼 필요가 있다.

> MCP의 핵심 가치는 이미 있는 기능을 여러 AI 애플리케이션에서 공통된 방식으로 발견하고 호출할 수 있게 하는 데 있다. API와 함께 설계할 때는 업무 로직을 재사용하면서, AI에 어떤 기능을 어떤 단위로 제공할지 정한다.

이 글은 주문 조회 기능을 AI 앱에 연결하는 가상 예제로 개념을 설명하고, 실제 서비스에서 API와 MCP를 함께 설계하는 순서를 정리한다.

## API, MCP, MCP 서버는 무엇이 다른가?

API는 프로그램이 다른 프로그램의 기능을 이용할 수 있도록 제공하는 인터페이스다. 웹 개발에서 흔히 말하는 API는 HTTP로 요청을 보내고 데이터를 받는 웹 API지만, API라는 개념 자체는 그보다 넓다.

MCP는 Model Context Protocol의 약자다. AI 애플리케이션과 외부 시스템 사이에서 기능과 데이터를 주고받는 방법을 정한 공개 프로토콜이다. 공식 문서도 이를 AI 애플리케이션을 외부 시스템에 연결하는 표준으로 소개한다. [1]

| 개념 | 의미 | 주문 서비스 예시 |
| --- | --- | --- |
| 업무 기능 | 서비스가 실제로 수행하는 처리 | 주문 조회, 배송 상태 확인 |
| 업무 API | 다른 프로그램에서 그 기능을 사용하는 접점 | `GET /orders/103` |
| MCP | AI 앱과 외부 기능 사이의 연결 규약 | 도구 목록을 받고, 도구를 호출하고, 결과를 받는 규칙 |
| MCP 서버 | 그 규약에 맞춰 기능을 제공하는 프로그램 | 주문 조회 기능을 MCP 도구로 제공 |
| MCP 도구 | MCP 서버가 제공하는 개별 호출 기능 | `get_order_status` |

따라서 “만들어진 MCP를 사용한다”는 표현은 보통 **누군가 구현한 MCP 서버를 연결해 그 서버의 도구를 사용한다**는 뜻이다.

API와 MCP를 완전히 별개의 기술 범주로 나눌 필요도 없다. MCP 서버 역시 프로그램이 사용할 인터페이스를 제공한다. MCP는 그중 AI 애플리케이션과 외부 기능을 연결하는 상황에 공통 규칙을 부여한다.

MCP 서버에 반드시 LLM이 들어가는 것은 아니다. 기존 API를 호출하고 결과를 돌려주는 프로그램으로 만들 수도 있다. 또한 “서버”는 역할을 뜻하므로 별도의 컴퓨터가 필수라는 의미도 아니다. 로컬 프로그램으로 실행하거나 원격 서비스로 제공할 수 있다. [2]

## 같은 주문 조회를 웹 화면과 AI 앱에서 사용해 보자

사용자가 다음과 같이 요청했다고 가정한다.

> 103번 주문은 왜 아직 도착하지 않았어?

주문 서비스에는 이미 다음 API가 있다.

```http
GET /orders/103
```

조회 권한을 확인한 서버가 아래 데이터를 반환한다.

```json
{
  "order_id": "103",
  "delivery_status": "delayed",
  "expected_delivery_date": "2026-11-12",
  "delay_reason": "물류센터 출고 지연"
}
```

### 웹 화면에서는 개발자가 호출 흐름을 미리 정한다

사용자가 주문 상세 화면을 열면 프론트엔드 코드가 주문 API를 호출한다. 서버가 반환한 배송 상태와 지연 사유를 화면에 표시한다.

어떤 API를 호출할지는 개발자가 작성한 화면 코드가 결정한다.

### AI 앱도 MCP 없이 기존 API를 사용할 수 있다

AI 앱 개발자는 모델에 주문 조회 도구의 설명을 제공하고, 모델이 해당 도구를 선택하면 기존 API를 호출하도록 코드를 작성할 수 있다.

예를 들어 모델이 `get_order_status(order_id="103")`를 선택하면, 앱의 실행 코드가 `GET /orders/103`을 호출하는 식이다.

이처럼 모델이 사용할 도구와 인자를 제안하도록 하는 기능을 보통 Function Calling 또는 Tool Calling이라고 한다. **도구를 모델에 제공하고 실행하는 일 자체는 MCP 없이도 가능하다.**

### MCP를 사용하면 도구를 소개하고 호출하는 연결 방식이 공통화된다

주문 서비스용 MCP 서버는 다음과 같은 도구 정보를 제공할 수 있다. 아래는 도구 정의 예시이며 실제 통신 메시지 전체는 아니다.

```json
{
  "name": "get_order_status",
  "description": "주문 번호로 배송 상태, 예정일, 확인된 지연 사유를 조회한다.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "order_id": {
        "type": "string",
        "description": "조회할 주문 번호"
      }
    },
    "required": ["order_id"]
  }
}
```

여기서 `inputSchema`는 입력 항목과 자료형을 적은 명세다. AI 앱은 이 도구에 주문 번호가 필요하다는 것을 공통 형식으로 확인할 수 있다.

MCP에는 도구 목록을 가져오는 `tools/list`와 도구를 호출하는 `tools/call` 같은 공통 메서드가 있다. AI 앱이 도구 설명을 모델에 어떻게 제공하고 어떤 도구를 허용할지는 해당 앱이 결정한다. [3]

아래 흐름에서는 AI 앱 안에 MCP 클라이언트가 포함되어 있다고 가정한다.

1. **AI 앱 → MCP 서버:** 사용 가능한 도구 조회
2. **MCP 서버 → AI 앱:** 이름과 설명 및 입력 형식
3. **AI 앱 → LLM:** 사용자 질문과 필요한 도구 설명
4. **LLM → AI 앱:** 주문 조회 도구와 103번 선택
5. **AI 앱 → MCP 서버:** 허용 여부 확인 후 도구 호출
6. **MCP 서버 → 주문 서비스:** 기존 조회 기능 실행
7. **주문 서비스 → MCP 서버:** 배송 상태와 지연 사유
8. **MCP 서버 → AI 앱:** 도구 결과
9. **AI 앱 → LLM:** 조회 결과 전달
10. **LLM → AI 앱:** 사용자에게 전달할 설명

이 예제에서 역할을 구분하면 다음과 같다.

- **LLM:** 질문을 해석하고 사용할 도구와 입력을 제안한다.
- **AI 앱:** 도구 설명을 모델에 전달하고, 허용된 호출을 실행한다.
- **MCP 서버:** 기능을 소개하고 호출을 받아 해당 기능에 연결한다.
- **주문 서비스:** 실제 주문 데이터와 업무 규칙을 처리한다.

마지막으로 AI 앱은 “103번 주문은 물류센터 출고가 지연되어 아직 도착하지 않았습니다”라는 답변을 사용자에게 보여 줄 수 있다.

배송 상태를 조회하는 업무 기능은 기존과 같다. 자연어에 따라 기능을 선택하는 부분은 모델과 AI 앱이 담당하고, MCP는 외부 기능을 소개하고 호출하는 공통 규격을 제공한다.

## 기존 API에도 표준이 있는데 MCP가 주목받는 이유는 무엇일까?

기존 API에도 표준과 재사용 수단이 있다. HTTP, OpenAPI, 서비스별 SDK는 이미 연결 작업을 줄여 왔다. MCP를 이해할 때 이 부분을 생략하면 “API는 모두 제각각이고 MCP가 처음으로 표준을 만들었다”는 오해가 생긴다.

| 기술·규격 | 주로 정하는 내용 |
| --- | --- |
| HTTP | 요청과 응답을 주고받는 규칙 |
| OpenAPI | HTTP API의 경로, 입력, 출력 등을 기술하는 방식 |
| Function Calling / Tool Calling | 모델이 사용할 도구와 인자를 표현하는 방식 |
| MCP | AI 앱이 외부 도구·자료를 발견하고 호출·수신하는 방식 |

OpenAPI는 사람과 프로그램이 HTTP API의 기능을 이해할 수 있도록 설명하는 표준이다. OpenAPI를 활용해 클라이언트 코드나 도구 연결을 생성하는 방식도 가능하다. MCP와 함께 사용할 수도 있다. [4]

MCP가 주목받는 이유는 **AI 앱마다 반복하던 도구 연결 작업을 공통된 접점으로 재사용할 수 있기 때문**이다.

예를 들어 같은 주문 기능을 사내 챗봇, 개발용 IDE, 별도의 업무 에이전트에서 사용한다고 가정해 보자. 각각의 앱에 주문 기능을 소개하고 호출 결과를 전달하는 연결을 개별 구현할 수 있다. 또는 주문 MCP 서버를 만들고, 호환되는 앱들이 공통 MCP 클라이언트로 연결하도록 구성할 수 있다.

| 관점 | MCP에서 기대하는 변화 | 여전히 필요한 일 |
| --- | --- | --- |
| AI 앱 개발자 | 공통 클라이언트로 여러 MCP 서버를 연결 | 권한 설정, 제공 도구 선택, 앱별 동작 검증 |
| 서비스 제공자 | 같은 MCP 서버를 여러 호환 AI 앱에 제공 | 업무 기능 구현, 도구 설명과 입출력 설계 |
| 사용자 | 이미 제공되는 연결을 설정해 기능 사용 | 계정 연결, 접근 범위와 실행 내용 확인 |

이러한 연결의 재사용이 MCP의 큰 가치다. 다만 기존에도 SDK와 OpenAPI 기반 자동 생성으로 중복을 줄일 수 있었으므로, 모든 통합 코드가 사라지거나 모든 기능이 설정만으로 연결된다고 해석해서는 안 된다. MCP의 초기 발표 역시 여러 데이터 소스와 AI 시스템 사이의 분산된 연결을 공통 프로토콜로 정리하는 목표를 설명했다. [5]

### 실제 사례: Stripe

Stripe는 기존 API를 호출하고 문서를 검색하는 도구를 MCP 서버로 제공한다. 공식 문서는 같은 서버 주소를 여러 MCP 지원 AI 앱에 연결하는 방법을 안내한다. [6]

서비스 사용자는 Stripe의 결제 기능을 새로 구현하는 것이 아니다. 제공된 MCP 서버를 연결해 기존 기능을 이용한다. Stripe 입장에서는 AI 앱마다 별개의 연결 방식을 만드는 부담을 줄일 공통 접점을 제공하는 셈이다.

따라서 “MCP가 API보다 획기적인가?”라는 질문은 **기능 자체의 성능**과 **기능을 연결·재사용하는 방식의 변화**로 나눠 보는 편이 정확하다. MCP를 사용한다고 배송 조회가 더 정확해지거나 LLM이 자동으로 똑똑해지는 것은 아니다. 이점은 호환되는 도구 생태계와 연결 재사용에서 나타난다.

## 이미 만들어진 MCP 서버가 편해서 사용하는 것도 맞다

다만 비교 대상을 정확히 잡아야 한다.

외부 서비스의 API도 대부분은 이미 만들어진 것을 가져다 쓴다. 이때 직접 작성하는 것은 그 API를 호출하고 내 앱의 동작에 맞게 연결하는 코드다.

제공 업체가 MCP 서버까지 제공하면, AI 앱과 외부 API 사이에서 필요한 연결의 일부도 이미 구현되어 있는 것이다.

| 상황 | 할 일 |
| --- | --- |
| 외부 서비스가 API만 제공 | API를 호출하거나 SDK·연결 도구를 사용 |
| 외부 서비스가 MCP 서버도 제공 | 호환 AI 앱에 연결하고 제공되는 기능 사용 |
| 우리 서비스에 기존 API가 있음 | 필요한 API를 호출하는 MCP 서버 추가 가능 |
| 우리 서비스의 업무 기능이 아직 없음 | 업무 로직을 구현하고 필요한 접점을 설계 |
| 자체 AI 앱에서 자체 기능 몇 개만 사용 | 직접 함수·API 연결로 시작할 수도 있음 |

만들어진 MCP 서버를 연결하면 편하지만, 그 서버가 제공하는 기능까지만 사용할 수 있다. 주문 조회 도구만 있는 서버에 연결한다고 우리 회사만의 복잡한 반품 정책이나 승인 절차가 자동으로 생기는 것은 아니다.

서로 다른 업체가 만든 MCP 도구의 업무 의미까지 같아지는 것도 아니다. 같은 주문 조회 기능이라도 한 곳은 주문 번호를 받고 다른 곳은 배송 번호를 받을 수 있다. MCP는 그 차이를 설명하고 호출하는 공통 형식을 제공한다.

## API와 MCP는 실제로 어떻게 함께 설계할까?

가장 먼저 정할 것은 서비스가 수행할 업무 기능이다. 그다음 웹 화면과 AI 앱이 그 기능에 접근하는 방법을 설계하면 된다.

### 1단계: 공통 업무 기능을 정한다

주문 서비스라면 다음을 정한다.

- 어떤 주문을 조회할 수 있는가?
- 배송 상태와 지연 사유는 어디에서 가져오는가?
- 사용자별로 어떤 주문에 접근할 수 있는가?
- 데이터가 없거나 배송 정보가 오래됐을 때 무엇을 반환하는가?

이 내용은 웹과 AI 앱이 함께 적용받아야 하는 업무 규칙이다.

### 2단계: 웹 API와 MCP 도구가 같은 업무 로직을 사용하게 한다

가상의 구조는 다음과 같다.

- 업무 웹 화면 → HTTP API → **공통 업무 서비스**
- AI 앱 → MCP 도구 → **공통 업무 서비스**
- **공통 업무 서비스** → 업무 DB, 배송사 API

웹은 `GET /orders/103`을 호출하고, AI 앱은 `get_order_status(order_id="103")`를 호출한다. 두 경로는 같은 조회·권한·상태 판정 로직을 사용한다.

기존 시스템을 활용할 때는 MCP 서버가 기존 HTTP API를 호출하면 된다. 같은 애플리케이션 안에서 구현한다면 공통 업무 함수를 직접 호출할 수도 있다. **MCP 도구마다 반드시 별도 REST API를 먼저 만들 필요는 없다.**

이 구조의 목적은 처리 기준을 일치시키는 데 있다. 화면에서 보이는 주문 상태와 AI가 설명하는 상태가 서로 다른 규칙으로 계산되지 않도록 한다.

### 3단계: AI에게 제공할 기능의 단위를 정한다

API 하나를 MCP 도구 하나에 연결하는 것이 적절한 경우도 있다. 단순한 주문 상태 조회가 그런 예다.

하지만 질문 하나를 해결하기 위해 거의 항상 같은 정보를 여러 번 조회해야 한다면 함께 제공하는 방식을 검토할 수 있다.

| 필요한 업무 | 도구 구성 예시 |
| --- | --- |
| 특정 주문의 배송 상태 확인 | `get_order_status` |
| 주문·배송·처리 이력을 함께 확인 | `get_order_context` |
| 취소 가능한지 확인 | `check_order_cancellation` |
| 실제 주문 취소 | `cancel_order` |

Anthropic은 에이전트를 위한 도구 설계에서 기존 API를 그대로 감싸는 방식만 고집하기보다, 필요한 정보를 모아 주고 불필요한 결과를 줄이는 구성을 권고한다. [7]

업무 정보를 묶은 API를 만드는 것은 기존 개발에서도 가능하다. MCP에서 새롭게 주의를 기울일 부분은 **모델이 도구 설명을 보고 적절한 기능을 선택할 수 있는가**다.

한 도구의 목적이 너무 넓으면 무엇이 실행되는지 이해하기 어렵고, 너무 잘게 나누면 필요한 정보를 얻기 위한 호출이 늘어날 수 있다. 자주 수행할 업무를 기준으로 비교하면 된다.

### 4단계: 이름·설명·입출력의 의미를 명확히 한다

`get_data`보다 `get_order_status`가 구체적인 이유는 반환할 정보의 범위를 이름에서 알 수 있기 때문이다.

설명에는 무엇을 하는지, 언제 사용하는지, 입력에 무엇이 필요한지, 데이터가 변경되는지를 적는다. 반환값은 모델이 다음 행동을 판단할 수 있도록 구성한다.

| 항목 | 주문 조회에서 정할 내용 |
| --- | --- |
| 입력 | 주문 번호인지 배송 번호인지 |
| 조회 기준 | 현재 상태인지 특정 시점의 상태인지 |
| 반환 | 배송 상태, 예정일, 확인된 지연 사유 |
| 정보 부족 | 지연 사유를 모를 때 어떻게 표시할지 |
| 데이터 범위 | 상세 주소 등 답변에 불필요한 정보는 제외할지 |
| 부작용 | 조회만 하는지, 기록이나 알림도 생성하는지 |

예를 들어 지연 사유가 확인되지 않았다면 `delay_reason: null`처럼 그 상태를 명시할 수 있다. 모델이 빈칸을 추측으로 채우지 않도록 응답 정책도 함께 정한다.

### 5단계: 실행 규칙은 서버에서 보장한다

주문 취소처럼 데이터가 변경되는 도구를 추가한다면 다음을 확인한다.

- 해당 사용자가 이 주문을 취소할 권한이 있는가?
- 현재 상태에서 취소가 가능한가?
- 승인이 필요한 경우 실제 승인 기록이 있는가?
- 응답이 끊겨 재요청해도 같은 취소가 중복 처리되지 않는가?

이 요구는 기존 API에서도 필요하다. MCP를 연결할 때 새로운 진입 경로에서도 동일하게 적용해야 한다. 도구 설명은 기능을 이해하도록 돕고, 서버의 검증 코드는 실제 실행을 통제한다.

Stripe의 MCP도 AI 앱의 도구 호출 승인과 실제 업무에 필요한 확인 절차를 구분한다. [6]

## Function Calling, API 호출, MCP의 관계를 다시 정리하면

주문 예제에서 세 개념을 다음과 같이 연결할 수 있다.

| 구분 | 예제에서 맡은 일 |
| --- | --- |
| Function Calling / Tool Calling | 모델이 주문 조회 도구와 `order_id="103"`을 선택 |
| MCP | AI 앱과 MCP 서버가 도구 소개·호출·결과를 공통 규약으로 주고받음 |
| 업무 API 또는 업무 함수 | 실제로 주문을 조회하고 접근 권한과 업무 규칙을 적용 |

Function Calling과 MCP는 함께 사용할 수 있다. MCP 서버가 제공한 도구 정보를 AI 앱이 모델의 Tool Calling 형식에 맞춰 전달하는 구조다. 공식 아키텍처 문서도 MCP가 문맥 교환 프로토콜에 집중하며, 앱이 LLM과 문맥을 어떻게 관리할지는 정하지 않는다고 설명한다. [2]

자체 AI 앱에서는 MCP 없이 Tool Calling과 직접 API 호출을 결합할 수도 있다. 반대로 MCP 도구 호출 자체는 일반 프로그램 코드로 수행할 수 있으므로, MCP 서버마다 LLM을 둘 필요도 없다.

**자연어를 해석해 기능을 선택하는 능력과, 외부 기능을 연결하는 공통 규약을 구분하면 각 기술의 역할이 명확해진다.**

## 어떤 상황에서 MCP를 도입하는 것이 유리할까?

MCP의 가치가 커지는 상황은 연결과 재사용의 필요가 커질 때다.

| 상황 | 판단 |
| --- | --- |
| 제공 업체의 MCP 서버를 AI 앱에서 바로 활용 | 제공 기능이 맞는다면 연결 코드 작성 부담을 줄일 수 있음 |
| 같은 업무 기능을 여러 AI 앱에서 사용 | 공통 MCP 서버로 재사용할 가치가 커짐 |
| 내 서비스를 외부 AI 앱에 제공 | 웹 API와 함께 MCP 접점을 검토할 수 있음 |
| 한 AI 앱에서 내부 함수 몇 개만 사용 | 직접 함수·API 연결이 간단할 수 있음 |
| 모델이 판단할 필요 없는 고정 순서 작업 | 일반 API 연동이나 워크플로부터 검토. MCP도 사용할 수 있지만 필수는 아님 |
| 필요한 기능이 기존 MCP 서버에 없음 | 서버 확장·자체 구현·직접 API 호출 중 선택 |

MCP를 추가하면 서버 배포·인증·호환성 관리가 필요할 수 있다. 네트워크 경로가 늘어나는 구조라면 지연과 장애 지점도 함께 고려해야 한다. 그래서 MCP 사용 여부만으로 성능이나 개발 생산성의 우열을 판단할 수는 없다.

도입을 결정할 때 먼저 물어볼 질문은 다음과 같다.

> 이 기능을 누가, 어떤 AI 앱에서, 몇 군데나 재사용해야 하는가?

한 번의 내부 호출을 구현하는 상황과 여러 도구에 같은 기능을 제공하는 상황에서는 답이 달라질 수 있다.

## 실제 프로젝트에 적용해 본다면

다음은 구현 완료 사례가 아니라 적용을 검토할 수 있는 설계 예시다.

### TaxDesk

기존 규정 검색과 근거 조회 기능이 있다면 이를 공통 업무 기능으로 유지한다. 자체 상담 화면에서는 기존 방식으로 호출하고, 다른 AI 앱에서도 사용해야 할 때 MCP 도구로 제공할 수 있다.

- `search_tax_rules`: 질문과 적용 시점에 맞는 규정 검색
- `get_tax_rule_source`: 확인할 근거의 원문 조회

MCP 연결 여부와 별도로 검색 품질, 시행일, 예외 조항, 근거 부족 대응은 계속 검증해야 한다.

이 단계에서 먼저 결정할 것은 MCP 서버의 개수가 아니라 **AI가 수행할 업무의 범위와 재사용할 공통 로직**이다.

## API 설계에서 함께 생각할 질문

1. 이 기능은 웹 화면과 AI 앱에서 어떤 목적으로 사용되는가?
2. 어떤 업무 로직과 검증을 공통으로 유지할 것인가?
3. 모델이 사용자 요청과 도구 이름·설명을 보고 적절하게 선택할 수 있는가?
4. 입력·출력에 대상, 단위, 기준 시점이 명확한가?
5. 조회, 초안 작성, 실제 변경의 차이가 드러나는가?
6. 여러 AI 앱에 제공할 필요가 있는가, 현재는 직접 연결로 충분한가?
7. 실제 모델이 잘못된 도구나 대상을 선택하는 상황을 어떻게 검증할 것인가?

MCP를 고려한 API 설계는 우리 기능을 여러 AI 앱에 제공할 수 있도록 접점을 정리하는 작업으로 볼 수 있다. 공통 업무 로직을 바탕으로 웹 API와 MCP 도구를 구성하고, 모델이 이해할 설명과 입출력의 의미를 분명하게 만드는 것이 출발점이다.
