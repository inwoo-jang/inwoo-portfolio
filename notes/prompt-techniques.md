> 원하는 결과가 무엇인지 먼저 정해야 프롬프트 기법도 고를 수 있다고 생각한다.

수업에서 배운 프롬프트 기법을 **언제 꺼내 쓸지** 기준으로 정리한 참고용 노트다. 기본 구조는 RICE로 잡고, 목적에 따라 다른 기법을 얹는다. 예를 들어 RICE로 요청을 정리한 뒤 Step-back으로 전제를 한 번 더 검토하는 식이다.

## 언제 무엇을 쓰나

| 기법 | 사용할 상황 | 작성 방법 |
|---|---|---|
| RICE | 요청의 기본 구조를 잡을 때 | 역할 · 지시 · 배경 · 예시를 구분해서 작성 |
| Zero / One / Few-shot | 원하는 출력 형식을 전달할 때 | 예시를 제공하지 않거나(Zero), 1개(One), 여러 개(Few) 제공 |
| CoT(단계별 추론) | 원인 분석·계산처럼 단계가 있는 문제 | 분석 단계를 나눠 요청 |
| Self-Consistency | 응답마다 결론이 달라질 때 | 여러 번 추론한 결과를 비교하고 다수결로 선택 |
| Step-back | 문제의 배경이나 전제를 먼저 확인할 때 | 세부 작업에 앞서 근본 질문을 제시 |
| Devil’s Advocate(반대 관점 검토) | 기획안의 약점을 찾을 때 | 실패한 상황을 가정하고 이유와 보완 근거를 요청 |
| Multi-Persona(여러 역할 부여) | 여러 관점에서 검토할 때 | 역할별 의견을 비교한 뒤 결론을 요청 |
| Meta Prompting | 요청 문장을 작성하기 어려울 때 | AI에게 작업에 맞는 프롬프트 작성을 요청 |
| Socratic(질문을 통한 구체화) | 요구사항이나 배경이 정리되지 않았을 때 | AI가 필요한 정보를 먼저 질문하도록 요청 |
| Markdown | 긴 요청을 구조화할 때 | 제목 · 목록 · 표로 내용을 구분 |

## RICE 템플릿

```markdown
[Role]        누가 — 예: 10년 차 B2B 전략 컨설턴트
[Instruction] 무엇을 — 결과물 · 범위 · 우선순위
[Context]     상황 — 회사 · 문제 · 목표 (구체적일수록 환각 ↓)
[Examples]    모양 — 예시 또는 출력 목차
+ 규칙 · 말투 · 제약(글자 수) · 형식(표·JSON)
```

## 예시

```text
[Few-shot]
문장을 긍정/부정으로 분류해.
"정말 감동적이었어요" -> 긍정
"지루해서 졸았어요" -> 부정
"연기가 훌륭했어요" ->

[CoT]
원인을 단계적으로 생각해 줘: 증상 → 원인 후보 → 근거 대조·순위 → 검증 방법 → 즉시 조치 / 근본 대책

[Step-back]
보고서 쓰기 전에 먼저 답해: 이 서비스가 안 팔리는 근본 원인은?

[Devil's Advocate]
이 제안서가 부결됐다고 가정해. 거절 이유 5개 + 각각 보완할 근거.

[Multi-Persona]
CFO와 COO로서 찬반 토론 → 최종 결정과 승인 조건 정리.
```

## 헷갈리지 말 것

- CoT: 효과는 모델에 따라 다르며, 작은 모델에서는 성능이 낮아질 수도 있다
- Few-shot: 예시의 출력 형식을 일관되게 맞춘다
- Temperature: API에서 지정하는 설정값이다. 프롬프트에 쓰는 말투 지시와 구분한다
- 공손한 표현이나 감정에 호소하는 문구의 효과는 모델·과제마다 다르므로 필수 규칙으로 두지 않는다
