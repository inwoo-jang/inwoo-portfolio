> 데이터 전처리의 목적은 단순히 데이터를 깨끗하게 만드는 것이 아니라, 데이터를 사용하는 과정에서 의미가 왜곡되지 않도록 준비하는 것이라고 생각한다.

## 전처리는 반드시 필요할까?

데이터 전처리(Data Preprocessing)는 원본 데이터를 분석, 모델 학습, 검색 등의 목적에 적합하도록 정리하고 변환하는 과정이다.

하지만 모든 데이터를 반드시 전처리해야 하는 것은 아니다.

이미 정형화된 데이터이거나 짧은 텍스트를 LLM에 직접 전달하는 경우에는 별도의 전처리 없이도 사용할 수 있다.

반면 다양한 형식의 데이터를 통합하거나, 머신러닝 모델을 학습시키거나, 대량의 문서로 RAG 시스템을 구축한다면 데이터의 품질과 구조를 점검하는 과정이 중요해진다.

즉, 전처리의 필요성과 범위는 **데이터의 상태와 사용 목적에 따라 달라진다.**

전처리는 **데이터 품질 관리(Data Quality)** 와도 구분해 두면 좋다. 전처리는 데이터를 목적에 맞게 변환하는 과정이고, 데이터 품질 관리는 원본의 정확성·완전성·최신성·일관성을 지속적으로 확인하는 더 넓은 개념이다. 원본이 틀렸다면 전처리를 아무리 잘해도 결과는 틀린다.

## 표 데이터의 전처리

표 데이터에서는 결측값, 중복, 이상값, 자료형, 단위 등을 확인한다.

| 항목 | 처리 예시 | 주의할 점 |
|---|---|---|
| 결측값 | 대체, 삭제, 결측 유지 | '모름'과 0을 혼동하지 않기 |
| 중복 | 중복 행 확인·제거 | 정상적인 반복 거래를 삭제하지 않기 |
| 이상값 | 범위 검증, 수정 또는 유지 | 실제로 발생한 극단값일 수 있음 |
| 단위 | 원·만원, kg·g 통일 | 환산 오류 방지 |
| 형식 | 날짜·숫자·문자열 통일 | 원래 의미와 정밀도 유지 |
| 스케일링 | 정규화·표준화 | 사용하는 모델의 특성에 따라 선택 |

예를 들어 급여 데이터에서 수당이 0원인 것과 수당 정보가 입력되지 않은 것은 다르다.

결측값을 일괄적으로 0으로 채우면 미입력 데이터가 실제 지급액 0원으로 해석될 수 있다.

또한 머신러닝에서는 전처리 과정에서 데이터 누수(Data Leakage)가 발생할 수 있다. 학습 데이터와 테스트 데이터를 분리하기 전에 전체 데이터의 평균으로 결측값을 채우면 테스트 데이터의 정보가 학습 과정에 반영될 수 있다.

따라서 전처리는 데이터를 정리하는 작업인 동시에 **데이터의 의미와 평가의 신뢰성을 관리하는 작업**이다.

## 문서 데이터의 전처리

RAG 시스템에서는 PDF, 이미지, Word 등 다양한 문서를 검색 가능한 형태로 변환해야 한다.

대표적인 과정은 다음과 같다.

**문서 수집 → 텍스트·구조 추출 → 오류 검토 → 청킹 → 메타데이터 부여 → 임베딩·인덱싱**

- **OCR:** 이미지나 스캔 문서에서 텍스트 인식
- **문서 구조 분석:** 제목, 문단, 목록, 표의 관계 파악
- **청킹(Chunking):** 문서를 검색에 적합한 단위로 분할
- **메타데이터:** 문서명, 출처, 작성일, 시행일, 버전 등 관리

특히 청킹은 무조건 일정한 글자 수로 나누는 것이 최선은 아니다.

조문이나 문단의 의미가 분리되지 않도록 문서 구조를 기준으로 나누는 방식도 고려해야 한다.

## 전처리를 지나치게 하면 생기는 문제

가상의 세법 문서를 예로 들어 보자.

> 제○조: 일정 요건을 충족하는 경우 세액공제를 적용한다. 다만, 특정 업종은 제외한다.

이 문서를 청킹하면서 본문과 '다만'으로 시작하는 예외 조항을 분리하고, 검색 결과에 본문만 포함된다면 AI는 제외 업종에도 공제가 가능하다고 답변할 수 있다.

시행일이나 적용 연도를 제거한 경우에도 과거 규정을 현재 규정으로 잘못 안내할 위험이 있다.

표 데이터 역시 마찬가지다. 결측값을 임의로 채우거나 이상값을 무조건 제거하면 실제 데이터가 가진 의미를 왜곡할 수 있다.

**전처리를 많이 했다는 것이 반드시 데이터 품질이 높아졌다는 뜻은 아니다.**

## 전처리의 범위는 어떻게 결정할까?

전처리 기준은 사용 목적과 오류 발생 시의 영향을 고려해 결정해야 한다.

1. 데이터가 어떤 업무와 판단에 사용되는가?
2. 원본 데이터에 어떤 품질 문제가 존재하는가?
3. 무엇을 수정하거나 제거하면 의미가 달라지는가?
4. 전처리 후 결과를 원본과 비교할 수 있는가?
5. 실제 모델 성능이나 검색 정확도가 개선되었는가?

특히 법률·세무처럼 정확성이 중요한 도메인에서는 날짜, 수치, 적용 대상, 예외 조건, 출처를 보존하는 기준이 필요하다.

## 전처리의 효과는 어떻게 검증할까?

전처리 방식이 실제로 유효한지는 **같은 평가 데이터에서 전처리 방식만 바꿔 비교해야** 알 수 있다.

예를 들어 RAG를 구축할 때 청킹 방식을 이렇게 비교할 수 있다.

| 비교안 | 방식 | 설명 |
|---|---|---|
| A | 전처리 최소화 | 문서 전체 또는 큰 단위로 검색 |
| B | 고정 크기 청킹 | 일정 토큰 수로 분할 |
| C | 구조 기반 청킹 | 조문·제목·문단 경계 중심으로 분할 |

같은 문서·질문·검색 조건에서 아래 항목을 비교한다.

| 지표 | 확인할 내용 |
|---|---|
| 정답 근거 검색률(Recall@k) | 정답에 필요한 근거가 상위 k개 검색 결과 안에 들어오는가? |
| 답변 정확도 | 미리 정한 정답 기준을 충족했는가? |
| 응답 시간 | 검색과 답변 생성에 얼마나 걸렸는가? |
| 비용 | 임베딩·검색·모델 호출에 드는 비용 |

세법 문서라면 위에서 본 위험한 경우를 평가 질문에 일부러 넣는다. 예외 조항(‘다만’)이나 시행일에 따라 답이 달라지는 질문을 넣어야, 청킹이 맥락을 끊었는지 확인할 수 있다.

실제 결과를 측정하기 전에는 어떤 방식이 가장 좋은지 단정하지 않는다. TaxDesk 같은 세무 RAG 서비스를 기획할 때 이 비교 방식을 요구사항으로 정할 수 있다.

## 현재의 생각

전처리는 데이터를 무조건 단순하게 만드는 과정이 아니라, **목적에 맞게 정리하면서 판단에 필요한 정보를 보존하는 과정**이라고 생각한다.

AI 서비스 기획자라면 전처리 기술을 모두 직접 구현하지 않더라도, 어떤 정보가 누락되면 잘못된 결과가 나오는지 이해하고 데이터 처리 기준과 검증 방법을 정의할 수 있어야 한다.

특히 RAG에서는 청킹 크기 자체보다 검색된 문서가 질문에 답할 수 있는 충분한 맥락을 포함하는지가 더 중요한 판단 기준이 될 수 있다.
