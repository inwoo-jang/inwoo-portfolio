> 기술스택을 선택한다는 것은 가장 뛰어난 기술을 고르는 일이 아니라, 서비스의 요구사항을 충족하기 위해 필요한 기술과 복잡도를 결정하는 일이라고 생각한다.

## 한눈에 보기

기획자가 프레임워크를 직접 고를 필요는 없다. 대신 이 순서로 판단 기준을 만들어 개발팀에 넘긴다.

| 순서 | 할 일 | 이 글에서 |
|---|---|---|
| 1 | 기능뿐 아니라 응답 시간·정합성·처리량·보안 같은 **품질 기준**을 먼저 정한다 | 기획자는 무엇을 정하나 |
| 2 | 이미 있는 시스템과 **팀 역량**을 확인하고, 새 기술이 정말 필요한지 본다 | 기술 선택 기준 6가지 |
| 3 | 기술을 더할 때 얻는 효과와 늘어나는 **운영 비용**을 비교한다 | 오버엔지니어링 · MSA |
| 4 | **지금 필요한 것**과 미래를 위한 준비를 구분한다 | 지금과 미래 구분하기 |
| 5 | 선택한 **근거와 재검토 조건**을 남긴다 | ADR |

## 이 질문을 하게 된 계기

웹 서비스나 AI 프로젝트를 하면서 기술스택을 어떻게 조합해야 하는지 궁금했다. 같은 웹 서비스라도 어떤 프로젝트는 Next.js만으로 프론트엔드와 백엔드를 구현하고, 어떤 프로젝트는 React와 Spring Boot를 나눈다. 여기에 Redis, Docker, Kubernetes, Kafka가 더해지기도 한다.

각 기술이 무슨 역할을 하는지는 공부하면 알 수 있다. 하지만 **어떤 상황에서 그 기술이 필요한지, 굳이 도입하지 않아도 되는지는 별개의 문제**였다. 최신 기술을 적극적으로 써야 할까? 지금 요구사항만 만족하면 될까? 나중의 확장까지 미리 고려해야 할까? 그리고 기획자는 기술스택을 어디까지 이해하고 어떤 결정에 참여해야 할까?

이 질문을 중심으로 아키텍처 선택 기준과 오버엔지니어링을 조사했다.

## 기획자는 무엇을 정하나

구체적인 프레임워크와 데이터베이스를 고르고 아키텍처를 설계하는 건 개발자와 아키텍트의 역할이다. 하지만 아키텍처는 서비스가 **얼마나 빠르고 안정적으로 동작해야 하는지, 어떤 데이터와 연결되는지, 운영 비용을 얼마나 쓸 수 있는지**에 따라 달라진다. 이 요구사항과 우선순위를 정하는 데는 기획자의 판단이 필요하다.

| 구분 | 기획자·PM | 개발자·아키텍트 |
|---|---|---|
| 기능 요구사항 | 사용자 업무 흐름과 기능 정의 | 구현 구조와 로직 설계 |
| 비기능 요구사항 | 성능·보안·가용성 목표 협의 | 목표 달성을 위한 기술 설계 |
| 기술스택 선정 | 비즈니스 제약과 우선순위 제공 | 기술 대안 평가와 선정 주도 |
| 시스템 연동 | 연동 목적·범위·데이터 요구 정의 | API·인증·데이터 연동 구현 |
| 운영 | 비용·장애 영향·운영 정책 정의 | 배포·모니터링·복구 체계 구현 |
| 기술 도입 판단 | 기대 효과와 비용의 균형 검토 | 구현 난도와 기술적 위험 검증 |

실제 책임 범위는 조직과 프로젝트에 따라 다르다. 중요한 건 특정 기술을 쓰라고 지시하는 게 아니라, **개발팀이 합리적인 선택을 할 수 있도록 요구사항과 제약조건을 명확하게 만드는 것**이다.

> [!예시] 같은 기능도 조건에 따라 구조가 달라진다
> PDF를 올리면 AI가 내용을 분석하는 서비스. 기능만 보면 `PDF 업로드 → AI 분석 → 결과 표시`로 간단하다. 하지만 아래 조건에 따라 구조가 달라진다.
>
> - **응답 시간:** 5초 안에 보여줘야 하는가, 3분이 걸려도 괜찮은가?
> - **처리량:** 동시에 몇 개의 문서를 처리해야 하는가?
> - **데이터:** 개인정보나 기밀정보가 들어가는가?
> - **안정성:** 분석 중 오류가 나면 재시도해야 하는가?
> - **사용자 경험:** 화면을 닫아도 분석을 계속해야 하는가?
> - **운영 비용:** 문서 한 건당 허용 가능한 처리 비용은 얼마인가?
>
> 짧게 끝나는 작업이라면 일반 API 요청으로 충분하다. 분석에 몇 분이 걸리고 작업이 많다면 비동기 작업 큐, 별도 Worker, 처리 상태 저장이 필요할 수 있다.

필요한 기술은 기능 자체보다 **기능에 붙은 조건**에서 정해지기도 한다. 이 조건을 정의하는 것이 기술스택 선택에 참여하는 기획자의 역할이라고 생각한다.

## 기술 선택 기준 6가지

기술스택은 유행하는 기술을 조합하는 게 아니라, 서비스에 필요한 역할을 나누고 각 역할에 맞는 기술을 배치하는 과정이다.

| 영역 | 역할 | 기술 예시 |
|---|---|---|
| Frontend | 화면과 사용자 상호작용 | React, Next.js, Vue |
| Backend | 비즈니스 로직, 인증, API | Spring Boot, FastAPI, NestJS |
| Database | 영속 데이터 저장 | PostgreSQL, MySQL |
| Cache | 반복 조회 결과 등 임시 저장 | Redis |
| Queue | 비동기 작업 전달과 처리 조율 | RabbitMQ, SQS |
| Infrastructure | 서버 실행, 배포, 확장 | 클라우드 호스팅, Docker, Kubernetes |
| Observability | 로그, 메트릭, 추적 | OpenTelemetry, Prometheus, Grafana |

이 기술이 모든 서비스에 필요한 건 아니다. Next.js와 PostgreSQL만으로 구현할 수 있는 서비스도 있고, 복잡한 업무 시스템이라면 별도 백엔드가 필요할 수 있다. 기술을 고를 때는 이 여섯 가지를 본다.

| 기준 | 확인할 질문 | 주의할 점 |
|---|---|---|
| 요구사항 적합성 | 필요한 기능과 품질 수준을 안정적으로 제공하는가? | 기능이 많다고 좋은 게 아니다 |
| 팀의 기술 역량 | 팀이 개발하고, 개발 후에도 직접 관리할 수 있는가? | 낯선 기술은 학습과 시행착오 시간이 든다 |
| 기존 시스템과의 호환성 | 이미 있는 인증·DB·API를 재사용할 수 있는가? | 성격이 크게 다른 기능은 분리가 나을 수도 있다 |
| 운영·유지보수 비용 | 배포, 모니터링, 장애 대응, 보안 관리를 누가 하는가? | 클라우드 요금뿐 아니라 사람의 운영 시간도 비용이다 |
| 생태계와 성숙도 | 문서, 보안 업데이트, 장기 지원이 있는가? | 새 기술은 운영 사례가 부족하고, 오래된 기술이 늘 안전한 것도 아니다 |
| 변경 가능성 | 나중에 바꾸거나 걷어내기 쉬운가? | 교체를 위한 추상화를 처음부터 많이 만드는 것도 과잉 설계다 |

마지막 기준은 특히 균형이 필요하다. **변경 가능성을 확보하는 비용과 실제로 변경할 가능성을 함께 판단해야 한다.**

## 오버엔지니어링은 어떻게 판단할까?

조사하면서 가장 중요하다고 느낀 개념은 Overengineering, 즉 과잉 설계다. 오버스펙이 성능 요구보다 지나치게 높은 사양을 쓰는 것이라면, 오버엔지니어링은 **시스템 구조와 기술 구성 자체가 필요 이상으로 복잡해지는 문제**까지 포함한다.

다만 서비스가 작다는 이유만으로 복잡한 구조를 오버엔지니어링이라고 단정할 수는 없다. 처음부터 높은 안정성이나 대규모 처리량이 필수인 서비스도 있다. 판단의 핵심은 **추가되는 복잡성이 해결하는 문제와 그 비용이 균형을 이루는가**다.

| 기술 | 도입이 필요한 상황의 예 | 과잉 설계가 될 수 있는 상황 |
|---|---|---|
| Redis | 반복 조회 병목이나 캐시 요구가 확인됨 | 기존 DB만으로 성능 목표를 충족함 |
| Kafka | 다수 소비자, 이벤트 스트림, 재처리 요구 | 단순 알림이나 소규모 비동기 작업 |
| Kubernetes | 컨테이너 운영 규모와 자동화 요구 | 관리할 서비스가 적고 운영 역량이 부족함 |
| MSA | 독립 배포와 확장이 실질적으로 필요함 | 하나의 작은 팀이 단일 제품을 개발함 |
| Vector DB | 의미 기반 검색과 유사도 검색이 필요함 | 일반 SQL·키워드 검색으로 충분함 |
| Multi-Agent | 역할 분리로 검증 가능한 이점이 있음 | 하나의 Agent나 Workflow로 처리 가능함 |

이 표만으로 도입 여부를 판단할 수는 없다. 예를 들어 Kubernetes가 이미 조직의 표준 인프라라면, 새 프로젝트가 이를 쓰는 게 따로 운영 환경을 만드는 것보다 효율적일 수 있다. 결국 기술의 개수가 아니라 **늘어나는 복잡성을 정당화할 수 있는지**가 중요하다.

## MSA는 언제 필요한가?

**모놀리식(Monolithic)** 은 회원, 주문, 결제, 알림 같은 여러 기능을 하나의 애플리케이션으로 개발하고 배포하는 구조다. 초기에는 개발·테스트·배포가 단순하지만, 코드가 강하게 얽히면 작은 수정에도 전체를 배포해야 하고 기능별 독립 확장이 어렵다. 다만 모놀리식이 곧 뒤섞인 코드는 아니다. 기능을 모듈로 분리한 **Modular Monolith**도 가능하다.

**마이크로서비스(MSA)** 는 기능이나 도메인별로 서비스를 나눠 독립적으로 개발·배포하는 구조다. 서비스별로 배포·확장할 수 있지만, 서비스 간 통신, 데이터 정합성, 분산 트랜잭션, 장애 추적을 따로 관리해야 한다.

| 판단 기준 | Monolith | MSA |
|---|---|---|
| 초기 개발·운영 | 상대적으로 단순 | 운영 구성 복잡 |
| 배포 | 애플리케이션 단위 | 서비스별 독립 배포 |
| 확장 | 전체 또는 분리된 구성 단위 | 서비스별 확장 가능 |
| 데이터 관리 | 단일 트랜잭션 구성에 유리 | 분산 데이터 정합성 관리 필요 |
| 장애 분석 | 상대적으로 추적 쉬움 | 분산 추적 필요성 증가 |
| 적합한 상황 | 작은 팀, 초기 제품, 강하게 결합된 업무 | 독립성이 높은 도메인, 다수 팀, 서비스별 운영 요구 |

Martin Fowler의 *Monolith First*는 모놀리식으로 시작해 서비스 경계가 분명해지면 분리를 검토하는 접근을 제시한다. 모든 프로젝트가 꼭 모놀리식으로 시작하라는 뜻은 아니고, **도메인과 서비스 경계를 아직 모르는 상태에서 구조를 너무 잘게 나누는 위험**을 경계하라는 것이다.

기획자가 던질 질문은 이것이다. **회원·주문·결제를 각각 나누면 얻는 이점이, 서비스를 따로 개발하고 운영하는 비용보다 큰가?** 모듈을 나누는 것만으로 해결되는 문제인지, 실제로 독립 배포와 확장이 필요한지도 구분해야 한다. MSA는 더 발전된 기술이라서 고르는 게 아니라, 모놀리식으로는 풀기 어려운 요구가 있을 때 고르는 것이라고 이해했다.

## 신기술은 언제 도입해야 할까?

기술이 새롭다는 사실만으로 기존 시스템보다 낫다고 판단할 수는 없다. 참고할 만한 자료가 Thoughtworks의 **Technology Radar**다. 기술과 기법을 네 단계로 분류한다.

| 구분 | 의미 | 적용 관점 |
|---|---|---|
| Adopt | 도입을 적극 고려할 수 있음 | 요구사항에 맞으면 실무 적용 |
| Trial | 제한된 범위에서 시험 | PoC나 작은 프로젝트로 검증 |
| Assess | 가능성과 특성 탐색 | 조사·학습·적용 가능성 평가 |
| Caution | 도입 시 주의 필요 | 위험과 대안 검토 |

이 기준을 그대로 따르기보다, 신기술을 무조건 도입하거나 배제하지 않고 **기술의 성숙도와 프로젝트 적합성을 나눠 평가하는 방식**을 참고할 수 있다.

> [!예시] 기존 Spring Boot 시스템에 AI 상담 기능을 더한다면
> 기존 서비스에 **Spring AI를 연결**하면 인증, 비즈니스 로직, DB, 인프라를 그대로 쓸 수 있다. **Python/FastAPI 서비스로 분리**하면 Python의 데이터 처리·모델 라이브러리를 쓰기 편하지만, 서비스 간 API 통신, 배포, 장애 대응, 인증·데이터 연동을 따로 관리해야 한다.
>
> 외부 LLM API를 호출하고 검색 결과를 쓰는 서비스라면 Java로도 충분하다. 특정 Python 라이브러리에 강하게 의존하거나 모델 학습·추론을 직접 해야 할 때 Python을 고를 근거가 생긴다. 자세한 비교는 [AI 개발에는 왜 Python을 많이 사용할까?](#n-why-python-ai)에 정리했다.

**필요한 작업을 기준으로 기술을 골라야지, 기술을 쓰기 위해 새 시스템을 만드는 건 경계해야 한다.**

## 지금 필요한 것과 미래를 위한 준비 구분하기

사용자가 적다고 확장을 전혀 고려하지 않으면 나중에 요구가 바뀔 때 크게 고쳐야 할 수 있다. 반대로 수백만 사용자를 가정해 처음부터 복잡한 분산 시스템을 만들면 지금은 불필요한 비용이 든다.

여기서 도움이 되는 개념이 **YAGNI(You Aren't Gonna Need It)** 다. 실제로 필요하지 않은 기능이나 구조를, 미래에 필요할 거라는 예상만으로 미리 구현하지 말자는 원칙이다. 미래를 전혀 고려하지 말라는 뜻은 아니다. 중요한 건 **확장을 미리 구현하는 것과 나중에 확장할 수 있게 설계하는 것을 구분하는 일**이다. 처음부터 Kubernetes를 쓰지 않아도 상태 관리와 설정을 잘 설계해 두면 확장에 대응할 수 있고, 처음부터 MSA를 구성하지 않아도 기능별 모듈 경계를 정리해 두면 나중에 분리를 검토할 수 있다.

| 구분 | 예 | 대응 |
|---|---|---|
| 지금 반드시 충족할 요구 | 응답 시간, 데이터 정합성, 보안 | 출시 시점부터 갖춘다 |
| 바뀔 가능성이 높은 요소 | 사용량 증가, 외부 API 변경, AI 모델 교체 | 바뀔 때 고칠 범위가 작도록 경계를 나눈다 |
| 일어날지 불확실한 미래 | 글로벌 확장, 대규모 분산 처리, 수십 개 서비스 간 통신 | 가능성만으로 미리 구현하지 않는다 |

확장성을 고려한다는 건 미래의 기능을 다 만들어 두는 게 아니라, **어떤 변화가 예상되고 그 변화에 대응하는 비용이 얼마나 클지 판단하는 과정**이라고 이해했다.

## 가장 단순한 구조가 항상 정답일까?

과잉 설계를 피하려면 구조를 단순하게 유지해야 하지만, 단순함 자체를 목표로 삼는 것도 위험하다. 결제 서비스라면 구조가 단순하다는 이유로 실패 재시도, 중복 결제 방지, 거래 기록을 생략할 수 없다. 개인정보를 다루는 서비스라면 규모가 작아도 접근 통제와 보안이 필요하다. **단순한 구조와 필요한 품질을 생략한 구조는 다르다.**

AWS Well-Architected Framework는 아키텍처를 평가할 때 운영 우수성, 보안, 안정성, 성능 효율성, 비용 최적화, 지속가능성을 함께 본다. 이를 바탕으로 기술 선택을 이런 순서로 검토할 수 있을 것 같다.

1. 해결해야 할 문제와 요구사항을 정의한다
2. 현재 구조나 더 단순한 대안으로 해결되는지 확인한다
3. 해결되지 않는다면 추가 기술의 효과를 검증한다
4. 도입으로 늘어나는 개발·운영 복잡성을 평가한다
5. 요구사항을 충족하는 대안 중 총비용과 위험이 합리적인 구조를 고른다
6. 실제 운영 결과를 보고 결정이 여전히 유효한지 다시 검토한다

여기서 총비용은 인프라 요금만이 아니라 개발 기간, 학습, 유지보수, 장애 대응, 기술 변경 비용까지 포함한다. 목적은 가장 단순한 기술스택이 아니라, **필요한 품질을 충족하는 범위에서 불필요한 복잡성을 줄이는 것**이다.

## 기술 선택의 근거 남기기 — ADR

기술스택은 한 번 고르면 끝나는 게 아니다. 사용자가 늘거나 요구가 바뀌면 다시 검토해야 하는데, 왜 그 기술을 골랐는지 기록이 없으면 같은 검토를 반복하게 된다.

**ADR(Architecture Decision Record)** 은 주요 아키텍처 결정에 대해 당시의 상황, 검토한 대안, 선택한 이유, 예상되는 영향을 남기는 문서다.

> [!예시] ADR — Redis 도입 여부
> **상황** · 초기 B2B SaaS에서 PostgreSQL로 조회 기능을 구현했고, 현재 응답 시간 요구를 충족한다.
>
> **검토한 대안** · 기존 PostgreSQL 유지 / 쿼리·인덱스 최적화 / Redis 캐시 도입
>
> **결정** · 지금은 PostgreSQL 구조를 유지한다. 성능 문제가 생기면 쿼리와 인덱스부터 본다.
>
> **근거** · 성능 요구를 이미 충족하는데 Redis를 더하면 캐시 무효화, 데이터 일관성, 인프라 운영 부담이 늘어난다.
>
> **재검토 조건** · 주요 API 응답 시간이 합의한 기준을 계속 넘거나, DB 부하로 서비스 품질이 떨어지면 다시 검토한다.

이 기록에서 중요한 건 Redis를 안 쓰기로 한 결정 자체가 아니라, **어떤 조건에서 그렇게 정했고 어떤 상황이 오면 결정을 바꿀지**를 적어 둔 점이다. ADR은 기술 결정을 일회성 선택이 아니라 추적하고 고칠 수 있는 과정으로 만들어 준다.

## 현재의 생각

처음에는 기술스택을 잘 조합하려면 많은 프레임워크와 인프라 기술을 알아야 한다고 생각했다. 하지만 조사하면서 **기술을 많이 아는 것과 적절한 기술을 고르는 것은 다른 역량**이라는 걸 알게 됐다.

기획자가 모든 기술 결정을 내릴 필요는 없다. 대신 **기술 결정이 서비스의 목표와 요구사항에서 벗어나지 않도록 판단 기준을 제공하고, 선택에 따른 비용과 영향을 이해하는 역할**은 중요하다고 생각한다.

좋은 기술스택은 최신 기술을 많이 쓴 조합이 아니라, 지금의 요구사항을 충분히 충족하면서 개발과 운영의 복잡성을 감당할 수 있는 조합이다. 그리고 좋은 아키텍처는 처음부터 완벽한 구조라기보다, 선택한 이유를 설명할 수 있고 상황이 바뀌었을 때 다시 판단할 수 있는 구조에 가깝지 않을까.
