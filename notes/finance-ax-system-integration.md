> 금융 AI는 기존 시스템이 확정한 사실을 설명하는 역할로 연결한다. 문서는 적용 버전과 접근권한을 붙여 검색하고, 현재 값은 권한이 확인된 업무 API에서 기준시각과 함께 받고, 상태를 바꾸는 일은 기존 거래 절차에 남긴다. 연결 지점이 늘어도 원본 데이터의 권한과 업무의 책임은 기존 시스템에 그대로 둔다.

## 이 질문을 하게 된 계기

금융 AI 아키텍처 그림은 대개 채널계·계정계·정보계와 MCI·EAI·FEP가 있는 기존 구조 옆에 AI 플랫폼, AI Gateway, MCP, RAG를 추가한 모양이다. 상자는 늘어나는데, 그 상자들이 기존 시스템과 어디서 만나는지는 그림만으로는 보이지 않는다.

![금융 AI 아키텍처. 왼쪽 기존 업무 경로는 채널계에서 MCI로 업무 서비스·API Gateway, EAI로 계정계와 정보계, FEP로 외부 기관에 이어지고 문서 저장소가 있다. 오른쪽 AI 보조 경로는 AI 앱이 AI Gateway, MCP·Tool Gateway, RAG·검색 색인으로 갈라진다. 두 경로는 세 지점에서 만난다. 업무 조회는 기존 업무 서비스·API를 거쳐 조회 전용으로 연결하고 권한은 그 서비스가 다시 확인한다. 정보계·문서 저장소의 변경은 CDC·문서 갱신으로 색인에 반영하며 적용 버전과 접근권한을 함께 붙인다. 거래·상태 변경은 AI 앱이 아니라 기존 업무 경로에서 처리한다.](media/notes/finance-ax-architecture.svg)

그래서 상담 질문 하나를 끝까지 따라가 봤다. 고객이 가입한 상품의 조건을 설명하려면 계약정보를 읽어야 하고, 현재 상태를 알려면 업무 시스템을 조회해야 한다. AI 플랫폼을 옆에 두어도 두 경로는 결국 다시 만난다. 그러면 질문은 **어디서 만나고, 무엇을 전달하며, 어느 시스템이 결과를 책임지는가**로 바뀐다. [판단·실행편](#n-finance-ax-decision-execution)에서 나눈 업무 경계를 이번에는 시스템 구조로 옮겨 보는 글이다.

> [!예시] “작년에 가입한 이 상품을 지금 해지하면 어떤 조건이 적용되나요?”
>
> 상담 화면은 인증된 직원과 선택된 고객의 업무 맥락을 서버에 전달한다. 업무 서비스는 그 직원이 이 고객의 계약정보를 조회할 수 있는지 확인한다.
>
> 계약 조회 API가 상품 식별자·가입 시점·적용 계약 버전을 돌려주면, 검색은 그 조건에 맞고 직원에게 열람 권한이 있는 약관을 찾는다. 적용 버전이 확인되지 않으면 최신 문서로 대신 답하지 않는다. 예상금액은 승인된 계산 서비스에서 기준시각과 함께 받고, 모델이 다시 계산해 확정 금액처럼 바꾸지 못하게 별도 필드로 표시한다.
>
> AI는 설명 초안을 만들고, 화면은 근거·기준시각·추가 확인이 필요한 항목을 함께 보여준다. 실제 해지는 기존 고객 확인·승인·거래 절차에서 처리한다.

## 계정계·정보계·문서는 같은 종류의 근거가 아니다

금융권에서 쓰는 시스템 명칭을 AI가 가져갈 정보의 성격으로 다시 정리하면 아래와 같다. 회사마다 명칭과 경계는 다르지만, **거래를 확정하는 곳과 분석·검색을 위해 복제한 곳을 구분하는 것**이 연결 설계의 출발점이다.

| 영역 | 역할 | AI가 연결할 때 먼저 확인할 것 |
| --- | --- | --- |
| 채널계 | 모바일뱅킹·영업점·콜센터 등 접점 | 누구의 요청이며 어떤 업무 맥락인가 |
| 계정계·업무 원장 | 계좌·계약·거래 상태를 기록하고 처리 | 어떤 API가 필요한 값과 확정 상태를 제공하는가 |
| 정보계·ODS·DW | 업무 데이터를 모아 조회·분석 | 원본 대비 갱신 지연과 집계 기준은 무엇인가 |
| 문서 저장소 | 약관·상품설명서·업무 규정·매뉴얼 | 어떤 상품·계약·기간에 적용되며 누가 열람할 수 있는가 |
| 검색 색인·캐시 | 검색·응답 속도를 위한 파생 데이터 | 원문·권한·삭제·버전 변경이 언제 반영되는가 |

이렇게 나누면 데이터가 필요한 이유에 따라 조회 경로가 달라진다. 중도해지 조건은 그 계약에 적용되는 약관에서 찾고, 지금의 해지 예상금액은 업무 API나 계산 서비스에서 받는다. 문서의 예시 금액이나 과거 분석 데이터를 현재 고객의 확정 값처럼 쓰지 않는다.

정보계가 항상 오래된 데이터라는 뜻은 아니다. 계통 이름으로 최신성을 판단하는 대신 **그 조회 결과의 기준시각과 허용 지연**을 봐야 한다. 분석에 충분히 신선한 데이터와 지금 실행할 거래를 판단할 만큼 신선한 데이터는 다를 수 있다.

기존 연계와 MCP의 관계도 같은 식으로 정리된다. MCI는 채널과 업무 시스템, EAI는 내부 시스템 간, FEP는 외부 기관과의 전문 연계를 맡는다. MCP는 이들을 대체하지 않고 AI 애플리케이션이 어떤 도구를 쓸 수 있는지 발견하고 호출하는 접점을 표준화할 뿐이다. 전문 형식, 거래 처리, 원장 검증은 여전히 기존 연계의 일이다. 그래서 기존 연계를 유지한 채 필요한 업무 기능만 도구로 감싼다. “MCP 서버를 만들었는가”보다 **“그 도구가 어떤 기존 업무 계약을 호출하는가”**가 먼저다.

## 업무 경로와 AI 경로를 분리한다는 것

상담·문서·분석을 돕는 생성형 AI는 실시간 이체·승인·주문 경로와 분리하고, 계정계 연결도 조회 전용부터 시작한다. 카드 이상거래 탐지처럼 이미 기존 ML이 맡고 있는 업무는 이 분리의 대상이 아니다. 검증된 예측모델을 업무 규칙에 넣는 일과 생성형 모델이 다음 행동과 도구 인자를 정하는 일은 구분해서 봐야 한다.

> [!예시] 상담 보조를 붙이는 두 경로
>
> ```text
> 기존 업무 경로
> 고객·직원 → 인증·업무 서비스 → 기존 연계 → 계정계
>
> AI 보조 경로
> 상담 화면 → AI 앱
>              ├─ 권한이 적용된 문서 검색
>              ├─ 허용된 업무 조회 API
>              └─ AI Gateway → 허용된 모델
> ```
>
> AI 앱은 문서와 조회 결과를 조합해 답변 초안을 만들고, 거래를 바꿀 일이 생기면 별도의 업무 절차로 넘긴다.

직원용 상담 보조라면 AI가 잠시 응답하지 못해도 기존 조회 화면과 업무 처리는 계속 쓸 수 있어야 한다. AI의 설명 능력이 기존 업무의 필수 의존성이 되지 않게 하는 것이다.

경로를 나누는 것만으로 독립성이 생기지는 않는다. 두 경로가 같은 DB 연결 풀이나 API 호출 한도를 공유하면 AI의 반복 조회가 기존 업무에 영향을 준다. 조회 도구에도 시간 제한·호출 한도·동시 요청 제한을 따로 두고, AI가 보낼 수 있는 질의의 범위를 좁혀야 한다.

## API Gateway·AI Gateway·MCP 허브는 통제하는 대상이 다르다

게이트웨이라는 이름이 반복되면 비슷한 제품을 여러 개 놓는 것처럼 보인다. 각각 무엇을 확인하는지 나누고 나니 차이가 선명해졌다.

| 연결 지점 | 확인하는 질문 | 그 지점만으로 끝내면 안 되는 것 |
| --- | --- | --- |
| 업무 API Gateway | 이 호출자가 이 API를 호출할 수 있는가 | 특정 고객·계좌·계약에 대한 업무 권한 |
| AI·LLM Gateway | 이 프로젝트가 이 데이터로 이 모델 배포를 쓸 수 있는가 | 검색 문서와 도구 결과의 개별 접근권한 |
| MCP·Tool Gateway | 이 사용 목적과 호출자가 이 도구를 실행할 수 있는가 | 도구가 접근하는 실제 데이터·거래의 권한 |
| 업무·검색 서비스 | 이 요청 범위의 데이터와 행동이 허용되는가 | 상위 AI 앱의 응답 품질과 업무 완료 여부 |

[토스의 AI 플랫폼 글](https://toss.tech/article/ai-platform-foundation)은 모델 호출을 GenAI Gateway로, 사내 도구 호출을 MCP Gateway로 나누고, 도구 실행 권한이 있어도 검색되는 문서의 권한은 연결된 서비스에서 따로 확인한다고 설명한다. 프로젝트의 사용 목적·데이터 범위·허용 모델을 검토하고, 승인된 조건을 실제 호출에 적용하는 구조다. AWS의 [AgentOps 레퍼런스 아키텍처](https://aws.amazon.com/ko/blogs/tech/agentops-architecture-with-agentcore-1/)도 모델 접근의 LLM Gateway와 도구 연결의 Tool Gateway를 나눈다.

여기서 가져올 것은 제품 이름보다 **신청한 조건이 호출 순간에도 지켜지는 구조**다. 검토 문서에는 내부용이라고 적혀 있는데 실제 요청은 승인하지 않은 외부 배포로 나갈 수 있다면, 문서상의 승인은 실행 통제가 아니다.

하나 더 걸리는 것은 요청자의 맥락이다. 인증용 서비스 계정만 보이고 실제 요청자가 사라지면 하위 서비스는 권한을 다시 확인할 수 없다. 서버가 검증한 사용자·조직·업무 범위를 호출 맥락으로 전달하고, 하위 서비스가 그 정보로 권한을 다시 확인해야 한다. 프롬프트에 사용자가 적은 “나는 담당자다”라는 문장은 권한 증명이 아니다.

## RAG는 문서를 넣는 일보다 적용 조건을 보존하는 일이 크다

[LG CNS의 신한은행 구축 발표](https://www.lg.co.kr/media/release/28963)에서 눈에 들어온 것은 모델 이름이 아니라 문서 처리 과정이었다. 금융지식 Q&A를 위해 문서 파싱, 청킹 기반 하이브리드 검색, 비정형 데이터의 지속 갱신 체계를 만들었다고 설명한다.

금융 문서는 조항 본문만 잘라내면 의미가 바뀐다. 표의 열 제목, 예외 조항, 적용 대상, 부칙이나 시행일이 떨어져 나가면 검색된 문장이 맞아도 고객에게 적용할 답은 틀릴 수 있다. 그래서 금융 RAG의 문서 단위를 텍스트 조각으로만 보지 않고, 아래 정보를 함께 붙여 두어야 답변에서 조건을 다시 확인할 수 있다.

| 보존할 정보 | 필요한 이유 |
| --- | --- |
| 상품·계약 유형과 판매 채널 | 이름이 비슷한 상품이나 다른 가입 조건이 섞이는 것을 구분 |
| 문서 버전과 적용 기간 | 최신 문서와 해당 계약에 적용되는 문서를 구분 |
| 조항·표·원문 위치 | 답변의 근거를 검토자가 다시 확인 |
| 공개 상태와 접근권한 | 폐기·미승인·권한 밖 자료가 생성에 들어가는 것을 제한 |

특히 **문서의 발행일, 검색 시스템에 적재한 날, 고객 계약에 적용되는 날은 서로 다른 값**이다. ‘최신순 검색’으로 이 셋을 해결할 수 없다. 계약 적용 관계는 문서 관리 부서의 기준정보와 연결하고, 관계가 불명확하면 답변을 확정하지 않는 쪽이 낫다.

## 권한은 답변을 가리는 단계가 아니라 근거를 가져오는 단계부터 적용한다

최종 답변에서 이름이나 계좌번호만 가리면 충분할까. 그 전에 권한 없는 문서가 모델 입력이나 로그에 들어갔다면 이미 보호 범위를 벗어난 것이다.

[Azure AI Search 문서](https://learn.microsoft.com/en-us/azure/search/search-document-level-access-overview)는 문서 단위 접근 통제에 보안 필터와 권한 메타데이터를 쓰는 방식을 설명하는데, 원본의 권한 변경은 색인에 동기화된 뒤에야 검색에 반영된다고 명시한다. 기능 이름만 보고 권한이 실시간으로 따라온다고 가정하면 안 된다.

설계로 옮기면 검색 결과를 모델에 전달하기 전에 사용자의 문서 권한을 적용하고, 같은 제약을 재랭킹·답변 캐시·대화 이력에도 이어 가야 한다. 다른 사용자가 만든 답변을 재사용할 수 있는지는 질문 문자열이 같은지가 아니라 그 답변의 근거를 두 사용자 모두 읽을 수 있는지에 달려 있다.

문서 권한과 업무 조회 권한도 다르다. 직원이 상품 약관을 읽을 수 있다고 모든 고객의 계약정보를 조회할 수 있는 것은 아니다. 그리고 정보를 읽을 수 있는 것과 외부 모델에 보낼 수 있는 것도 같지 않다. **열람 권한, 업무상 이용 범위, 외부 처리 허용 범위는 서로 다른 조건으로 남겨야 한다.**

## 밖으로 나가는 것은 질문만이 아니다

금융권에서 말하는 Hybrid RAG는 문서 검색을 내부에서 하고, 답변 생성에 필요한 일부 정보를 외부 관리형 모델로 보내는 구조다. 이 ‘하이브리드’는 내부·외부 배치의 결합이고, 앞의 신한은행 사례에서 말한 키워드·벡터 결합의 하이브리드와는 다른 뜻이다.

이 구조에서 사용자 질문만 마스킹하면 되는 것이 아니다. 검색된 문서 조각, 도구의 조회 결과, 이전 대화, 첨부파일 내용이 프롬프트에 붙기 때문에, 외부 전송 검사는 **최종적으로 조립된 모델 입력 전체**를 대상으로 해야 한다. 반대로 모든 값을 먼저 지워 버리면 필요한 계약을 찾지 못할 수도 있다. 내부 조회에서는 권한이 확인된 식별자를 쓰고, 외부 생성에는 업무상 필요한 속성만 보내는 식으로 마스킹의 위치를 목적에 맞게 정해야 한다. 토큰으로 치환했다면 복원 매핑표도 보호 대상이다.

생성 모델만 내부에 둔다고 전체 경로가 설명되는 것도 아니다. OCR, 임베딩, 재랭킹, 평가, 로그 수집이 어디서 수행되는지도 데이터 흐름에 들어가야 한다. **모델 배치도와 데이터 이동도는 같은 그림이 아니다.**

사설 연결과 데이터 처리 조건도 따로다. AWS의 [PrivateLink 문서](https://docs.aws.amazon.com/bedrock/latest/userguide/vpc-interface-endpoints.html)는 VPC와 Bedrock 사이의 사설 연결을 설명하지만 모델 처리가 회사 내부로 옮겨지는 것은 아니고, Microsoft의 [데이터 처리 문서](https://learn.microsoft.com/en-us/azure/foundry/responsible-ai/openai/data-privacy)는 배포 유형에 따라 처리 위치가 달라지며 학습 미사용 조건과 악용 모니터링 중의 처리·저장 조건을 따로 둔다. “학습에 사용하지 않는다”, “인터넷을 경유하지 않는다”, “국내에 저장한다”는 서로 대체할 수 없는 문장이다. [금융위원회의 2024년 망분리 개선 로드맵](https://www.fsc.go.kr/no010101/82885)이 생성형 AI·SaaS 활용을 열어 둔 것과, 지금 내 서비스의 외부 호출이 허용되는지도 별개의 확인이다. 그렇다고 내부 호스팅이 무조건 나은 것도 아니다. 외부 전송을 줄이는 대신 모델 운영·패치·접근 통제를 직접 맡게 되니, 배치는 **업무에 필요한 데이터의 처리 가능 범위와 그것을 유지할 조직의 역량**으로 결정할 문제다.

## MCP는 연결을 표준화하지만 업무 권한까지 정하지 않는다

[MCP의 HTTP 인가 명세](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)는 보호된 MCP 서버에 접근하는 인증·인가 흐름을 정의하고, 서버가 자신을 대상으로 발급된 액세스 토큰인지 검증하도록 요구한다. 그러나 특정 고객의 계약을 조회해도 되는지는 그 서비스가 정할 문제다.

그래서 도구를 연결할 때는 목록을 보여주는 권한과 실제 실행 권한을 둘 다 확인해야 한다. 목록에서 숨기기만 하고 실행 요청은 받아 주면 통제가 아니다. 범위도 작게 잡는 편이 검토하기 쉽다. 임의 SQL을 실행하는 만능 도구보다 특정 계약의 적용 조건을 조회하는 도구처럼 목적과 입출력이 분명한 인터페이스가 낫고, 사용자·조직·고객 범위는 모델이 넣은 값이 아니라 서버가 검증한 맥락과 대조한다. 호출자를 추적한다는 이유로 하나의 액세스 토큰을 서로 다른 대상 서비스에 그대로 전달하는 것도 적절하지 않다.

연결 대상이 고정돼 있고 호출 순서도 명확하면 일반 API와 워크플로로 충분하다. 여러 AI 클라이언트가 도구를 공유하거나 도구 발견·호출 방식을 통일할 필요가 생길 때 MCP의 이점이 분명해진다. 금융이라는 이유만으로 MCP 허브부터 도입할 필요는 없다.

검색된 문서가 새로운 실행 지시가 되는 문제도 연결 설계의 일부다. Greshake 등의 [간접 프롬프트 인젝션 연구](https://arxiv.org/abs/2302.12173)는 사용자가 직접 입력하지 않은 검색 자료도 공격 지시의 전달 경로가 될 수 있음을 보였고, CaMeL 연구인 [Defeating Prompt Injections by Design](https://arxiv.org/abs/2503.18813)은 비신뢰 데이터와 제어 흐름을 분리해 정책을 모델 바깥에서 집행하는 접근을 제시한다. 내게 남는 질문은 하나다. **문서 안의 문장이 도구 실행 범위·데이터 반출 대상·승인 절차를 바꿀 수 있는가?** 그렇다면 가드레일 문장을 강화하는 것으로는 부족하고, 도구와 데이터 흐름의 허용 조건을 실행 코드에서 제한해야 한다.

## CDC는 변경을 전달하지만 검색의 정합성을 완성하지는 않는다

CDC는 정보계와 RAG 등 여러 소비자에게 원장의 변경 데이터를 전달하는 수단으로 쓰인다. 다만 ‘원장을 읽지 않고 변경만 전달한다’고 단순화하면 초기 적재와 재처리를 놓친다. [Debezium PostgreSQL 커넥터 문서](https://debezium.io/documentation/reference/stable/connectors/postgresql.html)도 초기 스냅샷과 이후의 로그 기반 변경 수집을 구분하고, 초기 테이블 읽기와 운영 권한이 필요하다고 적는다. CDC를 원본 부하가 전혀 없는 기능으로 보면 안 된다.

변경 이벤트를 받았다는 사실은 파싱·청킹·색인·캐시 갱신이 끝났다는 뜻이 아니다. 재처리, 변경 순서, 중복 이벤트, 이전 버전 조각의 잔존까지 봐야 한다. 그리고 이미 업무 API로 정확하게 가져올 수 있는 값까지 행 전체를 텍스트로 만들어 임베딩할 이유는 없다.

삭제와 권한 변경은 내용 갱신과도 다르다. 접근권한이 회수됐는데 색인 갱신이 지연되면 그동안 검색 결과가 노출된다. 약관 구버전은 더 섬세하다. 새 약관이 나왔다고 이전 문서를 지우면 과거 계약의 근거를 잃는다. **검색에서 현재 고객에게 적용되지 않는 버전을 제외하는 일, 원문을 이력으로 보존하는 일, 폐기 대상 데이터를 삭제하는 일은 서로 다른 작업이다.**

## 실패 응답도 인터페이스 계약에 포함한다

앞의 해지 상담 흐름에 필요한 인터페이스는 `질문 → 답변`보다 구체적이다. 조회 결과에는 기준시각과 출처, 문서 결과에는 적용 버전과 원문 위치가 있어야 하고, 모델 호출에는 외부 전송 검사를 통과한 데이터만 들어가야 한다. 값이 부족할 때 어떻게 돌려줄지도 계약의 일부다. 계약을 못 찾은 경우, 문서가 없는 경우, 권한이 없는 경우, 조회가 실패한 경우를 모두 ‘답변할 수 없음’으로 뭉치면 사용자는 같은 질문을 반복하고 운영자는 원인을 구분하지 못한다. 단, 권한 없는 문서의 존재나 고객정보가 오류 메시지로 새지 않게 해야 한다.

## 현재의 생각

금융 AI는 기존 시스템을 대신 판단하게 만드는 것이 아니라, **기존 시스템이 확인한 사실을 필요한 범위에서 설명하도록 연결한다.** 실행 기능으로 확장해도 업무 권한과 최종 상태의 책임은 모델로 옮기지 않는다. 금융 AI 아키텍처가 복잡한 이유는 모델이 많아서가 아니라, 한 번의 질문에 문서의 적용 조건, 고객정보 접근권한, 현재 업무 상태, 외부 처리 범위가 함께 걸려 있기 때문이다.

연결 규칙은 세 가지다. 문서는 적용 버전·기간·접근권한을 붙여 검색하고, 관계가 불명확하면 답을 확정하지 않는다. 현재 값은 권한이 확인된 업무 API에서 기준시각과 함께 받고, 모델이 다시 계산하지 않는다. 외부 모델에는 최종 조립된 입력 전체를 검사한 뒤 업무상 필요한 속성만 보낸다.

AI Gateway는 모델 접근의 조건을, MCP는 도구 연결의 접점을, RAG는 근거를 가져오는 과정을 맡고, 어느 하나도 나머지의 권한 확인을 대신하지 않는다. 이번에 본 공개 사례는 직원 지원과 금융지식 검색이 중심이므로, 거래 실행 업무에서는 같은 구조를 다시 확인해야 한다.

## 남은 질문

- 외부 생성이 허용되더라도 고객정보를 얼마나 제외한 상태에서 답변 품질을 유지할 수 있을까? 마스킹 강도와 품질을 추상적으로 비교하기보다 실제 업무에 필요한 필드부터 확인해 보고 싶다.
- 문서 권한이 바뀐 뒤 색인·캐시까지 반영되는 지연을 어디까지 허용할 수 있을까? 검색 시점의 원본 재확인과 동기화 방식 사이에서 지연·부하·보안을 함께 봐야 한다.
- 업무 API·문서·모델 배포가 바뀌었을 때 이 연결 구조를 누가 다시 검증할까? 경계를 정한 다음의 변경 승인과 운영 책임은 [검증·운영편](#n-finance-ax-production-operations)에서 이어서 본다.
