> 모델에게 무엇을 지시할지뿐 아니라, 어떤 정보가 필요한지, 언제 조회할지, 얼마나 유지할지, 어떤 정보를 버릴지까지 설계해야 한다.

## 이 질문을 하게 된 이유

좋은 답변을 얻으려면 프롬프트를 잘 쓰는 게 중요하다고 생각하기 쉽다. 역할을 주고, 답변 형식을 정하고, 예외 조건을 구체적으로 적으면 품질이 나아질 수 있다.

하지만 아무리 정확하게 답하라고 지시해도, 필요한 정보가 제때 없으면 올바른 답을 만들기 어렵다. 반대로 관련 자료를 최대한 많이 주면 정확해질까? 꼭 그렇지도 않다. 불필요한 자료가 섞이면 모델이 중요한 정보를 놓칠 수 있고, 오래된 정보와 새 정보가 충돌할 수도 있다.

그래서 프롬프트를 어떻게 쓸지뿐 아니라, **모델이 작업할 때 어떤 정보를 줄지 설계하는 일**에 관심을 갖게 됐다. 특히 AI Agent는 검색, 도구 호출, 이전 작업 결과를 함께 쓰기 때문에 컨텍스트 관리가 더 복잡해진다.

결국 궁금한 건 세 가지다.

- 어떤 정보를 모델에 줘야 할까?
- 필요한 정보를 언제 검색하거나 갱신해야 할까?
- 얼마나 많은 정보를 주는 게 적절할까?

## Prompt Engineering과 Context Engineering

**Prompt Engineering**은 모델에 어떤 행동을 요구할지 지시문을 설계하는 것이다. 세무 상담 AI라면 이렇게 쓸 수 있다.

> 사용자의 세무 질문에 관련 법령을 근거로 답변한다. 법령에 명시되지 않은 내용은 추측하지 않으며, 적용 조건이 불명확하면 추가 정보를 요청한다.

여기서는 역할, 답변 방식, 제한 조건, 출력 형식을 정의한다.

**Context Engineering**은 모델이 작업하는 데 필요한 정보를 고르고 구성하고, 작업 과정에 따라 갱신하는 것이다. 같은 세무 상담 AI라면 이런 정보가 필요할 수 있다.

- 사용자 질문과 앞선 대화에서 확인한 조건
- 관련 법령과 적용 시점
- 검색된 문서와 출처
- 이전 도구 호출 결과
- 현재 작업의 진행 상태
- 반드시 지켜야 하는 정책과 제약 조건

Prompt Engineering이 **어떻게 행동해야 하는가**에 집중한다면, Context Engineering은 **무엇을 알고 판단해야 하는가**에 집중한다. 다만 둘은 따로 떨어진 기술이 아니라 서로 보완하는 관계다. 지시문도 모델에 전달되는 컨텍스트의 일부이기 때문이다.

RAG는 Context Engineering에 쓸 수 있는 방법 중 하나일 뿐, Context Engineering 전체를 뜻하지는 않는다.

## 내가 생각하는 컨텍스트 설계 기준

### 어떤 정보를 줘야 할까?

우선 볼 기준은 정보의 양보다 **작업과의 관련성, 신뢰성, 적용 가능성**이다.

세무 상담이라면 관련 법령을 찾는 것만으로 부족할 수 있다. 사용자가 개인사업자인지 법인사업자인지, 어느 과세기간인지에 따라 적용되는 규정과 판단이 달라지기 때문이다. 그래서 컨텍스트를 구성할 때 이렇게 나눠야 한다고 생각한다.

| 구분 | 내용 |
|---|---|
| 반드시 필요한 정보 | 판단 결과를 바꿀 수 있는 조건과 근거 |
| 있으면 유용한 정보 | 설명을 보완하거나 이해를 돕는 자료 |
| 제외할 정보 | 현재 질문과 무관하거나 중복된 내용 |
| 확인이 필요한 정보 | 출처가 불명확하거나 서로 충돌하는 내용 |

여기서 중요한 건 **정보가 부족한 상태를 알아차리는 것**이다. 필요한 조건이 확인되지 않았다면 무조건 답을 만들기보다, 사용자에게 묻거나 추가 정보를 조회하는 것도 하나의 설계 선택이다.

### 언제 줘야 할까?

모든 정보를 처음부터 줄 필요는 없다고 생각한다. AI Agent가 이런 순서로 일한다고 해 보자.

1. 사용자 요청을 해석한다
2. 필요한 정보를 판단한다
3. 검색이나 API 호출로 정보를 모은다
4. 모은 결과로 다음 행동을 정한다
5. 최종 답변을 만든다

단계마다 필요한 정보가 다르다. 요청을 해석할 때는 사용자의 목적과 조건이, 도구를 고를 때는 쓸 수 있는 도구와 호출 조건이, 최종 답변 때는 앞선 과정의 핵심 결과와 근거가 중요하다. 그래서 매 단계에 전체 정보를 반복해서 넘기기보다 **지금 단계에 필요한 정보를 골라서 주는 방식**을 검토할 수 있다.

다만 반드시 지켜야 하는 제약이나 승인 조건이 정보를 압축하는 과정에서 빠지면 안 된다. 그리고 중요한 권한 검사는 프롬프트에만 맡기지 말고 시스템에서 따로 강제해야 한다.

### 얼마나 줘야 할까?

컨텍스트가 많다고 결과가 항상 좋아지지는 않는다.

- 관련 없는 정보 때문에 판단이 틀어진다
- 중복된 문서로 토큰이 낭비된다
- 오래된 정보와 최신 정보가 충돌한다
- 긴 대화에서 핵심 조건이 빠진다
- 컨텍스트가 늘수록 응답이 느려지고 비용이 오른다

반대로 너무 줄이면 판단에 필요한 조건이나 예외가 사라질 수 있다. 목표는 컨텍스트를 최대한 줄이는 게 아니라 **정확하게 일하는 데 필요한 정보는 충분히 유지하면서 불필요한 정보를 줄이는 것**이라고 생각한다.

특히 요약해도 되는 정보와 원문을 유지해야 하는 정보를 구분하는 게 중요해 보인다. 일반적인 대화 경과는 요약할 수 있지만, 법령의 적용 요건, 수치, 날짜, 예외 조건은 요약하면서 의미가 달라지지 않게 주의해야 한다.

## AI Agent의 Memory도 같은 문제일까?

Context Engineering을 생각하다 보니 Agent Memory도 같이 봐야겠다고 느꼈다. 대화형 AI는 이전 대화를 계속 써야 할 수 있지만, 모든 기록을 무제한으로 넘기는 건 비효율적이다.

| 정보 유형 | 예시 | 관리 방향 |
|---|---|---|
| 현재 요청 | 사용자의 최신 질문 | 현재 작업에 전달 |
| 작업 상태 | 완료한 단계, 남은 단계 | 작업 진행에 따라 갱신 |
| 대화 요약 | 이전에 결정된 조건 | 핵심 정보 유지 |
| 장기 기억 | 반복적으로 쓰는 선호·설정 | 필요할 때 조회 |
| 외부 지식 | 법령, 매뉴얼, 업무 문서 | 신뢰할 수 있는 출처에서 검색 |

고민되는 건 기억을 얼마나 오래 유지할지가 아니라 **어떤 정보가 기억할 가치가 있는지**다. 오래된 정보가 현재 작업에 영향을 주지 않도록 갱신하거나 버리는 기준도 필요하다. 사용자가 명시적으로 고친 조건은 과거 조건보다 우선 반영돼야 할 것이다.

## 프로젝트에 적용할 때 점검할 질문

어떤 AI 기능이든 컨텍스트를 설계할 때 아래 질문을 먼저 확인한다.

| 점검 항목 | 질문 |
|---|---|
| 판단 조건 | 답을 바꿀 수 있는 조건(대상, 기간, 유형 등)은 무엇이고, 그게 컨텍스트에 들어 있는가? |
| 정보 부족 | 필요한 조건이 없을 때 추측하는가, 묻는가, 추가 조회하는가? |
| 출처 우선순위 | 공식 문서, 내부 자료, 과거 기록이 함께 있을 때 무엇을 먼저 믿는가? |
| 충돌 처리 | 검색된 자료끼리 내용이 다르면 최신순인가, 출처순인가, 사람에게 넘기는가? |
| 단계별 전달 | 각 단계(해석·도구 선택·답변 생성)에 무엇만 넘기는가? |
| 유지할 조건 | 대화가 길어져도 절대 빠지면 안 되는 제약·승인 조건은 무엇인가? |
| 요약과 원문 | 요약해도 되는 정보와, 수치·날짜·예외처럼 원문을 유지해야 하는 정보는 무엇인가? |
| 기억과 폐기 | 무엇을 저장하고, 언제 갱신하거나 버리는가? 사용자가 고친 조건이 우선 반영되는가? |
| 강제 수단 | 권한·정책을 프롬프트에만 맡기고 있지 않은가? |

## 컨텍스트 구성을 비교하는 방법

컨텍스트를 바꿨을 때 정말 나아졌는지는 같은 조건에서 비교해야 한다. 모델 버전, 프롬프트, 질문, 생성 설정은 그대로 두고 **컨텍스트 구성만** 바꾼다.

| 비교안 | 컨텍스트 구성 | 확인할 것 |
|---|---|---|
| A | 관련 자료만 | 필요한 근거만 줬을 때의 기준선 |
| B | 관련 자료 + 관련성 낮은 자료 | 불필요한 정보가 섞였을 때 품질이 떨어지는가 |
| C | 관련 자료 + 핵심 조건 요약 | 구조화된 정보가 조건 준수를 높이는가 |

자료 개수보다 실제 길이와 토큰 수를 기록하거나 맞추는 게 중요하다.

| 지표 | 확인할 내용 |
|---|---|
| 정답률 | 미리 정한 정답 기준을 충족했는가? |
| 근거 정확성 | 제시한 출처가 실제로 답을 뒷받침하는가? |
| 조건 준수율 | 날짜, 대상, 예외 조건을 제대로 반영했는가? |
| 응답 시간 | 답을 만드는 데 얼마나 걸렸는가? |
| 토큰 사용량 | 입력과 출력에 쓴 토큰 수 |

모델 출력은 실행마다 달라질 수 있으므로, 여러 질문과 반복 실행으로 결과가 얼마나 흔들리는지도 같이 본다.

## 현재의 생각

Prompt Engineering과 Context Engineering 중 무엇이 더 중요하냐는 단순 비교는 맞지 않다고 생각한다. 프롬프트가 명확해도 판단에 필요한 정보가 없으면 틀린 답이 나오고, 정보가 충분해도 지시가 모호하거나 잘못 구성되면 결과가 좋지 않을 수 있다.

AI Agent를 기획할 때는 모델에게 무엇을 지시할지뿐 아니라 **어떤 정보가 필요한지, 언제 조회할지, 얼마나 유지할지, 어떤 정보를 버릴지**까지 설계해야 한다. 그리고 모델에 정보를 주는 것과 시스템에서 권한·정책을 강제하는 것은 구분해야 한다.

컨텍스트를 많이 주는 것과 잘 주는 것은 다르다. 무엇이 나은지는 단정하지 않고, 프로젝트마다 위 방법으로 비교해 확인한다.
