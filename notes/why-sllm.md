여기서 sLLM(Small Language Model)은 상대적으로 작은 언어모델이라는 뜻으로 쓴다. 파라미터 수로 선을 긋기보다, **맡길 작업과 실행 환경에서 필요한 품질을 내는가**로 보는 게 맞다고 생각한다.

## ‘작은 모델이면 충분하다’는 가설이다

Microsoft Research는 특정 업무 애플리케이션에서 작은 모델을 조정해 더 큰 모델과 정확도·실행 시간을 비교한 사례를 보여 준다. 다만 그건 그 과제의 결과일 뿐, 다른 업무에서도 같은 성능이 나온다는 보장은 아니다. [SLM application interactions case study](https://www.microsoft.com/en-us/research/publication/small-language-models-for-application-interactions-a-case-study/)

그래서 작은 모델을 쓰려는 이유를 가설로 적고, 실제 업무 입력으로 하나씩 확인해야 한다.

| 가설 | 확인할 조건 |
|---|---|
| 제한된 작업에 필요한 품질을 낼 수 있다 | 정해진 항목 추출·분류에서 누락과 오답 확인 |
| 응답 시간이나 자원 사용을 줄일 수 있다 | 같은 장비·입력 길이·동시 요청 조건에서 측정 |
| 조직이 정한 환경에 배포할 수 있다 | 모델 배포 권한, 장비, 외부 연결 경로 확인 |
| 반복 작업의 비용을 줄일 수 있다 | 추론뿐 아니라 장비·운영·검수 비용까지 비교 |

짧은 추출 과제에서 품질이 확인됐다고 긴 문서 종합이나 복잡한 판단까지 맡길 근거가 되지는 않는다. 맡길 작업은 전부 평가에 넣어야 한다.

## 헷갈리기 쉬운 것들

크기와 섞어서 생각하기 쉬운 것들을 떼어 놓았다.

- **작다 ≠ 업무 특화.** 크기가 작다고 업무 지식을 갖는 건 아니다. 프롬프트, 검색 자료, 추가 학습이 필요한지는 따로 판단한다
- **작다 ≠ 자체 운영.** 작은 모델도 외부 서비스로 쓸 수 있다. 자체 운영은 배포 방식의 선택이다
- **자체 운영 ≠ 데이터 통제.** 모델을 내부에 둬도 로그, 외부 검색, 연결 도구로 데이터가 나가는 경로는 따로 확인해야 한다
- **양자화 ≠ 모델 축소.** 양자화는 가중치를 낮은 정밀도로 저장해 메모리를 줄이는 방법이다. 파라미터 수를 줄이는 것과 다르다. [Hugging Face 양자화 개요](https://huggingface.co/docs/transformers/quantization/overview)

## 같은 조건으로 비교할 것

| 비교 항목 | 측정·확인 방법 |
|---|---|
| 업무 품질 | 필수 항목 누락, 잘못된 값, 없는 정보 생성 비율 |
| 예외 처리 | 오타, 여러 요청, 정보 부족, 긴 입력에서의 동작 |
| 응답 시간 | 평균과 함께 느린 요청의 지연 시간, 동시 요청 처리 확인 |
| 전체 비용 | 장비·호스팅·유지보수·추가 학습·검수 비용 포함 |
| 배포 조건 | 라이선스, 사용 가능한 장비, 버전 갱신과 장애 대응 |

요청당 추론 비용이 낮아도 검수와 재처리가 늘면 전체 비용은 오히려 커질 수 있다. 그래서 **업무 기준을 통과한 결과 한 건을 얻는 데 드는 비용**으로 비교하는 게 맞다고 생각한다.

## 품질이 모자랄 때

필수 항목 누락처럼 코드로 잡을 수 있는 실패는 재입력 요청이나 사람 검토로 넘길 수 있다. 더 큰 모델로 넘기는 방법도 있지만, 그 전에 외부로 보내도 되는 데이터인지와 비용 한도를 먼저 정해야 한다.

모델이 스스로 말하는 자신감으로 정확성을 판단하지 않는다. 전환 기준은 별도의 평가 데이터와 검사 규칙으로 정한다.
