> AI가 사용자를 잘 기억하는 것만큼 중요한 것은 잘못된 정보를 계속 기억하지 않는 것이다. 기억을 얼마나 많이 저장할지가 아니라, 무엇을 저장하고 언제 수정하거나 삭제할지를 정하는 기준이 필요하다.

## 이 질문을 하게 된 계기

9월 AI Agent 팀 실습에서 사용자의 선호를 저장하는 도구를 구현했다. 처음에는 계획 확정과 선호 저장 두 작업에 모두 사용자 승인을 요구했지만, 계획 확정은 사용자가 이미 고른 결과를 다시 확인하는 과정이었다. 반면 선호 저장은 이후 대화에도 영향을 줄 수 있어 Human-in-the-Loop(HITL)를 유지했다.

당시에는 **어떤 작업에 사용자의 승인을 받아야 하는가**에 집중했다. 그런데 저장 이후의 문제도 생각해 볼 필요가 있었다.

사용자가 선호를 바꾸면 기존 정보는 어떻게 처리해야 할까? 한 번의 행동으로 추론한 취향을 계속 기억해도 될까? 사용자가 기억을 지워 달라고 하면 실제로 어디까지 지워야 할까?

AI Agent의 Memory를 이전 대화를 저장하는 기능이 아니라, **정보의 유효성과 사용 범위를 관리하는 문제**로 살펴봤다.

## Context Engineering과 Memory Management는 무엇이 다를까?

Context Engineering은 AI가 지금 작업을 할 때 필요한 정보를 고르고 구성하는 일이다. Memory Management는 여러 작업과 대화에 걸쳐 쓸 정보를 저장하고, 갱신하고, 삭제하는 일이다.

| 구분 | Context Engineering | Memory Management |
|---|---|---|
| 핵심 질문 | 지금 어떤 정보가 필요한가? | 어떤 정보를 계속 유지해야 하는가? |
| 주요 대상 | 현재 요청, 검색 결과, 작업 상태 | 사용자 선호, 장기 정보, 과거 경험 |
| 주요 판단 | 선택, 압축, 전달, 검색 | 저장, 갱신, 유효성 확인, 삭제 |
| 문제 사례 | 필요한 정보가 모델에 전달되지 않음 | 오래된 정보가 현재 판단에 사용됨 |

두 영역은 나뉘어 있지만 서로 영향을 준다. 메모리가 정확하게 저장돼 있어도 지금 작업에서 검색되지 않으면 쓸 수 없다. 반대로 관련된 기억을 잘 찾았더라도 그 내용이 오래됐다면 잘못된 답이 나온다.

그래서 **기억을 저장하는 것, 지금도 유효한 것, 지금 사용해도 되는 것은 서로 다른 문제**다.

## AI Agent의 Memory는 어떤 종류가 있을까?

LangGraph 공식 문서는 메모리를 단기 기억(Short-term Memory)과 장기 기억(Long-term Memory)으로 나눈다.

- **Short-term Memory:** 하나의 대화나 작업 흐름에서 유지되는 상태와 기록
- **Long-term Memory:** 여러 대화나 작업에 걸쳐 재사용하는 정보

장기 기억은 다시 이렇게 나눌 수 있다.

| 유형 | 의미 | 예시 |
|---|---|---|
| Semantic Memory | 사실과 지식 | 사용자의 선호, 프로젝트 설정 |
| Episodic Memory | 과거 경험과 사건 | 이전 작업의 처리 결과 |
| Procedural Memory | 작업 수행 규칙과 절차 | 특정 작업의 처리 방식 |

이 구분을 보면서 메모리마다 유지 기준이 달라야 한다는 생각이 들었다. 지금의 예약 상태는 작업이 끝나면 쓸모가 줄어든다. 반면 사용자가 명시적으로 정한 언어 선호는 여러 세션에서 쓸 수 있다. 모든 정보를 같은 기간 동안 보관하거나 같은 방식으로 갱신하는 건 맞지 않을 수 있다.

## 기억을 많이 하는 AI가 더 좋은 AI일까?

### LongMemEval — 기억은 저장보다 활용과 갱신이 중요하다

ICLR 2025에 발표된 *LongMemEval*은 장기 기억 능력을 다섯 가지 측면에서 평가한다.

1. 이전 대화에서 필요한 정보 추출
2. 여러 대화에 흩어진 정보의 연결
3. 시간과 사건의 순서 이해
4. 새로운 정보에 따른 기존 기억 갱신
5. 모르는 내용에 대한 답변 보류

특히 눈여겨본 건 Knowledge Updates와 Abstention이다. AI가 과거 정보를 정확하게 기억하더라도, 이후 바뀐 내용을 반영하지 못하면 지금 사용자에게는 틀린 답을 한다.

> [!예시] 시간에 따라 바뀐 선호
> - 9월: “재택근무를 선호해.”
> - 10월: “출근하는 회사도 괜찮아.”
> - 11월: “앞으로는 주 2회 이상 재택 가능한 회사만 추천해 줘.”
>
> 9월의 선호가 틀린 정보였던 건 아니다. 하지만 지금 채용 공고를 추천할 때 그대로 적용하면 문제가 된다.

그래서 메모리는 **과거 기록을 보존하는 것**과 **지금 유효한 조건을 판단하는 것**을 구분해야 한다.

### MemoryAgentBench — 잘 잊는 능력도 평가 대상이다

ICLR 2026의 *MemoryAgentBench*는 에이전트 메모리의 평가 영역에 Selective Forgetting(선택적 망각)을 포함한다. 중요한 정보를 기억하는 것뿐 아니라, 더 이상 맞지 않는 정보를 현재 판단에서 빼는 능력도 필요하다는 뜻이다.

여기서 구분할 것은 **망각과 삭제가 꼭 같은 동작은 아니라는 점**이다. 오래된 정보를 현재 판단에 쓰지 않도록 비활성화하는 것과 저장소에서 실제로 지우는 것은 다르다. 특히 사용자가 개인정보 삭제를 요청했다면 검색 결과에서 빼는 것만으로는 충분하지 않을 수 있다.

## 어떤 정보를 장기 기억으로 저장해야 할까?

모든 대화 내용을 장기 기억으로 저장할 필요는 없다. 저장 여부는 이런 기준으로 판단할 수 있다.

| 판단 기준 | 확인할 내용 |
|---|---|
| 재사용 가능성 | 이후 작업에서도 필요한가? |
| 정보의 출처 | 사용자가 직접 말했는가, AI가 추론했는가? |
| 확실성 | 검증된 사실인가, 추정인가? |
| 유효기간 | 시간이 지나면 달라지는 정보인가? |
| 민감도 | 개인정보나 인증정보가 들어 있는가? |
| 사용자 통제 | 저장 여부를 확인하고 수정·삭제할 수 있는가? |

특히 **명시적인 정보와 추론한 정보는 구분해야** 한다고 생각한다.

> [!예시] 추론한 선호
> 사용자가 검은색 옷을 여러 번 샀다고 해서 검은색을 선호한다고 볼 수는 없다. 선물로 샀을 수도 있고, 잠깐 필요했을 수도 있다. AI가 이를 확정된 선호로 저장하면 이후 추천이 틀어진다.

추론한 정보는 사용자가 직접 말한 사실과 같게 취급하지 않고, 필요하면 확인하거나 확실성을 나눠 관리해야 한다.

## 기존 기억은 언제 수정해야 할까?

새 정보가 들어왔다고 무조건 기존 기억을 덮어쓰는 것도 맞지 않다.

> [!예시] 일시적인 예외인가, 선호의 변경인가
> - **기존 기억:** “사용자는 커피를 마시지 않는다.”
> - **새 요청:** “오늘은 아이스라테를 주문해 줘.”
>
> 이 요청만으로 커피를 마시지 않는다는 선호가 바뀌었다고 볼 수 있을까? 오늘만 예외일 수도 있다. 반대로 “이제는 커피를 자주 마시니까 기존 선호를 수정해 줘”라고 했다면 명시적인 변경 요청이다.

그래서 메모리 갱신에는 최신순 정렬 이상의 기준이 필요하다.

| 상황 | 관리 방향 |
|---|---|
| 명시적인 변경 | 기존 기억을 갱신 |
| 일시적인 예외 | 현재 작업에만 적용할지 판단 |
| 새로운 추론 | 기존 사실과 구분해 보류하거나 확인 |
| 정보 충돌 | 출처, 시점, 적용 범위 확인 |
| 유효기간 경과 | 재확인하거나 현재 사용에서 제외 |

중요한 건 최신 정보가 항상 이전 정보보다 옳다는 게 아니라, **어떤 조건에서 어떤 정보가 유효한지 판단하는 것**이다. 이런 기준이 없으면 에이전트는 새 행동이 생길 때마다 사용자 선호를 불필요하게 바꿀 수 있다.

## 메모리는 언제 삭제해야 할까?

메모리 관리에서 ‘삭제’는 여러 의미로 쓰인다.

| 처리 방식 | 의미 |
|---|---|
| 현재 작업에서 제외 | 해당 요청의 컨텍스트에 넣지 않음 |
| 비활성화 | 현재 판단에 쓰지 않지만 정당한 보존 목적에 따라 유지 |
| 갱신 | 기존 값을 새 정보로 수정 |
| 삭제 | 정해진 삭제 범위의 저장 데이터 제거 |

이 넷은 구분해야 한다. 프로젝트가 끝났다고 관련 기록을 모두 바로 지워야 하는 건 아니다. 업무 이력이나 정당한 보존 목적이 있을 수 있다. 반면 사용자가 삭제를 요구한 개인정보는 관련 법령과 보존 의무를 검토해 처리해야 한다. 한국 개인정보 보호법 제21조는 개인정보가 불필요해진 경우의 파기 원칙을, 제36조는 일정 조건에서의 정정·삭제 요구를 규정하고 있다.

그래서 기억을 얼마나 오래 유지할지는 저장 용량이나 모델 성능만으로 정할 문제가 아니다. **저장 목적, 정보의 성격, 사용자의 권리, 보존 의무를 함께 봐야 한다.**

## 삭제한 기억이 다시 나타날 수도 있을까?

AI 서비스는 같은 정보를 여러 형태로 가지고 있을 수 있다.

- 원본 대화 기록
- 장기 기억 저장소
- 대화 요약
- 검색 인덱스
- 작업 상태와 로그

장기 기억에서 어떤 선호를 지웠더라도 원본 대화에 같은 정보가 남아 있다면, 나중에 메모리를 다시 만드는 과정에서 같은 선호가 다시 추출될 수 있다. 그래서 삭제 기능을 설계할 때는 이걸 구분해야 한다.

1. 사용자가 삭제를 요청한 대상은 무엇인가?
2. 그 정보가 어느 저장소에 있는가?
3. 파생된 요약이나 검색 인덱스에도 들어 있는가?
4. 법적으로 따로 보존해야 하는 정보가 있는가?
5. 삭제 후에도 그 정보가 다시 쓰이는가?

특히 마지막은 실제로 테스트해야 한다. 저장소에서 삭제가 성공했다고 AI가 그 정보를 더 이상 쓰지 않는다는 것까지 자동으로 보장되지는 않는다.

## Agent Memory의 생명주기를 어떻게 설계할까?

리서치 내용을 바탕으로 메모리의 생명주기를 이렇게 나눠 볼 수 있다.

| 단계 | 관리 기준 |
|---|---|
| 저장 후보 | 장기 기억할 가치가 있는 정보인가? |
| 활성 기억 | 지금 유효하고 쓸 수 있는 정보인가? |
| 재검토 | 오래됐거나 충돌하는 정보인가? |
| 갱신 | 새 사실로 고치거나 적용 범위를 바꿔야 하는가? |
| 비활성화 | 현재 판단에서는 빼되 보존할 이유가 있는가? |
| 삭제 | 삭제 요청, 목적 달성, 보존기간 등의 기준에 따라 제거해야 하는가? |

모든 정보가 이 순서대로 움직일 필요는 없다. 사용자가 삭제를 명시적으로 요청했다면 재검토 단계를 기다리지 않고 삭제 정책에 따라 처리해야 한다. 명시적인 수정 요청도 정해진 조건을 충족하면 바로 반영할 수 있어야 한다.

이 생명주기를 실제 시스템으로 만들려면 메모리 내용뿐 아니라 관리에 필요한 메타데이터도 함께 정해야 한다.

| 메타데이터 | 목적 |
|---|---|
| Memory ID | 기억 식별 |
| 사용자·업무 범위 | 다른 사용자나 프로젝트와 섞이지 않게 함 |
| 정보 출처 | 직접 입력인지 추론인지 확인 |
| 생성·수정 시점 | 시간에 따른 변경 확인 |
| 적용 범위 | 현재 작업인지 장기 기억인지 구분 |
| 유효 상태 | 활성, 재검토, 비활성 등 관리 |
| 보존·삭제 기준 | 불필요한 장기 보관 방지 |

실제로 구축한 데이터 스키마가 아니라, 서비스 기획 단계에서 고려할 수 있는 관리 항목이다.

## 메모리 관리 정책은 어떻게 검증할까?

9월에 구현한 선호 저장 도구를 활용한다면, 저장 이후의 갱신과 삭제까지 테스트하는 실험을 설계할 수 있다.

**실험 목적:** 사용자의 선호가 바뀌거나 삭제됐을 때, 에이전트가 기존 기억을 어떻게 처리하는지 확인한다.

| 시나리오 | 테스트 내용 | 기대 결과 |
|---|---|---|
| 명시적 변경 | 기존 선호를 새 조건으로 수정 | 새 조건 반영 |
| 일시적 예외 | 평소 선호와 다른 요청을 한 번 수행 | 기존 선호를 무조건 덮어쓰지 않음 |
| 정보 충돌 | 같은 항목에 서로 다른 조건 제시 | 출처·시점·적용 범위 확인 |
| 기억 삭제 | 저장된 선호 삭제 요청 | 정의된 삭제 범위에서 제거 |
| 삭제 후 재질문 | 삭제 후 관련 추천 요청 | 삭제한 기억을 근거로 다시 쓰지 않음 |

최종 응답만 보는 것으로는 부족하다. 메모리가 실제로 어떻게 바뀌었는지, 어떤 기억이 조회됐는지, 지금 요청에 어떤 정보가 전달됐는지 함께 확인해야 한다.

| 지표 | 확인할 내용 |
|---|---|
| Memory Update Accuracy | 명시적 수정 요청을 정확히 반영한 비율 |
| Stale Memory Usage Rate | 유효하지 않은 기억을 사용한 비율 |
| Deletion Compliance Rate | 삭제 대상에 대한 삭제 정책 이행 비율 |
| Unnecessary Retention Rate | 보존할 필요가 없는 기억이 남아 있는 비율 |

이 노트에서 제안한 평가 기준이고, 실제 측정 결과는 아니다. 특히 삭제 정책은 최종 응답뿐 아니라 저장소와 검색 경로를 함께 확인해야 해서 별도 검증이 필요하다. 아직 이 실험은 하지 않았다. 나중에 기존 Agent 실습을 넓힌다면, 메모리 변경 전후의 상태와 답변을 비교해 볼 수 있겠다.

## 현재의 생각

AI Agent의 메모리를 처음 접했을 때는 이전 대화를 얼마나 오래 기억할 수 있는지가 중요하다고 생각했다. 하지만 리서치를 하면서 기억의 양보다 **기억의 정확성, 유효성, 통제 가능성**이 더 중요한 설계 기준일 수 있다는 걸 알게 됐다.

- **저장:** 앞으로도 쓸 가치가 있는 정보인가?
- **갱신:** 기존 정보가 지금도 유효하고 새 정보와 충돌하지 않는가?
- **삭제:** 더 이상 보존할 필요가 없거나 사용자가 삭제를 요구한 정보인가?

메모리를 많이 저장하면 이전 맥락을 활용하는 데 도움이 되지만, 오래된 정보나 잘못 추론한 정보까지 계속 남겨 두면 오히려 답변 품질이 떨어질 수 있다.

결국 좋은 메모리 시스템은 모든 것을 기억하는 시스템이 아니라, **필요한 정보를 적절히 유지하면서 더 이상 유효하지 않은 정보는 갱신하거나 쓰지 않도록 관리할 수 있는 시스템**이라고 생각한다. AI 서비스 기획에서도 “대화 기억 기능을 제공한다”는 요구사항을 넘어, 어떤 정보를 저장하고 수정·삭제할 수 있는지, 그 결과를 어떻게 검증할지까지 정의해야 한다.
