> 관측은 어디에서 문제가 발생했는지 추정하는 과정이고, 평가는 수정 이후 실제로 개선되었는지 확인하는 과정이다.

## 문제 제기

AI 서비스에서 잘못된 답변이 나왔을 때, 가장 먼저 확인해야 할 것은 무엇일까?

일반적인 소프트웨어 오류는 예외 메시지나 서버 로그로 실패 지점을 추적할 수 있다. 하지만 RAG나 AI Agent는 검색, 프롬프트 구성, 모델 추론, 도구 호출 등 여러 단계를 거쳐 결과를 만든다. 최종 답변이 틀렸다는 사실만으로는 어느 단계에서 문제가 생겼는지 알기 어렵다.

예를 들어 세무 상담 AI가 잘못된 세율을 안내했다고 가정해 보자.

- 검색 시스템이 오래된 법령을 가져왔을 수 있다
- 최신 법령을 검색했지만, 필요한 부분이 모델에 전달되지 않았을 수 있다
- 올바른 근거를 전달했지만 모델이 잘못 해석했을 수 있다
- 도구 호출이나 후처리 과정에서 값이 바뀌었을 수 있다

결과는 모두 ‘잘못된 답변’이지만, 원인에 따라 고쳐야 할 대상은 다르다. 그렇다면 AI 서비스는 **최종 결과뿐 아니라 결과가 만들어지는 과정까지 기록해야 하지 않을까?**

## AI 오류를 단계별로 나눠 보기

AI의 실패를 하나의 문제로 보지 않고 단계별로 구분할 필요가 있다.

![AI 에이전트의 처리 과정: 질문 해석, 근거 검색, 도구 호출, 정책·권한 검증, 답변 생성, 최종 응답. 설명을 위한 예시 구조이며, 실제 에이전트는 검색과 도구 호출을 반복하거나 일부 단계를 생략할 수 있다.](media/notes/ai-failure-pipeline-clean.png)

| 단계 | 발생 가능한 문제 | 확인할 정보 |
|---|---|---|
| Retrieval | 관련 문서를 검색하지 못함 | 검색어, 검색 문서, 점수 |
| Context | 필요한 정보가 누락·잘림 | 모델에 실제 전달된 컨텍스트 |
| Generation | 근거를 잘못 해석하거나 없는 사실을 생성 | 모델 입력·출력, 프롬프트 |
| Tool Calling | 잘못된 도구 또는 인자 선택 | 도구 이름, 인자, 실행 결과 |
| Policy / Validation | 부적절한 실행을 허용하거나 정상 작업을 차단 | 정책 규칙, 판정, 승인 상태 |
| Output | 후처리 또는 응답 구성 오류 | 생성 결과와 최종 출력 비교 |

이 분류는 원인 분석의 출발점일 뿐이다. 하나의 오류가 여러 단계에 걸쳐 생길 수도 있어서, 각 단계를 독립적인 원인으로 단정할 수는 없다.

특히 구분해야 할 것은 **기술적인 실행 성공과 결과의 정확성은 다르다**는 점이다. API 호출이 정상적으로 끝나고 오류 코드가 없어도, 모델이 잘못된 정보를 만들었을 수 있다. 실행 상태와 답변 품질은 따로 평가해야 한다.

## Observability와 Tracing

관련 자료를 살펴보면서 AI Observability와 Tracing이라는 개념을 확인했다.

**Observability(관측 가능성)** 는 시스템이 외부로 남기는 데이터로 내부 동작과 상태를 이해할 수 있는 능력이다. AI 서비스에서는 모델 호출뿐 아니라 검색, 도구 실행, 입력과 출력, 지연 시간, 토큰 사용량도 관측 대상이 된다.

**Tracing(실행 추적)** 은 하나의 요청이 처리되는 과정을 단계별로 연결해 기록하는 방식이다.

- **Trace:** 하나의 요청이 처리되는 전체 실행 기록
- **Span:** Trace 안에서 수행된 개별 작업
- **Attributes:** 모델명, 입력·출력, 소요 시간, 상태 등 각 작업의 부가 정보

예를 들어 하나의 Trace 안에 검색 Span, LLM 호출 Span, 도구 실행 Span이 들어갈 수 있다.

### 최종 답변만 기록한다면?

질문과 최종 답변만 저장하면 오류가 났는지는 알 수 있지만, 원인을 분석하기에는 정보가 부족하다. 반대로 모든 입력, 검색 문서, 도구 인자와 중간 결과를 저장하면 추적에는 유리하지만 저장 비용이 늘고 민감정보가 노출될 위험도 커진다.

그래서 로그를 많이 남기는 것이 아니라, **실패 원인을 구분하는 데 필요한 정보를 우선 기록하는 설계**가 중요하다고 생각한다.

## 관련 도구 조사

AI 실행 과정을 추적하고 평가하는 도구로 LangSmith, Langfuse, Arize Phoenix를 살펴봤다.

| 도구 | 주요 기능 | 활용 관점 |
|---|---|---|
| LangSmith | Tracing, 실행 기록 분석, Evaluation | LangChain·LangGraph 기반 Agent 실행 확인 |
| Langfuse | Tracing, 프롬프트 관리, 평가, 사용량 분석 | 품질·비용·운영 지표 관찰 |
| Arize Phoenix | Tracing, RAG 평가, 실험 비교 | 검색과 생성 단계 분석 및 개선 검증 |

세 도구는 기능이 상당 부분 겹친다. 완전히 다른 목적의 도구로 구분하기보다는, 기존 개발 환경과 필요한 기능을 기준으로 고르면 되겠다.

LangSmith는 이전에 LangChain과 LangGraph를 학습하며 접했던 도구다. 이번에 다시 살펴보면서, 에이전트의 실행 결과를 확인하는 것과 실행 경로를 기록해 오류의 원인을 분석하는 것은 다른 활동이라는 점에 주목하게 됐다.

또한 Tracing 도구가 원인을 자동으로 확정해 주지는 않는다. 실행 기록은 원인에 관한 증거를 줄 뿐이고, 실제 원인 확인에는 추가 비교와 검증이 필요하다.

## 실패 원인은 어떻게 검증해야 할까?

Tracing으로 의심스러운 단계를 찾아도 그것만으로 원인이 확정되지는 않는다. 올바른 문서가 검색됐는데 최종 답변이 틀렸다면, 모델의 해석 오류뿐 아니라 컨텍스트 구성이나 프롬프트의 문제일 수도 있다.

그래서 이런 절차가 필요하다고 생각한다.

1. 실패 사례를 모으고 기대 결과를 정의한다
2. Trace로 단계별 입력과 출력을 확인한다
3. 오류 원인에 대한 가설을 세운다
4. 의심되는 요소를 고치고, 나머지 조건은 가능한 한 그대로 둔다
5. 같은 평가 사례와 추가 사례에서 개선 여부와 부작용을 확인한다

![틀린 답변의 원인을 좁히는 순서: 오류 감지, 올바른 근거 검색 여부에 따라 검색·데이터 또는 컨텍스트·생성 확인, 같은 조건에서 재현·비교, 수정과 회귀 테스트 및 모니터링](media/notes/ai-failure-triage-clean.png)

모델 출력에는 비결정성이 있을 수 있어서, 한 번 다시 돌려 본 결과로 개선 여부를 확정하기는 어렵다. 프롬프트, 모델, 검색 인덱스, 정책 등 바뀐 요소를 버전으로 관리하고, 같은 평가 데이터셋을 반복 실행해야 한다.

## 기획자 관점에서의 판단

### 모든 실행 정보를 기록하는 것이 최선일까?

처음에는 실행 과정을 상세하게 기록할수록 오류를 분석하기 쉬울 거라고 생각했다. 하지만 실제 서비스에서는 기록의 상세 수준에 따라 비용과 운영 부담이 달라진다. 특히 세무·의료·인사처럼 민감한 정보를 다루는 서비스에서는 사용자 입력이나 검색 문서, 도구 인자에 개인정보가 들어갈 수 있다.

| 판단 기준 | 고려할 사항 |
|---|---|
| 원인 분석 가능성 | 어떤 정보를 남겨야 실패 지점을 구분할 수 있는가? |
| 개인정보 보호 | 원문 저장이 필요한가? 마스킹이나 비식별화가 가능한가? |
| 저장 비용 | 모든 요청을 기록해야 하는가? |
| 운영 효율 | 어떤 실패를 우선 분석해야 하는가? |
| 재현 가능성 | 모델·프롬프트·데이터·정책 버전을 추적할 수 있는가? |

지금은 모든 데이터를 무조건 저장하기보다, **기본 실행 정보는 일관되게 기록하고 필요한 경우에만 상세 데이터를 제한적으로 수집하는 방식**을 먼저 검토하고 싶다. 예를 들어 정상 요청에서는 실행 단계, 소요 시간, 상태, 버전 같은 메타데이터를 남기고, 오류가 난 요청에서는 필요한 범위의 상세 정보를 볼 수 있게 설계하는 것이다.

단, 나중에 원문을 복구할 수 없는 경우도 있으므로 어떤 데이터를 미리 수집할지 정하는 과정이 중요하다.

### 오류 분석에도 우선순위가 필요하지 않을까?

모든 잘못된 답변을 같은 수준으로 조사할 수는 없다. 단순한 표현 오류와 잘못된 세율 안내, 승인되지 않은 도구 실행은 업무에 미치는 영향이 다르다. 발생 빈도뿐 아니라 사용자 영향도, 복구 가능성, 안전 위험을 함께 보고 분석 우선순위를 정해야 한다고 생각한다.

## 작은 실험 계획

**목표: 실패한 AI 응답 한 건을 Trace로 분석하고, 원인 가설을 세워 개선 여부를 검증한다.**

기존에 구현했던 RAG 또는 Agent 프로젝트를 활용해 볼 계획이다.

1. 정상 사례와 실패 사례를 포함한 소규모 평가 데이터셋을 만든다
2. LangSmith 등 Tracing 도구로 실행 과정을 기록한다
3. 실패 사례 하나를 골라 검색 결과, 모델 입력, 도구 호출을 확인한다
4. 원인 가설을 정리하고 관련 요소 하나를 바꾼다
5. 같은 사례를 다시 실행하고, 전체 평가 데이터셋에서도 성능을 비교한다

| 기록할 항목 | 내용 |
|---|---|
| 실패 사례 | 질문, 기대 결과, 실제 결과 |
| Trace | 실행 단계별 입력·출력과 상태 |
| 실행 환경 | 모델, 프롬프트, 데이터·정책 버전 |
| 원인 가설 | 문제가 발생했다고 추정한 단계와 근거 |
| 수정 내용 | 실제 변경한 요소 |
| 재검증 | 같은 조건에서의 개선 여부와 다른 사례에 준 영향 |

실험은 아직 하지 않았다. 결과를 확인한 뒤 실제 Trace와 함께 기록할 예정이다.

## 현재의 생각

AI의 답변이 틀렸을 때 중요한 것은 프롬프트를 고치거나 모델을 바꾸는 것이 아니라, **어떤 단계에서 무엇이 잘못됐는지 근거를 바탕으로 판단하는 것**이라고 생각한다. 이를 위해서는 개발 단계부터 실행 경로를 추적할 수 있어야 하고, 필요한 로그와 버전 정보를 설계해야 한다.

- 최종 응답의 성공·실패만으로는 개선 대상을 정하기 어렵다
- 단계별 실행 기록은 오류 원인을 좁히는 데 도움이 된다
- 로그 자체가 원인을 증명하지는 않으므로 재현과 비교 실험이 필요하다
- 관측 범위는 분석 가능성뿐 아니라 비용과 개인정보 보호를 함께 고려해야 한다

결국 AI 서비스 기획에서도 **무엇을 만들 것인가뿐 아니라, 문제가 생겼을 때 어떻게 발견하고 분석하고 개선할 것인가**를 설계해야 한다.
