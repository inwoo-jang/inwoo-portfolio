> [!예시]
> 고객 문의를 읽고 답변 초안을 만드는 기능을 가정한다. 담당자가 “멤버십 해지 문의 답변을 써 줘”라고 요청하면 몇 초 만에 문장이 나온다. 그런데 결제 상태를 확인했는지, 어떤 정책을 적용했는지, 초안인지 이미 발송한 답변인지 알 수 없다면 담당자는 일을 다시 확인해야 한다.

입력하는 시간은 줄었지만 확인할 일이 늘었다. 이런 기능의 UX는 무엇으로 평가해야 할까?

기존 SaaS에도 자동화·추천·승인·비동기 처리는 있다. 여기서는 **AI가 요청을 해석하고 결과를 생성하거나 행동을 선택하면서 추가되는 불확실성**에 집중한다. 업무용 SaaS에 AI 기능을 추가할 때 다시 확인할 기준을 연구와 공개 설계 사례에서 정리했다.

## AI를 쓰기 전에 기존 방식과 비교한다

사용자가 원하는 것은 AI와 대화하는 것보다 문의를 정확하게 처리하는 데 가깝다. 정해진 항목을 고르거나 정확한 상태값을 조회하는 일을 모두 자연어로 바꿀 필요는 없다.

Google PAIR는 사용자 문제를 먼저 정의하고, 규칙 기반 방식으로도 충분한지 비교하도록 권한다. 예측 가능성이 중요하거나 정보의 범위가 제한된 일에서는 더 단순한 방식이 유리할 수 있다는 설계 가이드다. [User Needs + Defining Success](https://pair.withgoogle.com/guidebook-v2/chapter/user-needs/)

문의 처리 예시라면 다음처럼 역할을 나누겠다.

| 해야 할 일 | 먼저 비교할 방식 | AI를 검토할 이유 |
| --- | --- | --- |
| 결제·해지 상태 확인 | 기존 조회 화면과 API | 조회 결과를 설명하는 보조 역할이 필요한가 |
| 정해진 정책 안내 | 검색·필터·승인된 답변 템플릿 | 다양한 문의 표현에서 관련 조항을 찾는 일이 어려운가 |
| 긴 문의 정리와 답변 작성 | 직접 요약·템플릿 편집 | 비정형 내용을 정리하는 이득이 검토·수정 부담보다 큰가 |

**AI가 만든 초안과 기존 템플릿 중 어느 쪽으로 정확한 답변을 더 쉽게 완성하는지**부터 비교한다. AI를 쓰지 않고 직접 처리하는 경로도 남긴다.

## 먼저 AI가 맡을 일을 나눈다

AI 기능을 모두 같은 UX로 설계할 수는 없다. 문장 초안을 만드는 기능과 실제 고객에게 발송하는 기능은 사용자가 확인할 내용이 다르다.

| 맡길 일 | 고객지원 예시 | 사용자가 알아야 할 것 |
| --- | --- | --- |
| 생성·편집 | 답변 초안 작성, 말투 수정 | 원본, 바뀐 부분, 아직 확인하지 않은 내용 |
| 판단 보조 | 문의 분류, 처리 방법 제안 | 적용 조건, 근거, 다른 선택지, 추가 확인할 항목 |
| 업무 실행 | 답변 발송, 해지 신청 접수 | 대상, 실행 내용, 권한, 승인 조건, 실제 처리 결과 |

한 서비스에 세 역할이 함께 있어도 경계는 표시해야 한다. “답변 준비 완료”와 “고객 발송 완료”가 같은 완료 메시지로 나오면 사용자는 다음 행동을 잘못 고를 수 있다.

Microsoft의 Human-AI Interaction 가이드라인은 첫 사용, 사용 중, 오류 발생, 장기 사용에 걸쳐 기능과 성능의 한계, 수정, 피드백, 통제를 다룬다. 이를 이 글에 적용하면 화면 요소를 추가하기 전에 **사용자가 AI에게 무엇을 기대하게 할지와 잘못됐을 때 어떻게 개입할지**를 정하는 것이 출발점이다. [Microsoft Research, CHI 2019 가이드라인 소개](https://www.microsoft.com/en-us/research/articles/guidelines-for-human-ai-interaction-eighteen-best-practices-for-human-centered-ai-design/)

## 입력창에 업무 맥락을 전부 떠넘기지 않는다

빈 입력창은 자유로워 보이지만, 사용자가 제품의 기능과 필요한 정보까지 알고 있어야 한다. 고객지원 담당자가 매번 고객·상품·정책·답변 채널을 프롬프트에 다시 적어야 한다면 기존 화면에서 제공하던 맥락을 잃은 셈이다.

NN/g의 좁은 범위와 넓은 범위의 생성형 AI 기능을 비교한 정성적 사용성 연구에서는 좁은 범위의 기능이 목적 이해, 요청 작성, 결과 조정에 더 수월한 경향이 있었다. 모든 업무에서 좁은 기능의 성과가 더 높다는 보편적 결론은 아니다. [Scope in Generative AI Features](https://www.nngroup.com/articles/scope-ai-features/)

문의 답변을 설계한다면 자연어 입력과 기존 업무 화면을 함께 쓰겠다.

- **지금 선택된 문의:** 어떤 고객·문의에 대한 작업인지 표시한다.
- **할 일 선택:** 초안 작성, 요약, 말투 수정처럼 시작할 작업을 제공한다.
- **사용할 맥락:** 참조할 문의·정책·첨부파일을 확인하고 제외할 수 있게 한다.
- **추가 질문:** 결과나 실행 범위가 달라지는 정보가 빠졌을 때 묻는다.

예를 들어 말투가 정해지지 않은 경우에는 기본값으로 초안을 만들 수 있다. 어느 고객에게 발송할지 불명확하다면 실행 전에 확인해야 한다. 모든 모호함에 질문을 늘리기보다 **가정해도 수정할 수 있는 조건과, 먼저 확인해야 하는 조건**을 나눈다.

제품이 자동으로 가져온 맥락도 사용자에게 보여줘야 한다. 이전 대화나 다른 고객의 정보가 섞여 있어도 사용자가 알아볼 수 없다면, 입력창이 간단해진 만큼 오류 발견은 어려워진다. 실제 데이터 접근권한은 서버에서 확인하고 화면에는 허용된 범위만 제공한다.

## 시작 전에 데이터·시간·비용·실행 범위를 알린다

결과를 보고 나서야 첨부파일이 외부 서비스에 전송됐다는 사실을 알면 사용자가 선택할 기회는 이미 지나갔다. OECD의 2026년 정책 브리프는 프롬프트의 개인정보 처리와 학습 사용 여부를 알리고, 개인정보처리방침에만 의존하지 않고 상호작용 시점에 관련 정보를 제공하는 방식을 다룬다. [Enhancing user control and privacy protections in the context of AI](https://www.oecd.org/en/publications/enhancing-user-control-and-privacy-protections-in-the-context-of-ai_e0bd9a46-en/full-report.html)

이 관점에 시간·비용·실행 범위를 더해, 작업 시작 전 화면에서 다음을 확인할 수 있게 설계한다.

| 확인할 내용 | 보여줄 시점과 행동 |
| --- | --- |
| 사용할 문의·정책·첨부파일 | 실행 전 선택된 자료를 표시하고 불필요한 자료는 제외 |
| 외부 전송·보관·학습 사용 | 실제 처리 방식을 안내하고 민감한 자료를 넣기 전에 확인 가능하게 함 |
| 예상 대기 | 관측 근거가 있으면 범위로 안내하고, 길어질 때 이탈·알림·재진입 경로 제공 |
| 사용자에게 청구되는 비용·한도 | 유료 실행 전 차감 단위, 재시도·중단 시 과금 조건, 한도 초과 처리 안내 |
| 이번 작업의 실행 범위 | 초안만 만드는지, 조회하는지, 외부 발송까지 하는지 표시 |

시간·비용·실행 범위를 묶은 표는 이 글의 설계안이다. 정확히 예측할 수 없는 시간이나 비용을 확정값처럼 약속하지 않는다. 모든 실행에 긴 안내창을 띄우기보다, 기본 설정을 확인할 경로를 두고 **새 자료를 전송하거나 유료 작업·외부 실행으로 범위가 넓어지는 지점**에서 다시 안내한다. 안내와 별개로 데이터 접근·전송·실행 권한은 시스템에서 검사한다.

## 결과는 다시 읽고 고칠 수 있는 작업물로 남긴다

대화는 요청을 구체화하거나 추가로 묻기에 편하다. 다만 결과를 검토할 때는 원문과 수정안이 대화 여러 곳에 흩어지지 않는 편이 낫다. 다음은 고객 문의 답변을 위한 설계 예시다.

| 화면 영역 | 담을 내용 | 허용할 행동 |
| --- | --- | --- |
| 원본 문의 | 고객 요청, 확인된 계약·처리 상태 | 원문 열기, 확인된 정보 갱신 |
| 적용 근거 | 정책의 해당 조항, 버전, 적용 조건 | 주장과 근거 대조 |
| 답변 초안 | 고객에게 전달할 문장 | 직접 편집, 선택 영역만 재작성 |
| 확인할 항목 | 정보 부족, 조건 불일치, 미확인 사실 | 보완, 보류, 담당자 이관 |
| 처리 상태 | 초안·검토·발송과 결과 | 허용된 다음 단계로 이동 |

전체 재생성을 유일한 수정 방법으로 두지 않는다. 문장 하나를 바꾸려다가 이미 검토한 내용까지 달라지면 검토를 처음부터 해야 한다. 사용자가 직접 고친 부분은 보존하고, AI가 바꾼 범위와 이전 버전으로 돌아갈 지점을 보여준다.

여러 사람이 검토하는 B2B 업무라면 현재 버전, 누가 수정했는지, 어떤 버전을 승인했는지도 필요하다. 검토 중에 본문이 바뀌었다면 기존 승인이 새 내용에도 유효한지 정책으로 정해야 한다. 이는 이 글의 설계 제안이며 특정 제품의 구현을 설명한 것은 아니다.

## 신뢰를 높이는 표시와 검증을 돕는 표시는 다르다

Bansal 등의 CHI 2021 연구는 세 데이터셋의 의사결정 과제에서 AI의 설명이 사람과 AI의 공동 성능을 추가로 높이지 못했으며, AI가 맞거나 틀린 경우 모두 제안에 동의하는 경향을 높였다고 보고했다. 설명이 필요 없다는 뜻보다는, **설명을 보여줬다는 사실만으로 검토가 효과적이었다고 볼 수 없다는 근거**로 읽었다. [Does the Whole Exceed its Parts?](https://arxiv.org/abs/2006.14779)

Ding 등의 AAAI 2025 연구에서도 인용이 있으면 자기보고 신뢰가 높아졌고, 무관한 인용에서도 그 효과가 나타났다. 인용을 확인한 참가자에게서 신뢰가 낮아지는 양상도 관찰됐다. 이 결과를 인용 확인의 보편적인 인과효과로 단정하기보다, 링크의 존재와 근거의 타당성을 구분해야 한다는 질문으로 가져온다. [Citations and Trust in LLM Generated Responses](https://ojs.aaai.org/index.php/AAAI/article/view/34550)

그래서 검토 화면에는 설명의 분량보다 대조할 수 있는 정보를 우선 두겠다.

- 답변의 어느 문장이 어떤 원문 구간을 근거로 하는가?
- 그 정책은 이 고객과 현재 상황에 적용되는가?
- 실제로 확인한 사실과 추가로 확인해야 할 내용이 구분되는가?
- 정보를 보완하면 어느 부분을 다시 검토해야 하는가?

모델이 말하는 “확신도 90%”를 검증 없이 정답일 확률로 보여주지는 않는다. 수치를 쓴다면 무엇을 측정한 값인지, 해당 업무에서 어떻게 보정·검증했는지 정해야 한다. 그런 근거가 없다면 “결제 상태 미조회”, “적용 정책 확인 필요”처럼 **확인하지 못한 조건을 구체적으로 표시하는 방식**부터 검토한다.

## 사람의 확인은 판단할 수 있는 지점에 둔다

모든 단계에서 확인 버튼을 누르게 한다고 검토 품질이 높아지는 것은 아니다. Buçinca 등의 2021년 연구에서는 숙고를 요구하는 상호작용이 단순 설명 방식보다 과도한 AI 의존을 줄였지만, 과도한 의존을 가장 많이 줄인 설계의 주관적 평가는 가장 낮았다. 검토 효과와 사용 부담을 함께 볼 필요가 있다. [To Trust or to Think](https://arxiv.org/abs/2102.09692)

사용자가 해당 내용을 판단할 지식과 원자료를 갖고 있는지도 중요하다. 초보자에게 “AI 결과가 맞는지 확인하세요”만 보여주는 것으로는 충분하지 않다. 필요한 비교 정보를 제공하거나 적절한 담당자에게 이관할 경로가 있어야 한다.

고객 발송 전에는 수신 대상, 최종 문구, 첨부파일, 채널을 하나의 실행안으로 보여줄 수 있다. 승인 뒤 내용이나 대상이 바뀌면 다시 확인할 조건을 정한다. 실제 실행 허용 여부는 시스템에서도 검사해야 한다. 승인 화면만으로 권한 통제가 완성되지는 않는다.

이 관점을 검토 업무에 적용하면 확인 단계는 다음처럼 나뉜다.

| 상황 | 검토할 설계 |
| --- | --- |
| 초안의 말투만 바꿈 | 즉시 미리보기와 되돌리기 |
| 정책 근거가 부족함 | 부족한 근거 표시, 보완·보류·이관 |
| 외부 고객에게 발송함 | 구체적인 실행안 확인과 권한 검증 |
| 승인 후 본문·수신자가 바뀜 | 기존 승인 유효성 확인, 필요한 재승인 |

표는 예시다. 일괄 승인이나 사전 위임이 가능한지는 업무의 영향과 복구 가능성에 따라 정한다.

## 완료·중단·재시도의 의미를 업무 상태와 맞춘다

AI가 “처리했습니다”라고 답하는 것과 실제 업무가 완료되는 것은 다르다. 발송 도구를 호출했어도 실패하거나 결과가 아직 확인되지 않았을 수 있다. 화면은 확인된 시스템 상태를 기준으로 안내해야 한다.

| 실제 상황 | 화면에서 구분할 것 |
| --- | --- |
| 답변 초안만 만들어짐 | 발송 전 초안임을 표시 |
| 생성 중 사용자가 중단함 | 생성 중단과 저장된 초안의 상태 |
| 발송 요청의 응답이 시간 초과됨 | 결과 미확정, 상태 조회 중 |
| 일부 대상에게만 발송됨 | 성공·실패·미확정 대상 구분 |
| 담당자에게 넘김 | 이관 접수 여부와 다음 처리 경로 |

재시도 버튼을 누르면 초안만 다시 만드는지, 발송도 다시 요청하는지 알려야 한다. 결과가 불명확할 때는 기존 실행 상태를 먼저 확인한다. 이미 발송한 안내는 초안을 지우는 것만으로 취소되지 않으므로 정정 절차도 따로 필요하다.

확인할 것은 **화면 문구와 실제 작업 상태가 일치하는지**다. 중단 요청, 중단 완료, 이미 실행돼 중단할 수 없는 상태를 같은 버튼 동작으로 뭉치지 않는다.

키보드·스크린리더 사용자에게도 상태와 다음 행동이 전달돼야 한다. 상태를 색상이나 애니메이션에만 의존하지 않고, 스트리밍 중인 모든 토큰을 반복해서 읽거나 화면의 초점을 빼앗지 않도록 설계한다. 이 역시 실제 접근성 사용성 평가로 확인할 항목이다.

## 수정·피드백·기억을 같은 동작으로 취급하지 않는다

담당자가 이번 답변의 표현을 고쳤다고, 다음 문의에도 같은 표현을 자동 적용해도 되는 것은 아니다. 동료나 다른 고객에게까지 그 수정이 영향을 미칠지도 별개의 결정이다.

Google PAIR의 Feedback + Control 가이드는 피드백을 모델 개선과 연결하는 방법, 사용자에게 줄 효과와 반영 시점, 자동화와 통제의 균형을 구분한다. [Google PAIR](https://pair.withgoogle.com/guidebook-v2/chapter/feedback-controls/)

이를 업무 화면에 옮긴다면 다음 범위를 나누겠다.

- **이번 결과 수정:** 현재 작업물에만 반영한다.
- **개인 설정 저장:** 이후 어떤 작업에 적용될지 보여준다.
- **공유 정책 변경:** 팀에 영향을 주므로 별도 권한과 검토를 거친다.
- **품질 피드백 제출:** 즉시 답변이 고쳐지거나 모델이 학습한다고 약속하지 않고, 처리 방식과 반영 시점을 알린다.

개인화가 있다면 사용한 기억을 확인·수정·삭제하는 경로도 필요하다. 외부 처리나 품질 평가에 사용하는 데이터의 범위도 따로 정한다. 화면을 단순하게 만들기 위해 이 차이를 숨기면 사용자가 허용한 범위를 오해할 수 있다.

## 기능이 바뀌면 이전의 기대도 다시 확인한다

처음에 “초안만 만든다”고 배운 사용자는 다음에도 같은 동작을 예상한다. 이후 자동 발송 기능이 생겼는데 예전 설정이 그대로 적용되면, 같은 버튼을 누르고 다른 결과를 맞게 된다.

Microsoft의 가이드라인은 장기 사용에서 신중한 업데이트와 변경 알림, 전체 설정을 통제할 수 있는 경로를 함께 다룬다. 이를 업무 기능에 적용한다면 모델 이름이 바뀌었다는 공지보다 **사용자의 확인과 행동이 어떻게 달라지는지**를 안내하겠다. [Microsoft Research](https://www.microsoft.com/en-us/research/articles/guidelines-for-human-ai-interaction-eighteen-best-practices-for-human-centered-ai-design/)

- **역할·권한 변경:** 초안 작성에서 자동 발송으로 넓어지면 기존 설정이 새 실행까지 허용하는지 다시 확인한다.
- **근거·동작 변경:** 적용 정책이나 처리 방식이 달라졌다면 영향을 받는 작업에서 알리고, 이전 승인 결과의 유효성을 확인한다.
- **누적된 설정:** 저장한 선호·기억·위임 권한을 한곳에서 확인·수정·해제할 수 있게 한다.

작업에 적용한 모델·정책 버전은 문제를 재현할 수 있도록 기록한다. 모든 내부 변경을 팝업으로 알리기보다, 결과·권한·데이터 사용·비용에 영향을 주는 변경을 구분한다. 테스트에서도 처음 쓰는 사람과 이전 동작에 익숙한 사람을 나눠 확인한다.

## 화면과 함께 AI의 행동을 검증한다

토스의 「AI로 바꾼 제품 설계의 순서」는 고객 문의에 대한 시나리오와 프로토타입을 함께 발전시키고, 조건 조합을 바꿔 대화를 반복 검증한 과정을 소개한다. 내가 참고할 부분은 화면 완성 뒤 AI를 붙이는 대신 **같은 문의라도 고객 상태에 따라 행동이 달라지는지 시험했다는 점**이다. 한 팀의 공개 설계 사례이며 다른 조직의 일정이나 효과를 보장하는 자료는 아니다. [토스 기술 블로그](https://toss.tech/article/chatbot)

이 글의 문의 답변 예시라면 최소한 다음을 프로토타입에서 확인하겠다.

| 테스트 조건 | 확인할 결과 |
| --- | --- |
| 문의에는 해지 요청만 있고 결제 상태는 없음 | 필요한 조회·추가 질문을 하고 환불 여부를 추측하지 않음 |
| 고객 조건과 검색한 정책이 맞지 않음 | 적용 불일치를 표시하고 확인 전 확정 안내를 하지 않음 |
| 외부 전송 전에 첨부파일을 제외함 | 실제 전송·참조 대상에서도 제외 |
| 유료 작업이 한도에 도달함 | 고지한 정책에 따라 중단하거나 추가 확인 후 진행 |
| 담당자가 일부 문장을 직접 수정함 | 다른 영역 재작성 시 수정 내용을 보존 |
| 승인 후 수신자나 본문이 달라짐 | 기존 승인으로 실행 가능한지 정책에 따라 재검증 |
| 발송 결과가 불명확함 | 성공으로 안내하거나 즉시 중복 발송하지 않음 |
| 직접 처리하려는 사용자 | 기존 편집·발송 경로를 이용할 수 있음 |
| 초안 전용 기능에 자동 발송이 추가됨 | 이전 사용자도 변경을 알아보고 실행 범위를 선택할 수 있음 |

## 생성 속도보다 최종 해결까지의 부담을 비교한다

AI 기능의 사용률이나 만족도만으로 업무 개선을 판단하기 어렵다. 잘못된 초안을 그대로 수용해서 처리가 빨라졌을 수도 있고, 어려운 문의를 모두 이관해서 AI 완료 단계만 좋아 보일 수도 있다.

아래는 특정 논문의 표준 지표가 아니라 이 글의 평가 제안이다.

| 평가할 것 | 비교 방법 |
| --- | --- |
| 업무 결과 | 동일한 조건에서 올바르게 해결한 비율, 미해결·이관·실패를 구분 |
| 전체 시간 | 요청 작성 + 대기 + 검토 + 수정 + 이관 뒤 해결까지 측정 |
| 검증 효과 | 검토가 필요한 오류 중 발견한 비율, 틀린 제안 중 그대로 수용한 비율 |
| 통제·복구 | 수정·중단·재시도가 의도한 상태로 이어지는지 확인 |
| 비용·부담 | 모델 호출과 재생성 비용, 사람의 확인·재작업 시간 포함 |

AI 없이 처리한 경우와 같은 업무 유형·난이도·사용자 숙련도로 비교한다. 사람이 혼자 하는 것보다 나아졌는지와, AI 단독보다 사람의 개입이 도움이 되는지도 다른 질문이다. 2024년 사람-AI 협업 메타분석도 더 나은 단독 수행자와 비교했을 때 협업이 평균적으로 자동 시너지를 내지는 않았으며, 과업 유형에 따라 차이가 있다고 보고했다. [When combinations of humans and AI are useful](https://www.nature.com/articles/s41562-024-02024-1)

첫 사용과 반복 사용도 나눠 본다. 처음에는 모든 근거를 읽던 사용자가 익숙해진 뒤 잘못된 결과까지 그대로 수용하지 않는지 확인해야 한다. 시험에서는 오류가 포함된 안전한 과제를 사용하되, 실제 고객에게 잘못된 안내를 보내는 실험과는 분리한다.

## 다음 설계에서 남길 것

AI UX를 설계할 때는 화면과 함께 다음 기준을 남긴다.

1. **도입·범위:** 기존 폼·검색·템플릿보다 나은 점과 AI에 맡길 역할은 무엇인가.
2. **시작 전 안내:** 어떤 데이터·시간·비용·실행 범위를 언제 알리는가.
3. **입력·작업물:** 필요한 맥락을 어떻게 받고 원본·근거·수정 내용을 어떻게 비교하는가.
4. **통제:** 누가 무엇을 판단하고, 승인·중단·이관하는가.
5. **상태·복구:** 완료·실패·미확정을 무엇으로 판정하고 어떻게 복구하는가.
6. **반복 사용:** 변경된 동작을 어떻게 알리고 저장된 설정·권한을 다시 확인하는가.
7. **평가:** 검토와 수정까지 포함한 전체 업무가 기존 방식보다 나아졌는가.

**사용자가 결과를 확인하고 필요한 부분을 고쳐 실제 업무를 끝낼 수 있는지**까지 비교한다. 초안이 나오는 시간만 줄었다면, 다음에 확인할 것은 검토와 재작업에 드는 시간이다.
